# LLM Wiki

**一种利用 LLM 构建个人知识库的模式。**

这是一份思路文件，旨在复制粘贴到你自己的 LLM Agent 中（如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高层思想，具体细节由你的 Agent 与你共同构建。

---

## 核心理念

大多数人与 LLM 和文档的交互方式类似于 RAG：你上传一组文件，LLM 在查询时检索相关片段，然后生成答案。这能工作，但 LLM 在每个问题上都得从头重新发现知识。没有积累。问一个需要综合五份文档的微妙问题，LLM 每次都得查找和拼凑相关片段。没有什么是被构建起来的。NotebookLM、ChatGPT 文件上传和大多数 RAG 系统都是这样工作的。

这里的思路不同。LLM **增量构建并维护一个持久的 wiki**——一个结构化的、带交叉引用的 markdown 文件集合——而不是只在查询时从原始文档检索。当添加新来源时，LLM 不仅仅是为后续检索而索引它。它阅读它，提取关键信息，并将其整合到现有 wiki 中——更新实体页面、修订主题摘要、标注新数据与旧声明相矛盾的地方、加强或挑战不断演变的综合认知。知识被编译一次，然后*保持最新*，而不是在每次查询时重新推导。

这是关键区别：**wiki 是一个持久的、会复合的产物。** 交叉引用已经在那里了。矛盾已经被标注了。综合认知已经反映了你所阅读的一切。Wiki 随着你添加的每个来源和提出的每个问题而变得越来越丰富。

你永远不（或很少）自己写 wiki——LLM 编写和维护所有内容。你负责的是来源管理、探索和提出正确的问题。LLM 做所有枯燥的工作——总结、交叉引用、归档和记账——这些工作使知识库随着时间推移真正有用。在实践中，我让 LLM Agent 在一侧打开，Obsidian 在另一侧打开。LLM 根据我们的对话进行编辑，我实时浏览结果——跟随链接、查看图谱视图、阅读更新的页面。**Obsidian 是 IDE；LLM 是程序员；wiki 是代码库。**

这可以应用于许多不同的场景。例如：

- **个人**：追踪自己的目标、健康、心理、自我提升——归档日记条目、文章、播客笔记，并随着时间建立关于自己的结构化图景。
- **研究**：在数周或数月内深入一个主题——阅读论文、文章、报告，并逐步构建一个包含不断演变的论文的综合 wiki。
- **阅读一本书**：在阅读每一章时将其归档，为角色、主题、情节线索及其联系方式构建页面。读完后你就有了一个丰富的配套 wiki。想象一下 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝 wiki——数千个相互链接的页面，覆盖角色、地点、事件、语言，由社区志愿者多年构建。你可以在阅读时个人构建类似的东西，由 LLM 完成所有交叉引用和维护工作。
- **业务/团队**：由 LLM 维护的内部 wiki，来源包括 Slack 讨论、会议记录、项目文档、客户电话。可能有人在循环中审查更新。Wiki 保持最新，因为 LLM 做了团队中没人愿意做的维护工作。
- **竞争分析、尽职调查、旅行计划、课程笔记、爱好深入研究**——任何需要长期积累知识并希望其有序而不是分散的领域。

## 架构

有三层：

**原始来源** —— 你策划的源文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 从中读取但从不修改。这是你的事实来源。

**Wiki** —— 由 LLM 生成的 markdown 文件目录。包括摘要、实体页面、概念页面、比较、概述、综合。LLM 完全拥有这一层。它创建页面、在新来源到来时更新它们、维护交叉引用并保持一切一致。你阅读它；LLM 编写它。

**Schema** —— 一份文档（如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM wiki 是如何组织的、有哪些约定，以及在摄取来源、回答问题或维护 wiki 时遵循什么工作流程。这是关键配置文件——它使 LLM 成为严谨的 wiki 维护者而不是通用聊天机器人。你和 LLM 会随着时间共同演进这个，以找出什么适合你的领域。

---

## 操作

**摄取（Ingest）。** 你把一个新来源放入原始集合，并告诉 LLM 处理它。一个示例流程：LLM 阅读来源，与你讨论要点，在 wiki 中写一个摘要页面，更新索引，更新 wiki 中相关的实体和概念页面，并在日志中追加一个条目。一个来源可能涉及 10-15 个 wiki 页面。就个人而言，我更喜欢一次摄取一个来源并保持参与——我阅读摘要、检查更新，并引导 LLM 强调什么。但你也可以在更少的监督下批量摄取多个来源。由你来开发适合你风格的工作流程，并将其记录在 schema 中供未来会话使用。

**查询（Query）。** 你针对 wiki 提问。LLM 搜索相关页面，阅读它们，并综合出带引用的答案。答案可以根据问题有不同的形式——一个 markdown 页面、一个比较表格、一个幻灯片 deck（Marp）、一张图表（matplotlib）、一块画布。重要的洞察：**好的答案可以存回 wiki 成为新页面。** 你要求的一个比较、一个分析、一个你发现的联系——这些是有价值的，不应该消失在聊天历史中。这样你的探索就像摄入的来源一样在知识库中复合。

**检查（Lint）。** 定期让 LLM 对 wiki 进行健康检查。查找：页面之间的矛盾、被新来源取代过的过时声明、没有入站链接的孤立页面、被提及但缺乏自己页面的重要概念、缺失的交叉引用、可以通过网络搜索填补的数据空白。LLM 善于建议新的要调查的问题和寻找新的来源。这使得 wiki 在增长过程中保持健康。

## 索引和日志

两个特殊文件帮助 LLM（和你）在 wiki 增长时导航。它们服务不同目的：

**index.md** 是面向内容的。它是 wiki 中所有内容的目录——每个页面列出链接、一句话摘要，以及可选的元数据如日期或来源数量。按类别组织（实体、概念、来源等）。LLM 在每次摄取时更新它。在回答查询时，LLM 首先阅读索引以找到相关页面，然后深入阅读它们。这在中等规模（~100 个来源，~数百个页面）下效果出奇地好，避免了对基于 embedding 的 RAG 基础设施的需求。

**log.md** 是时间序的。它是一个 append-only 的记录，记录发生了什么以及何时发生——摄取、查询、lint 通过。一个有用的技巧：如果每个条目以一致的前缀开头（例如 `## [2026-04-02] ingest | Article Title`），日志就可以用简单的 unix 工具解析——`grep "^## \[" log.md | tail -5` 给你最后 5 个条目。日志给你 wiki 演变的 timeline，并帮助 LLM 理解最近做了什么。

## 可选：CLI 工具

在某个时候，你可能想构建小工具来帮助 LLM 更高效地操作 wiki。搜索引擎是最明显的——在小规模下索引文件就足够了，但随着 wiki 增长，你需要适当的搜索。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是 markdown 文件的本地搜索引擎，具有混合 BM25/向量搜索和 LLM 重排序，全部在设备上。它既有 CLI（所以 LLM 可以调用它），也有 MCP 服务器（所以 LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的东西——LLM 可以帮助你凭感觉写一个朴素搜索脚本，随着需求出现。

## 技巧和窍门

- **Obsidian Web Clipper** 是一个浏览器扩展，将网络文章转换为 markdown。非常有用，可以快速将来源放入你的原始集合。
- **本地下载图片。** 在 Obsidian 设置 → 文件和链接中，设置"附件文件夹路径"为固定目录（例如 `raw/assets/`）。然后在设置 → 热键中，搜索"下载"找到"下载当前文件的附件"并绑定到热键（例如 Ctrl+Shift+D）。在剪辑一篇文章后，按热键，所有图片都会下载到本地磁盘。这是可选的，但有用——它让 LLM 直接查看和引用图片，而不是依赖可能失效的 URL。注意 LLM 不能原生地在一次传递中读取带有内联图片的 markdown——变通方法是让 LLM 先阅读文本，然后单独查看一些或全部引用的图片以获得额外上下文。有点笨拙但效果足够好。
- **Obsidian 的图谱视图** 是查看 wiki 形状的最佳方式——什么连接到什么，哪些页面是枢纽，哪些是孤立的。
- **Marp** 是一种基于 markdown 的幻灯片 deck 格式。Obsidian 有它的插件。用于直接从 wiki 内容生成演示文稿很方便。
- **Dataview** 是一个 Obsidian 插件，对页面 frontmatter 运行查询。如果你的 LLM 向 wiki 页面添加 YAML frontmatter（标签、日期、来源计数），Dataview 可以生成动态表格和列表。
- Wiki 只是一个 markdown 文件的 git 仓库。你免费获得版本历史、分支和协作。

## 为什么这有效

维护知识库最枯燥的部分不是阅读或思考——而是记账工作。更新交叉引用、保持摘要最新、标注新数据何时与旧声明矛盾、维持数十个页面之间的一致性。人们放弃 wiki 是因为维护负担增长快于价值。LLM 不会厌倦，不会忘记更新交叉引用，可以一次触及 15 个文件。维护成本接近零，wiki 保持被维护。

人类的工作是策划来源、引导分析、提出好问题，并思考这一切的意义。LLM 的工作是其他一切。

这个思路在精神上与 Vannevar Bush 的 Memex（1945）相关——一个具有文档间关联路径的个人策划知识库。Bush 的愿景比网络最终变成的更接近这个：私人的、积极策划的，文档之间的连接与文档本身一样有价值。他无法解决的部分是谁来维护。LLM 解决了这个问题。

## 注意

这份文档有意抽象。它描述的是思路，而不是具体实现。确切的目录结构、schema 约定、页面格式、工具——所有这些都取决于你的领域、你的偏好和你选择的 LLM。以上提到的所有都是可选的和模块化的——选择有用的，忽略没用的。例如：你的来源可能只有文本，所以你根本不需要图片处理。你的 wiki 可能很小，索引文件就是你需要的，不需要搜索引擎。你可能不关心幻灯片，只想要 markdown 页面。你可能想要完全不同的输出格式集。正确使用它的方式是将其分享给你的 LLM Agent，并共同合作实例化一个适合你需要的版本。这份文档的唯一工作是传达这个模式。你的 LLM 可以弄清楚其余的。
