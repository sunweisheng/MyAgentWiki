## 问题 1：停用词需要自己定义吗

### 1. 基本结论

停用词不需要完全自己从零定义，但建议维护一份适合自己知识库的“小而稳”的停用词表。

可以分三层理解：

```text
通用中文停用词：的、了、是、在、和、或、一个、这个、那个
查询意图词：如何、怎么、为什么、区别、对比、流程、方案
领域噪声词：本文、作者、认为、系统、方法、问题、内容
```

通用中文停用词可以使用现成词表。  
查询意图词不要随便删除，因为它们往往表达用户想要的回答类型。  
领域噪声词应该随着知识库增长逐步观察和调整。

### 2. 不建议删得太狠

在 LLM-Wiki 中，更推荐的策略是：

```text
少量删除 + 适度降权
```

而不是把所有常见词都删掉。

例如：

```text
如何搭建一个 LLM Wiki 知识库
```

分词后可能得到：

```text
如何 / 搭建 / 一个 / LLM / Wiki / 知识库
```

其中 `一个` 可以弱化或删除，但 `如何` 不一定要删除，因为它说明用户可能需要步骤型回答。

### 3. 当前项目建议

初版只需要：

```text
1. 使用一份通用中文停用词表
2. 增加少量自己的领域噪声词
3. 保留“对比、区别、流程、原因、方案”等意图词
4. 后续通过 Lint 或检索效果再调整
```

一句话总结：停用词需要维护，但不要把它当成一次性设计完成的词典；它更像一份随着知识库演化的检索卫生清单。

## 问题 2：倒排索引如何与 BM25 共同使用

### 1. 二者的关系

倒排索引和 BM25 不是互相替代的关系。

可以这样理解：

```text
倒排索引 = 数据结构
BM25 = 基于倒排索引的相关性排序算法
```

倒排索引负责回答：

```text
某个词出现在哪些页面或 chunk 里？
```

BM25 负责回答：

```text
这些候选页面或 chunk 中，谁和用户问题最相关？
```

### 2. 一个简单例子

用户问：

```text
Chunking 和 BM25 在 LLM-Wiki 里分别起什么作用？
```

分词后：

```text
Chunking / BM25 / LLM-Wiki / 作用
```

倒排索引可能找到：

```text
Chunking -> chunk_001, chunk_004, chunk_009
BM25 -> chunk_002, chunk_004, chunk_010
LLM-Wiki -> chunk_001, chunk_002, chunk_004, chunk_008
```

合并后得到候选：

```text
chunk_001, chunk_002, chunk_004, chunk_008, chunk_009, chunk_010
```

然后 BM25 对这些候选打分，把最相关的结果排到前面。

### 3. 推荐流程

```text
Ingest 阶段：
raw -> normalize -> chunk -> 分词 -> 去停用词/降权 -> 建倒排索引

Query 阶段：
用户问题 -> 分词 -> 查倒排索引 -> BM25 排序 -> top_k -> LLM 阅读并回答
```

一句话总结：倒排索引负责快速找候选，BM25 负责给候选排序；BM25 通常就是依赖倒排索引高效实现的。

## 问题 3：向量检索只作为大规模召回的辅助手段是什么意思

### 1. 召回是什么

召回就是在正式回答问题前，先从知识库中找出一批可能相关的材料。

```text
用户问题 -> 召回候选内容 -> 排序 -> 阅读 -> 综合回答
```

### 2. BM25 和向量检索的差异

BM25 偏向字面匹配。

如果用户问：

```text
raw 和 wiki 为什么要分离？
```

BM25 很擅长找包含 `raw`、`wiki`、`分离` 这些词的页面。

但如果用户问：

```text
为什么知识库要保留事实来源和认知整理之间的边界？
```

这句话语义上仍然是在问 raw/wiki 分离，但字面词不完全一样。这时向量检索可以补充召回。

### 3. 为什么说只是辅助

LLM-Wiki 的核心不是每次从原始文档 embedding 里捞片段，而是：

```text
raw 原始资料
-> ingest 编译
-> wiki 结构化知识页
-> query 基于 wiki 回答
```

如果一开始就把所有 raw 都 embedding，然后每次从 raw 里临时拼答案，就退回传统 RAG 了。

更合理的混合架构是：

```text
BM25 召回 top 30
向量检索召回 top 30
合并去重
rerank / 加权
选 top 5-10 给 LLM 阅读
```

并且优先对整理过的 wiki 页面、高质量 chunk、claim 做 embedding，而不是优先对所有原始脏数据做 embedding。

一句话总结：向量检索是大规模时的补漏手段，不是 LLM-Wiki 的知识本体；知识本体仍然是被整理、命名、链接、溯源过的 Wiki 页面。

## 问题 4：BM25 需要自己实现吗

### 1. 基本结论

不需要自己手写 BM25。

初版应该使用现成工具，例如：

```text
rank_bm25：适合最小原型
SQLite FTS5：适合本地长期使用
Whoosh / Lucene / Elasticsearch / OpenSearch：适合更大规模
```

个人 LLM-Wiki 初期，`rank_bm25` 或 SQLite FTS5 就够了。

### 2. BM25 的几个因素需要手动设置吗

BM25 的核心因素包括：

```text
词频：查询词在当前文档里出现多少次
稀有度：这个词在整个文档集合里是否稀有
长度归一化：避免长文天然占优势
```

这些不需要你手动给每个词设置分数，算法会自动计算。

你真正需要调整的是外围规则：

```text
分词规则
自定义词典
停用词
搜索字段权重
搜索粒度：按 page 还是按 chunk
top_k 返回数量
```

### 3. BM25 参数是否要调

BM25 常见参数：

```text
k1：控制词频增长的饱和程度
b：控制文档长度归一化强度
```

初期可以不调，使用默认值。

只有当出现明显问题时再考虑：

```text
结果总偏向长文档 -> 可以适当提高 b
某个词重复很多次就排名过高 -> 可以适当降低 k1
```

一句话总结：BM25 不需要自己实现，也不需要手动设置词频和稀有度；你主要负责分词、词典、停用词、字段权重和检索粒度。

## 问题 5：搜索字段权重和页面权重设计是一件事吗

### 1. 二者相关但不同

搜索字段权重解决的是：

```text
同一个页面或 chunk 里，命中哪个字段更重要？
```

页面权重设计解决的是：

```text
不同类型、不同状态、不同质量的页面，谁天然更值得优先读？
```

### 2. 字段权重示例

推荐初版：

```text
title: 5
aliases: 4
summary: 3
headings: 2.5
body: 1
source_refs: 0.5
```

含义是：

```text
命中标题 > 命中别名 > 命中摘要 > 命中小标题 > 命中正文 > 命中引用区
```

### 3. 页面类型权重示例

```text
overview 综述页: 1.25
concept 概念页: 1.15
entity 实体页: 1.10
source-summary 来源摘要页: 1.00
qa QA 沉淀页: 0.95
draft 草稿/临时页: 0.70
```

页面状态权重：

```text
stable: 1.10
draft: 0.80
disputed: 0.90
outdated: 0.60
```

### 4. 实现方式

最简单的方式是拼接加权文本：

```text
title 重复 5 次
aliases 重复 4 次
summary 重复 3 次
headings 重复 2 次
body 正常放入
source_refs 降低权重
```

更工程化的方式是多字段分别打分：

```text
score =
5.0 * bm25(title)
+ 4.0 * bm25(aliases)
+ 3.0 * bm25(summary)
+ 2.0 * bm25(headings)
+ 1.0 * bm25(body)
+ 0.5 * bm25(source_refs)

final_score = score * type_weight * status_weight
```

一句话总结：字段权重决定页面内部哪里命中更重要；页面权重决定哪类页面天然更值得优先读。

## 问题 6：Query 阶段使用 Chunking，为什么不怕断章取义

### 1. 会怕，但可以通过流程控制

如果只把 wiki 页面切成很多 chunk，然后只让 LLM 看一个孤立 chunk，确实容易断章取义。

所以 Query 阶段使用 chunk 的原则不是“只读碎片”，而是：

```text
chunk 负责定位，页面上下文负责防误读
```

### 2. 推荐查询流程

```text
用户问题
-> 搜索 page metadata / title / summary / aliases
-> 找到可能相关的 wiki 页面
-> 在这些页面内部找相关 chunk
-> 给 LLM：页面摘要 + 标题路径 + 命中 chunk + 前后相邻 chunk
-> 如果问题复杂，再读取整页或多个相关页面
-> 综合回答
```

### 3. chunk 必须带上下文元数据

```yaml
page_title: BM25
page_type: concept
page_summary: BM25 是一种关键词检索排序算法
section_path:
  - LLM-Wiki 检索
  - BM25 的作用
previous_chunk: ...
next_chunk: ...
source_refs: ...
```

这样 LLM 看到的不是一段孤立文本，而是知道它属于哪一页、哪一节、什么主题。

### 4. 防止断章取义的规则

```text
1. 命中 chunk 时，同时带上 page summary
2. 带上 section_path
3. 同时读取 previous_chunk 和 next_chunk
4. 对高分页面优先读取 frontmatter 和目录
5. 综合型、判断型、对比型问题不要只读 chunk
6. 涉及证据时回读 source_refs
```

如果一个 wiki 页面经常需要被 chunk 局部读取，说明它可能太大，应该拆分成多个概念页、实体页或综述页。

一句话总结：Query Chunking 不是让 LLM 孤立地看碎片，而是用 chunk 找位置，再用页面摘要、标题路径、相邻 chunk 和必要的整页回读防止误解。

## 问题 7：如何让人工参与决策，并在处理后继续自动化执行

### 1. 核心思路

人工参与应该设计成可恢复的审核队列，而不是让自动化流程随口停在聊天里。

流程是：

```text
自动化发现不确定事项
-> 写入 review queue
-> 暂停危险动作
-> 人工做结构化决策
-> 系统读取决策
-> 从暂停点继续执行
```

### 2. 决策单示例

```yaml
review_id: review_20260527_001
type: possible_duplicate
status: pending
candidate_a: wiki/10_核心概念/向量检索.md
candidate_b: wiki/10_核心概念/语义搜索.md
reason: 两个页面都讨论通过语义相似度召回内容，存在概念重叠。
suggested_action: keep_related
options:
  - merge
  - alias
  - parent_child
  - keep_related
  - keep_separate
  - defer
```

人工处理后：

```yaml
status: approved
decision: keep_related
human_note: 向量检索是技术手段，语义搜索是搜索范式。
decided_by: human
decided_at: 2026-05-27T10:45:00+08:00
```

### 3. 状态机设计

Ingest 可以有这样的状态：

```text
new
-> normalized
-> chunked
-> analyzed
-> generated
-> review_required
-> review_resolved
-> linked
-> indexed
-> done
```

当需要人工判断时：

```json
{"run_id":"ingest_20260527_001","source_id":"src_20260527_xxx","status":"review_required","blocked_by":["review_20260527_001"],"resume_from":"generated"}
```

当人工决策完成后，系统从 `resume_from` 继续执行。

### 4. 决策结果如何转成动作

如果：

```text
decision: keep_related
```

自动执行：

```text
1. 不合并页面
2. 两个页面互加 related_links
3. alias registry 记录 not_aliases
4. 更新 index.md
5. 更新 log.md
6. review 移入 resolved/applied
7. ingest_state 继续推进
```

一句话总结：人工参与不是让人手工维护 wiki，而是让系统在高风险节点生成“决策单”；人只填决策，机器继续执行后续修改。

## 问题 8：在 Codex 中如何实现决策单和继续执行

### 1. 推荐目录

在 Codex 中不需要先做 UI，可以直接用本地文件实现：

```text
your-llm-wiki/
├── raw/
├── wiki/
├── scripts/
├── AGENTS.md
└── .llm-wiki/
    ├── state/
    │   └── ingest_state.jsonl
    ├── reviews/
    │   ├── pending/
    │   ├── decided/
    │   └── applied/
    └── logs/
        └── actions.jsonl
```

### 2. Codex 的工作方式

在 `AGENTS.md` 中写明：

```text
遇到合并、重命名、删除、别名冲突、覆盖旧结论等高风险动作时，不直接执行，而是生成 review 文件。
```

之后可以用固定口令协作：

```text
摄入这篇资料；遇到高风险决策先生成 review，不要自动合并。
```

```text
列出当前 pending reviews，并给我推荐处理方式。
```

```text
review_20260527_001 选择 keep_related，继续执行。
```

```text
读取已决定的 reviews，从 state 断点继续。
```

### 3. 第一版可以不写脚本

第一版完全可以靠 Codex 按规则读写这些文件。

流程稳定后，再把机械动作抽成脚本：

```bash
python scripts/wiki_review.py list
python scripts/wiki_review.py continue
```

一句话总结：在 Codex 中，“决策单”就是 YAML 文件；“继续执行”就是 Codex 读取 YAML 里的人工决策和 state 里的断点，然后自动完成页面修改、建链、索引和日志更新。

## 问题 9：知识声明 Claim 层如何在第一版实现

### 1. Claim 是什么

Claim 是从 chunk 中抽取出来的一条相对原子的知识声明。

它不是普通摘要，也不是整段原文。

例如：

```yaml
claim_id: claim_20260527_bm25_001
text: BM25 是一种用于关键词检索的相关性排序算法。
claim_type: definition
subject: BM25
predicate: is_a
object: 关键词检索排序算法
source_refs:
  - source_id: src_20260527_xxx
    chunk_id: chunk_003
confidence: high
status: active
```

### 2. 推荐目录

第一版可以这样设计：

```text
.llm-wiki/
├── sources/
│   └── sources.jsonl
├── chunks/
│   └── chunks.jsonl
├── claims/
│   ├── claims.jsonl
│   └── claim_index.json
├── reviews/
│   ├── pending/
│   └── resolved/
└── state/
    └── ingest_state.jsonl
```

最小实现只需要：

```text
.llm-wiki/chunks/chunks.jsonl
.llm-wiki/claims/claims.jsonl
```

### 3. Claim 最小字段

```json
{
  "claim_id": "claim_20260527_001",
  "text": "BM25 适合 LLM-Wiki 初期作为轻量关键词检索方案。",
  "claim_type": "evaluation",
  "subjects": ["BM25", "LLM-Wiki"],
  "source_refs": [
    {
      "source_id": "src_20260527_001",
      "chunk_id": "chunk_004",
      "excerpt": "BM25 适合个人知识库早期使用..."
    }
  ],
  "confidence": "medium",
  "status": "active",
  "created_at": "2026-05-27T10:00:00+08:00"
}
```

`claim_type` 初版可以包括：

```text
definition：定义
fact：事实
comparison：对比
causal：因果
procedure：流程/步骤
evaluation：判断/建议
warning：限制/风险
```

### 4. Ingest 阶段如何使用 Claim

```text
raw
-> normalize
-> chunk
-> 从 chunk 抽取 claims
-> claims 聚合到概念/实体
-> 生成或更新 wiki page
-> wiki page 引用 claim/source
```

不是每句话都要抽成 Claim。优先抽：

```text
定义
关键结论
限制条件
对比关系
流程步骤
版本变化
争议观点
数字、时间、人物、产品事实
```

### 5. Wiki 页面如何引用 Claim

可以在 frontmatter 中记录关键 claim：

```yaml
claims:
  - claim_20260527_001
  - claim_20260527_002
source_refs:
  - src_20260527_001#chunk_004
```

正文底部可加：

```markdown
## 支撑声明

- claim_20260527_001：BM25 适合 LLM-Wiki 初期作为轻量关键词检索方案。
- claim_20260527_002：BM25 在语义表达不一致时可能漏召回相关内容。
```

### 6. Claim 层的价值

Claim 层可以帮助：

```text
1. 让 Wiki 页面里的重要结论可追溯
2. 让不同来源的结论可以互相补充或冲突检测
3. 查询时可以搜索 Claim，再回查 chunk/source
4. Lint 时检查孤立、失效、冲突声明
```

遇到冲突时，不要强行合并，而是生成 review：

```yaml
type: claim_conflict
status: pending
claim_a: claim_xxx
claim_b: claim_yyy
suggested_action: mark_disputed
```

一句话总结：Claim 层是把 Wiki 页面里的重要结论拆成可追踪、可冲突检测、可复用的知识声明；第一版用 `claims.jsonl` 就够了，不必上数据库。

## 问题 10：使用 Codex 后，上下文预算自动分配是否还需要实现

### 1. 基本结论

如果主要由 Codex 来维护知识库，就不需要自己实现“自动识别 LLM 配置并自动分配上下文预算”的完整机制。

这类机制更适合：

```text
自己创建独立 Agent
自己调用 API
自己实现 RAG/检索问答系统
```

在 Codex 中，模型上下文、文件读取、工具调用、任务续接等能力主要由 Codex 负责。

### 2. 但仍然需要保留轻量阅读策略

不需要实现：

```text
自动识别模型上下文长度
动态计算 32k / 128k / 200k token 分配
复杂 token 预算公式
```

但仍然需要告诉 Codex：

```text
优先读哪些文件
什么时候只读摘要
什么时候读 chunk
什么时候读整页
什么时候回看 raw
```

### 3. 推荐写进规则手册的版本

```markdown
## 上下文读取规则

1. 查询时先读 index.md、相关页面 frontmatter、summary 和 headings。
2. 只有命中相关页面后，才读取正文相关 section 或 chunk。
3. 不要一次性读取大量 raw 原文，除非需要核验证据。
4. 对长页面优先读取：
   - title
   - aliases
   - summary
   - headings
   - related_links
   - 支撑 claims
5. 如果问题涉及判断、冲突或引用，必须回读 claim 对应 chunk/source。
6. 如果页面过长且经常只读局部，应建议拆分页面。
```

### 4. 当前项目分工

Codex 负责：

```text
实际上下文管理
文件读取
分批处理
必要时继续任务
根据规则决定读哪些材料
```

你需要定义：

```text
知识库目录结构
```

一句话总结：不需要为 Codex 再造一个上下文预算调度器，但需要给 Codex 一套轻量的知识库阅读策略。

## 最后总结

今天的讨论把 LLM-Wiki 从“理念和工程清单”进一步推进到了 Codex 落地层：

```text
检索层：停用词、倒排索引、BM25、字段权重、页面权重
召回层：BM25 为主，向量检索作为规模扩大后的补漏手段
读取层：Query Chunking 要配合页面摘要、标题路径、相邻 chunk 和必要的整页回读
治理层：高风险动作通过 review 决策单让人工参与
执行层：Codex 读取 review 和 state，从断点继续自动化
证据层：Claim 把重要结论变成可追踪、可检查、可冲突处理的知识声明
上下文层：不需要自建预算调度器，只需要为 Codex 定义阅读策略
```

这意味着当前最值得优先落地的不是复杂 Agent，而是：

```text
1. AGENTS.md 规则手册
2. .llm-wiki/chunks/chunks.jsonl
3. .llm-wiki/claims/claims.jsonl
4. .llm-wiki/reviews/ 决策单机制
5. .llm-wiki/state/ 状态断点
6. 基础 BM25 / FTS 检索
```

一句话总结：在 Codex 里做 LLM-Wiki，最关键的是把规则、证据、决策和状态都文件化；Codex 负责执行，人负责边界判断。
