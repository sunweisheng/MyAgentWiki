# 工程落地补充清单

> 编写时间：2026-05-24  
> 适用场景：作为《LLM-Wiki知识库搭建学习总结》的工程补充版，帮助把“理念上可行”的方案，推进到“真正能长期稳定运行”的系统。  
> 文档风格：可执行优先。  
> 使用方式：优先从“必须先做”开始逐项补齐，再推进到第二阶段和规模扩大阶段。

---

## 一、这份清单解决什么问题

前一份总结已经把 LLM-Wiki 的核心理念、目录结构、Ingest / Query / Lint 主流程、BM25、分词、Chunking、双向链接等关键概念讲清楚了。但从工程落地角度看，真正容易出问题的地方，通常不在“知道要做什么”，而在“系统跑起来以后是否可控、可恢复、可维护、可扩展”。

这份清单的目标不是重复已有内容，而是补足那些在工程实现中最容易被忽略、但后期最容易出事故的部分。

重点覆盖三类问题：

1. 系统是否能稳定反复运行，而不是跑几次就乱。
2. 知识是否能持续演化，而不是越积越脏。
3. 自动化能力是否有边界，不会让 AI 改坏知识库。

---

## 二、优先级总览

建议把工程落地拆成三层：

### 第一层：必须先做

这是最小可运行系统真正落地前就应该明确的部分。如果这层没补齐，知识库很容易出现重复页面、更新失控、长文处理失真、回写污染、检索不稳等问题。

### 第二层：第二阶段补强

这是系统能跑起来以后，为了让它更稳定、更准、更省成本、更易维护而需要逐步补充的能力。

### 第三层：规模扩大后再做

只有当文档数量明显增多、数据来源更复杂、团队协作需求提升，或者开始引入生产级自动化时，才值得投入的内容。

---

## 三、第一层：必须先做

## 1. 原始文档唯一标识机制

### 为什么必须做

如果没有稳定的 source_id，同一篇原文改个文件名、换个目录、重复导入一次，系统就可能把它当成新文档再次摄入，最后生成重复摘要、重复概念页、重复引用。

### 至少要明确的设计

- 每份原始资料必须有唯一标识
- 标识不能只靠文件名
- 优先使用内容哈希、来源 URL、来源时间戳等稳定特征组合

### 推荐做法

可以为每个原始文档维护如下信息：

```yaml
source_id: src_20260524_a13f9c
source_type: article
source_uri: https://example.com/llm-wiki
source_hash: sha256:xxxxxx
imported_at: 2026-05-24T10:30:00+08:00
```

### 需要你现在就决定的问题

- 相同内容但不同文件名，是否视为同一来源
- 相同 URL 但内容更新后，是否新建版本还是覆盖旧版本
- 同一文档多次摄入时，是跳过、增量更新还是进入审核队列

---

## 2. 摄入状态机

### 为什么必须做

如果没有状态管理，摄入流程一旦中断，就不知道一篇文档处理到哪一步了。后续重跑时可能要么重复干活，要么留下半成品。

### 至少要有的状态

建议每个 source 维护一个简单状态机，例如：

```text
new -> normalized -> chunked -> analyzed -> generated -> linked -> indexed -> done
                                 \-> failed
```

### 推荐落地方式

可以在一个 `ingest_log.jsonl`、`state.yaml`、SQLite 或轻量数据库中记录状态。

### 现在就要确定的规则

- 失败后是否允许从 chunked 阶段恢复，而不是整篇重来
- 页面已生成但未入索引，算不算成功
- 某一步失败后，是否允许自动重试

---

## 3. 规范名、别名、重定向机制

### 为什么必须做

知识库前期最容易看不出来的问题，就是命名漂移。比如：

- LLM / 大语言模型 / Large Language Model
- Claude / Claude Code
- MCP / Model Context Protocol
- Chunking / 分块 / 文档切块

如果没有 canonical name 和 alias 规则，系统很快就会出现一堆重复节点。

### 至少要有的设计

每个核心概念或实体，最好有：

- 一个规范页名（canonical title）
- 一组别名（aliases）
- 必要时有重定向说明

### 推荐元数据字段

```yaml
title: 大语言模型
aliases:
  - LLM
  - Large Language Model
canonical_id: concept_llm
```

### 现在就要明确的事

- 页面文件名是统一中文、统一英文，还是允许双语混用
- 搜索时是否对 aliases 做扩展匹配
- AI 生成页面时发现别名，是否优先链接到规范页

---

## 4. 页面创建策略与页面更新策略分离

### 为什么必须做

很多人前期只考虑“怎么生成页面”，但后期真正难的是“已有页面怎么更新”。

例如新资料来了以后：

- 是新建页面
- 是补充到已有页面
- 还是标记冲突、等待人工判断

如果不把这三类动作拆开，AI 很容易把旧内容直接改没。

### 建议明确三种更新模式

#### append

仅追加新信息，不改旧结论。

#### merge

把新旧信息融合成一版更完整内容。

#### conflict-mark

发现冲突，不强行合并，而是标记分歧来源。

### 推荐规则

在 `CLAUDE.md` 中明确：

- 如果新文档只是补例子或补引用，优先 append
- 如果新文档提供更完整定义，可 merge
- 如果新旧说法冲突，不允许直接覆盖，必须标注 `disputed` 或写入冲突说明

---

## 5. 最小溯源粒度设计

### 为什么必须做

现在很多人只记录“这条知识来自某个 raw 文件”，但这在后续工程中通常不够。

你后面会需要知道：

- 结论来自哪一页 PDF
- 来自哪一段 chunk
- 来自哪一部分原始对话
- 来自哪次摄入任务

### 推荐最小粒度

至少细到 chunk 级别，而不是只有 file 级别。

### 建议记录字段

```yaml
source_refs:
  - source_id: src_20260524_a13f9c
    chunk_id: chunk_003
    page_range: 5-6
    excerpt: "BM25 is a ranking function..."
```

### 工程收益

- 更容易做带引用回答
- 更容易做冲突追踪
- 更容易回看证据
- 后续做质量审计时有依据

---

## 6. Chunking 规则不能只写“要分块”

### 为什么必须做

“长文要分段加载”这个原则你已经考虑到了，但工程上不能停在这一步。真正影响质量的是切块规则本身。

### 你需要明确的维度

- 优先按标题切，还是按字数切
- chunk 之间是否 overlap
- 表格、代码块、引用块是否允许截断
- 太短的 chunk 是否要自动合并
- OCR 文本如何与相邻上下文拼接

### 一个可执行的初版规则

可以先定义：

- 先按 Markdown 标题切
- 单块超过阈值时再按段落切
- 单块过短时与相邻块合并
- 相邻 chunk 保留少量 overlap
- 代码块和表格尽量整体保留，不做中途截断

### 推荐补一层 chunk 元数据

```yaml
chunk_id: chunk_012
section_title: BM25 的工作原理
char_count: 1850
token_estimate: 920
previous_chunk: chunk_011
next_chunk: chunk_013
```

---

## 7. Query 预处理规范

### 为什么必须做

用户提问往往是口语化的，而底层检索更适合结构化 query。如果没有 query normalization，哪怕 BM25 本身没问题，检索效果也会打折。

### 建议至少做的预处理

- 去掉无意义口头词
- 识别专有名词并保留
- 对中英混写术语做统一化
- 对 aliases 做同义扩展
- 必要时从自然语言问题中提取核心检索词

### 示例

原问题：

“那个 Karpathy 提的 LLM-Wiki 里面，搜索到底是不是语义搜索啊？”

可以抽成更适合检索的关键词：

- Karpathy
- LLM-Wiki
- 搜索
- BM25
- 语义搜索

### 现在就要决定的边界

- query 改写是规则式实现，还是允许 LLM 辅助改写
- 是否允许搜索时同时查 title、summary、aliases、正文

---

## 8. 上下文预算分配规则

### 为什么必须做

即便检索找对了页面，也不代表回答一定稳。因为真正进入模型上下文的内容仍然有限。

### 你需要明确的分配问题

- 一次回答最多加载多少页面
- 一页最多读取多少 chunk
- 索引页、摘要、正文、历史对话各占多少 token
- 超预算时优先保留什么

### 一个建议的初版思路

可以先规定：

- 先读索引和候选页 summary
- 再选 Top 3 页面深入读 chunk
- 每页最多读取 2～4 个相关 chunk
- 回答必须附带来源页名

### 更工程化一点的想法

后面可以把预算规则写进配置，例如：

```yaml
context_budget:
  total_tokens: 24000
  system_rules: 3000
  query_history: 2000
  page_summaries: 4000
  page_chunks: 12000
  reserve_for_answer: 3000
```

---

## 9. 人工审批边界

### 为什么必须做

自动化越强，越要明确哪些事不能让 AI 直接做。

### 建议必须人工确认的动作

- 删除页面
- 合并页面
- 重命名 canonical page
- 大规模批量修复链接
- 覆盖高置信度旧结论
- 将一次问答直接沉淀为正式概念页

### 可直接自动执行的动作

- 补充缺失的 `updated` 字段
- 更新索引中的链接列表
- 新建来源摘要页
- 为正文自动加已有页面链接

### 需要你明确写进规则的地方

不是只写“AI 要谨慎”，而是要写成“哪些动作必须先 ask”。

---

## 10. Git 工作流最小规范

### 为什么必须做

Git 不只是备份，更是知识库的安全网。如果没有最小规范，后面要么无法回滚，要么很难看懂改动历史。

### 至少要补的规则

- `raw/` 是否纳入版本控制
- 自动生成缓存是否纳入版本控制
- 每次 ingest 是一个 commit 还是一批文件一个 commit
- commit message 如何命名
- 是否默认先在分支改，再人工 merge

### 推荐最小 commit 规范

```text
ingest: add summary and concept links for karpathy-llm-wiki article
update: merge new BM25 notes into concept page
lint: fix broken wikilinks and add missing metadata
```

### 一个很关键的现实问题

如果 `raw/` 中有大量 PDF、图片、网页存档，大概率要考虑 Git LFS 或者把大文件与 Wiki 页面分开管理。

---

## 11. 失败恢复与重试策略

### 为什么必须做

现实里一定会遇到：

- PDF 解析失败
- OCR 乱码
- 模型中断
- 页面写了一半
- 链接更新一半失败

### 至少要明确的策略

- 哪些失败可以自动重试
- 最多重试几次
- 是否保留中间产物
- 失败是否要写入错误日志
- 是否支持从中间阶段恢复

### 建议最低限度保留

- source_id
- 当前状态
- 最近错误信息
- 最近处理时间
- 最后成功阶段

这样下次排查不会完全失忆。

---

## 12. 输入标准化层

### 为什么必须做

真正进入系统的原始资料，不会永远都是干净 Markdown。你很快会遇到：

- PDF
- 网页剪藏
- 截图 OCR
- 导出的聊天记录
- 带格式噪声的富文本
- 代码仓库文档

### 推荐补一层 normalize pipeline

在进入 Ingest 主流程前，先把输入统一整理成“可分析文本 + 基础元数据”。

### 这个阶段至少处理

- 编码统一
- 多余格式噪声清理
- 图片说明保留策略
- 表格文本化策略
- 网页导航栏和广告内容清洗

### 核心原则

不要让 Ingest 同时承担“脏数据清洗”和“知识编译”两件事。

## 四、第二层：第二阶段补强

## 13. 中间产物缓存

### 为什么建议尽早做

如果每次都重新分词、重新 chunk、重新摘要、重新抽取实体，系统会越来越慢、越来越贵。

### 值得缓存的内容

- normalized text
- chunk 结果
- chunk 摘要
- 分词结果
- aliases 识别结果
- 页面级检索索引

### 推荐思路

先不一定上复杂数据库，可以先用本地文件缓存或轻量 SQLite。

---

## 14. 检索排序增强

### 为什么值得做

仅靠基础 BM25 能跑，但未必够稳。第二阶段可以加轻量 re-rank 策略，而不一定要上向量数据库。

### 可补的排序信号

- title 命中加权
- summary 命中加权
- aliases 精确命中加权
- 最近更新加权
- canonical 页优先于别名页
- concept 页优先于零散 QA 页

### 好处

能明显减少“找到了相关页，但排在后面没读到”的问题。

---

## 15. 更完整的 Lint 指标体系

### 为什么值得做

断链和孤儿页只是最基础的 Lint。一个更成熟的知识库，还应该监控页面质量本身。

### 推荐补充的检查项

- summary 过泛预警
- 页面过长预警
- 页面链接过少预警
- 页面引用来源缺失预警
- 重复页面高相似度预警
- 别名冲突预警
- 高频震荡页面预警

### 实际价值

这些指标会帮助你更早发现知识库“正在变脏”的信号。

---

## 16. QA 回写策略细化

### 为什么值得做

不是所有精彩回答都适合直接存成正式概念页。有些更适合作为临时 QA 资产。

### 推荐做法

把回写类型拆成三类：

- `qa-note`：一次高质量问答的沉淀
- `overview`：多页整合后的专题综述
- `concept-update`：对现有概念页的补充

### 建议先别做的事

不要让系统把所有高质量回答都直接回写成正式概念页，否则很快会造成页面泛滥。

---

## 17. 页面模板再细化

### 为什么值得做

有了模板，AI 输出会更稳定，也更便于后续维护。

### 推荐为不同页面类型定义不同模板

#### 概念页模板

- 定义
- 为什么重要
- 工作原理
- 适用场景
- 局限性
- 相关概念
- 来源

#### 实体页模板

- 是谁/是什么
- 核心信息
- 相关项目/概念
- 在本知识库中的定位
- 来源

#### 来源摘要页模板

- 原文概览
- 核心观点
- 提取到的概念
- 提取到的实体
- 与现有页面的联系/冲突
- 后续建议

---

## 18. 双语和术语统一策略

### 为什么值得做

LLM-Wiki 相关资料天然会中英混杂。如果不做统一，检索和命名会越来越乱。

### 需要尽早定的规则

- 页名主语言是什么
- 英文原词是否保留在 aliases
- 摘要中是中文优先还是中英并列
- 搜索时是否自动做中英扩展

### 推荐务实策略

可以先采用：

- 页面标题以中文为主
- 英文术语放 aliases
- 首段首次出现时中英并列

例如：

```md
BM25（Best Matching 25）是一种经典的关键词相关性排序算法。
```

## 五、第三层：规模扩大后再做

## 19. 评测集与回归评估机制

### 为什么规模一大就必须有

当你开始频繁改 chunk 规则、改检索策略、改 `CLAUDE.md` 提示词时，如果没有评测集，你根本不知道系统是变好了还是变差了。

### 建议至少准备一套固定问题集

覆盖：

- 概念查询
- 多页综合
- 来源回溯
- 冲突识别
- 长文定位
- 别名检索

### 每次变更后要观察的指标

- Top N 命中是否更稳定
- 回答是否更短或更空泛
- 引用是否更准确
- 是否更容易漏掉关键页

---

## 20. 混合检索架构

### 为什么放在第三层

对个人早期知识库来说，BM25 + 索引导航通常就够了。只有在规模明显变大后，才需要引入向量召回。

### 正确引入方式

不是对所有 raw 直接做向量，而是优先对：

- 高质量 Wiki 页面
- 规范化后的 chunk
- 已做基础清洗的来源摘要

进行 embedding。

### 核心原则

Wiki 仍然是核心知识资产，向量检索只是扩大召回范围的辅助手段。

---

## 21. 模型角色分工

### 为什么规模变大后值得做

不是每一步都需要最强模型。随着规模增长，可以把不同任务拆给不同能力层级的模型。

### 一个常见分工思路

- 小模型：清洗、分块、摘要、初步分类
- 中等模型：概念抽取、实体归类、页面草稿
- 强模型：综述页、冲突分析、结构重组、复杂问答

### 好处

- 降低成本
- 提高吞吐
- 让重任务只在必要时调用强模型

---

## 22. 权限与隐私分层

### 为什么后期一定会遇到

如果后面资料不再只是公开技术内容，而是加入内部文档、会议记录、个人笔记，那就会出现访问边界问题。

### 至少要考虑的分层方式

- public wiki
- private wiki
- sensitive raw
- export-safe outputs

### 要尽早避免的坑

不要让默认日志、默认输出、默认回写把敏感内容带到不该出现的地方。

---

## 六、建议立刻落地的一组最小动作

如果你现在就准备开始推进，我建议你下一步优先做下面这些动作。

## 第一批动作

1. 为 `raw/` 文档定义 `source_id` 规则。  
2. 定义 ingest 状态机。  
3. 定义 canonical title + aliases 方案。  
4. 明确页面“新建 / 追加 / 合并 / 冲突标记”四种策略。  
5. 明确 chunk 切分规则和最小 chunk 元数据。  
6. 明确 query 预处理规则。  
7. 明确上下文预算和 Top N 读取规则。  
8. 明确哪些动作必须人工审批。  
9. 明确最小 Git 提交规范。  
10. 增加错误日志和失败恢复记录。

## 第二批动作

1. 增加缓存层。  
2. 给不同页面类型定义模板。  
3. 补全 Lint 指标。  
4. 做双语术语统一。  
5. 细化 QA 回写策略。

## 第三批动作

1. 准备固定评测集。  
2. 视规模决定是否引入向量召回。  
3. 拆分不同模型角色。  
4. 设计权限与隐私边界。

## 七、你最值得优先补齐的五个空白

如果只从投入产出比来看，我最建议你优先补下面五块，因为它们最容易决定系统后面是“越来越稳”还是“越来越乱”。

### 1. source_id + ingest 状态机

没有这层，系统连“可重复运行”都做不到。

### 2. canonical name + aliases

没有这层，知识图谱很快会长成一团重复节点。

### 3. chunk 规则 + 上下文预算

没有这层，长文场景和复杂问答会非常不稳定。

### 4. 更新策略 + 人工审批边界

没有这层，AI 很容易把旧知识改坏。

### 5. Lint + 失败恢复 + Git 回滚

没有这层，系统一旦出错，很难低成本修复。

## 八、最后的结论

如果说前一份《LLM-Wiki知识库搭建学习总结》回答的是“系统应该长什么样、主流程怎么走”，那么这份补充清单回答的就是“怎样让它在真实环境里长期跑得住”。

真正的工程落地，不只是会生成 Markdown、会加双向链接、会做 BM25 搜索，而是要补齐这些底层约束：

- 可重复
- 可恢复
- 可追踪
- 可回滚
- 可审计
- 可扩展

当你把这几层补上之后，这套系统才真正从“一个不错的知识整理想法”，进化成“一个可以持续积累和维护的知识基础设施”。
