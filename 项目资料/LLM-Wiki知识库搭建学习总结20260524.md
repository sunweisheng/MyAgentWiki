# LLM-Wiki知识库搭建学习总结

> 整理时间：2026-05-24  
> 整理目标：将一份关于 LLM-Wiki 的长篇讨论内容去重、归类、提炼，形成一份可直接用于后续搭建知识库系统的学习总结。  
> 适用对象：想基于本地 Markdown、Git、AI Agent 搭建个人或小团队 LLM-Wiki 知识库的人。

---

## 一、这套系统到底在解决什么问题

LLM-Wiki 的核心思路，不是“每次提问时临时去一堆原始资料里检索并拼答案”，而是先让 AI 把原始资料持续整理、编译成结构化的 Wiki 页面，再基于这些已经整理好的知识页面进行后续查询、补充和维护。

可以把它理解成：

- 传统 RAG 更像“现问现找，边找边答”
- LLM-Wiki 更像“先把资料整理成百科，再基于百科回答问题”

这种方式的关键价值在于：

1. 知识会沉淀，而不是每次从零开始。
2. 原始资料和整理后的知识分层明确，更容易溯源。
3. AI 更容易在结构化知识上做推理、建链接、做总结。
4. 对个人规模知识库来说，可以不依赖复杂向量数据库，系统更轻、更透明、更容易本地化。

---

## 二、LLM-Wiki 的核心理念

### 1. Compile, don’t retrieve

这套理念强调“编译知识”而不是“临时检索原文”。

所谓“编译”，就是把原始文档放入 `raw/`，再由 AI 抽取其中的概念、实体、结论、关系、差异和引用，生成可以长期复用的 Markdown 页面，存入 `wiki/`。

### 2. Raw 与 Wiki 分离

这是整个系统最重要的结构原则之一。

- `raw/` 存原始资料，只读、不改，负责保留事实来源。
- `wiki/` 存 AI 整理后的知识页面，负责承载概念、实体、摘要、综述与交叉链接。

这样做的好处是：

- 原文永远保留，方便回溯。
- Wiki 页面允许持续演化。
- 可以把“事实来源”和“认知整理”分开管理。

### 3. 知识要形成网络，而不是文件堆

LLM-Wiki 的灵魂不是“存了很多 Markdown 文件”，而是这些文件之间形成了大量交叉引用和结构化关系。这样知识库才是“活的”。

## 三、推荐的目录结构

下面是一种适合个人实践、也便于后续扩展的目录方案：

```text
your-llm-wiki/
├── raw/                      # 原始资料，只读区
│   ├── papers/
│   ├── articles/
│   ├── notes/
│   └── assets/
├── wiki/                     # AI 编译后的知识层
│   ├── 00_索引与地图/
│   │   ├── index.md
│   │   └── map.md
│   ├── 10_核心概念/
│   │   ├── 算法/
│   │   └── 架构/
│   ├── 20_人物与实体/
│   ├── 30_综述与对比/
│   ├── 40_来源摘要/
│   ├── 50_QA沉淀/
│   └── log.md
├── scripts/                  # Python/CLI脚本
│   ├── ingest.py
│   ├── search.py
│   ├── lint.py
│   └── utils.py
├── .claude/
│   ├── commands/
│   └── skills/
├── outputs/                  # 导出结果、报告、临时产物
├── requirements.txt
└── CLAUDE.md                 # 给 AI 的规则手册
```

### 为什么目录前建议加编号

像 `00_`、`10_`、`20_` 这样的编号，主要是为了排序稳定。

好处有两个：

- 文件夹顺序更符合人的认知顺序，而不是按拼音或字母乱排。
- 用 10、20、30 留空档，后面想插入 `15_` 之类的新分类时，不用整体重命名。

## 四、概念页、实体页、摘要页为什么要分开

很多讨论里反复出现一个问题：概念、实体这些不是页面里的属性吗，为什么还要做成目录？

答案是：它们既可以是元数据字段，也可以是独立页面类型，两者不是冲突关系，而是两个层面的组织方式。

### 1. 概念页（Concepts）

适合存放：

- 算法
- 方法论
- 架构模式
- 通用技术概念

例如：

- `BM25`
- `RAG`
- `MCP`
- `双向链接`
- `Chunking`

概念页重点回答的是：

- 这是什么
- 为什么重要
- 怎么工作
- 适用边界是什么
- 和其他概念有什么关系

### 2. 实体页（Entities）

适合存放：

- 人物
- 公司
- 产品
- 工具
- 项目
- 协议

例如：

- `Andrej Karpathy`
- `Claude`
- `Obsidian`
- `Hermes`
- `Elasticsearch`

实体页重点回答的是：

- 它是谁/是什么
- 它做过什么
- 它和哪些概念或项目相关
- 它在知识库中的定位是什么

### 3. 来源摘要页（Sources）

适合存放：

- 对某一篇原始文档的摘要
- 文档的核心观点
- 与现有知识库的联系和冲突
- 值得提炼成哪些概念或实体

来源摘要页相当于“原始文档进入知识库后的第一层编译产物”。

### 4. 综述与对比页

适合存放：

- 多篇资料对某个问题的综合结论
- 相同主题下不同方案的对比
- 最佳实践总结
- 某个领域的路线图、框架图

这类页面通常不是单篇原文的直接摘要，而是经过多源整合后的“高价值沉淀”。

## 五、元数据怎么设计，为什么它非常关键

元数据最好写在 Markdown 文件头部的 YAML Frontmatter 中。它的作用不是为了好看，而是为了让 AI 和检索工具能先看“结构化摘要”，再决定是否深入正文。

推荐字段示例：

```yaml
---
title: BM25 算法详解
type: concept
summary: 基于词频、逆文档频率和长度归一化的经典关键词相关性打分算法。
concepts: [信息检索, 搜索算法]
entities: [BM25, TF-IDF, Elasticsearch]
tags: [llm-wiki, retrieval, search]
source_files: [raw/articles/bm25-intro.md]
created: 2026-05-24
updated: 2026-05-24
status: stable
---
```

### 常见字段解释

`title`：页面标题。  
`type`：页面类型，比如 `concept`、`entity`、`source-summary`、`overview`。  
`summary`：一句话总结。这个字段非常重要，既利于人浏览，也利于 AI 快速判断相关性。  
`concepts`：该页所属的上层概念分类。  
`entities`：该页涉及的重要专有名词、人物、工具或项目。  
`tags`：补充标签。  
`source_files`：指向原始来源。  
`created` / `updated`：便于后续巡检与维护。  
`status`：可选，用于标识 `draft`、`stable`、`disputed`、`outdated` 等状态。

### 为什么元数据重要

因为 AI 不可能每次都先读全文再判断是否相关。元数据相当于页面的“快速预览卡片”。

它的价值包括：

- 提高检索速度
- 降低上下文消耗
- 稳定页面格式
- 方便后续脚本做 lint 和统计
- 为自动加链接、自动分类提供基础信号

## 六、双向链接到底是什么，应该加在哪

双向链接的基本写法就是：

```md
[[BM25]]
[[MCP]]
[[Chunking]]
```

### 具体加在哪里

主要加在正文中提到已有知识点的地方。

例如在 `RAG架构.md` 中写：

```md
在检索层中，可以先使用 [[BM25]] 做关键词召回，再结合其他策略完成重排。
```

如果 `wiki/` 里已经有 `BM25.md` 页面，那么这就是一个有效的 WikiLink。

### 它起到什么作用

双向链接的作用不是“像网页超链接那样能点一下跳过去”这么简单，它的真正价值是：

1. 把树状目录变成网状知识结构。
2. 让 AI 可以顺藤摸瓜读取关联页面。
3. 让知识之间产生复利。
4. 让人类浏览时更容易发现隐性关联。

### 文件可以不在同一层目录吗

完全不需要。

现代笔记工具和知识库工作流通常都支持在整个仓库里解析 `[[文件名]]`，即使目标文件在很深的子目录里，也能找到。为了避免重名，也可以写成带路径的形式：

```md
[[10_核心概念/算法/BM25]]
```

### 双向链接是手动加还是 AI 自动加

两种都可以，但推荐把“自动扫描正文并对已有页面加 `[[ ]]` 链接”写入摄入规则，让 AI 在生成或更新页面时自动完成。

## 七、搜索时到底怎么运作

LLM-Wiki 的查询流程，与“把所有原文都丢给模型临时回答”的思路不同。

更合理的查询流程是：

1. 先查索引页 `index.md` 或知识地图页
2. 再定位最相关的 Wiki 页面
3. 如有需要，再顺着双向链接扩展读取相关页面
4. 将这些结构化页面内容装入上下文
5. 最后由 LLM 生成回答

### 这是不是“语义搜索”

严格来说，不完全是。

“把找到的页面加载进上下文，由 LLM 生成答案”是一个完整问答流程中的“生成阶段”。

而“搜索”这一段，在原生 LLM-Wiki 里更偏向：

- 索引导航
- 关键词匹配
- 交叉引用扩展

如果底层用了 BM25，那它本质上是经典关键词检索，而不是向量语义检索。

---

## 八、BM25 在这里是什么角色

BM25 不是 Agent，也不是 LLM。它只是一个经典的文本相关性打分算法。

在系统中的职责是：

- 根据 query 和文档词项的匹配情况打分
- 按分数排序候选页面
- 选出最相关的 Top N 页面交给后续步骤

### BM25 为什么适合这类系统

原因主要有这些：

1. 对专有名词、报错码、工具名、概念名等精确词非常友好。
2. 不需要向量库，不需要 embedding 预处理，工程更轻。
3. 本地运行快，成本低。
4. 对几百到几千篇规模的个人知识库很实用。

### BM25 的核心思想

BM25 的打分受三个因素影响：

- 词频：查询词在当前文档里出现多少次
- 稀有度：这个词在整个文档集合里是否稀有
- 长度归一化：避免长文天然占优势

它可以防止简单的“关键词堆砌作弊”，也能让短而精确的页面排得更靠前。

## 九、分词是谁做的？是不是 LLM 做的

不是。

在这套系统里，分词和 BM25 一样，都属于传统信息检索链路的一部分，通常由 Python 脚本和相关库完成，不需要 LLM 参与。

### 中文分词的常见做法

通常会使用类似 `jieba` 这样的中文分词工具。

示例：

```python
import jieba

query = "如何搭建 LLM Wiki 知识库"
terms = jieba.lcut(query)
print(terms)
```

可能得到：

```python
['如何', '搭建', 'LLM', 'Wiki', '知识库']
```

这些切分后的词，再交给 BM25 去计算匹配度。

### 还可以做什么增强

1. 加载自定义词典，让分词器认识领域词汇，例如 `大语言模型`、`Claude Code`、`向量数据库`。  
2. 去停用词，降低无意义高频词的影响。  
3. 在摄入阶段提前抽取关键词，辅助构建倒排索引。

## 十、实体抽取、概念抽取是谁做的

这部分通常更适合由 LLM 在摄入阶段完成，而不是由 BM25 完成。

需要明确区分：

- 分词：把句子拆成词
- BM25：拿词去做相关性打分
- 实体抽取/概念抽取：从内容中识别“这篇文档讲了哪些关键对象和关键主题”

### 为什么这一步更适合 LLM

因为“概念”和“实体”很多时候不是简单的字面切词，而是要靠理解。

例如：

- `Andrej Karpathy` 是人物实体
- `BM25` 是算法实体
- `LLM-Wiki` 是系统/项目实体
- `交叉引用` 是概念
- `Chunking` 是技术策略

这些分类带有一定语义判断，用 LLM 来做更自然。

## 十一、原生 LLM-Wiki 是否一定要用向量检索

不一定，甚至可以说，原生理念里并不强调向量检索。

### 为什么

LLM-Wiki 的一个重要哲学是：

- 先把知识编译成高质量 Wiki 页面
- 再围绕这些页面做查询和维护

它不是那种“每次问题来了，就从海量原始文档里做 embedding 检索再拼答案”的典型 RAG 路线。

### 什么时候才考虑向量检索

当知识库规模变得很大，或者文档很长，单靠索引页和 BM25 已经不够高效时，可以考虑引入“混合架构”：

- 仍然保留 Wiki 作为核心知识资产
- 只对高质量 Wiki 页面或文档 chunk 做 embedding
- 向量检索只作为大规模召回的辅助手段

也就是说，即使用向量检索，也更适合对“已经整理好的知识层”做，而不是对所有原始脏数据直接做。

## 十二、超长文档怎么处理：分段加载与 Chunking

这是讨论中非常重要、也很容易遗漏的工程细节。

如果原始文档特别长，一次性塞进上下文会出现几个问题：

- token 超限
- 模型遗忘前面内容
- 成本变高
- 生成结果不稳定

### 推荐策略：按块处理

#### 1. 预分块

先用脚本把长文档按标题、段落、章节或固定长度切成多个 chunk。

切分原则建议：

- 尽量按语义边界切，而不是死按字数截断
- 每个 chunk 自身尽量完整
- chunk 之间可少量重叠，避免上下文断裂

#### 2. 先粗筛，再细读

先基于标题、摘要、关键词、BM25 或其他方法找出最相关的 chunk，再把这些 chunk 加入上下文，而不是整篇全读。

#### 3. 增量汇总

如果一篇文档涉及多个概念，可以分批读取多个 chunk，然后逐步归纳，最后汇总成页面。

### 一个实用的摄入思路

- 第一步：切分全文
- 第二步：为每个 chunk 生成一句摘要
- 第三步：判断每个 chunk 涉及的概念/实体
- 第四步：按概念聚合不同 chunk 的内容
- 第五步：输出最终 Wiki 页面

这个思路特别适合论文、长篇教程、访谈实录、会议整理等材料。

## 十三、AI 摄入新文档时的完整工作流

这是整个系统最关键的自动化流程之一。

### 推荐的 Ingest 工作流

#### 第一步：发现新文件

扫描 `raw/` 中尚未处理的新资料。

#### 第二步：读取原文

根据文件类型读取内容，必要时先转文本。

#### 第三步：分析

这里最好不要让 AI 一步到位直接写页面，而是采用“两步思维链”。

先分析，再生成。

分析阶段重点提取：

- 核心主题
- 核心概念
- 关键实体
- 与现有知识库的关联
- 是否存在冲突、补充或更新
- 是否值得拆分成多个页面

#### 第四步：生成页面

按模板生成或更新：

- 来源摘要页
- 概念页
- 实体页
- 必要时生成综述页

#### 第五步：自动建链

正文中提到已有知识点时，加上 `[[ ]]` 双向链接。

#### 第六步：更新索引

将新增页面写入 `index.md` 或地图页。

#### 第七步：记录日志

在 `log.md` 中记录本次摄入处理了哪些文件、生成了哪些页面、发现了哪些冲突。

## 十四、查询工作流应该怎么设计

查询工作流的目标，不只是“答出一个答案”，而是“尽量利用已经沉淀好的知识层”。

### 推荐 Query 流程

1. 读取索引页，定位主题范围。
2. 根据 query 做关键词检索或页面定位。
3. 读取最相关的 3～5 个 Wiki 页面。
4. 如信息不够，顺着双向链接继续扩展相关页面。
5. 组合这些内容形成回答。
6. 如果这次回答很有价值，可考虑沉淀成新页面或 QA 页。

### 高质量问答如何回写知识库

讨论中提到一个很重要的实践：

如果某次问答特别精彩、特别系统，或者形成了新的最佳实践总结，可以将其沉淀回知识库。

但更推荐“先提议、后确认”的机制，而不是 AI 直接自动写入。

例如在 `CLAUDE.md` 中规定：

> 如果你认为某次回答具有长期保存价值，请先询问用户是否需要整理入 Wiki；只有用户确认后，再执行写入。

这样可以避免 AI 过度积极、生成一堆用户不想保留的页面。

## 十五、健康检查（Lint）为什么必要

如果没有巡检机制，知识库会逐渐“腐烂”。

常见问题包括：

- 死链
- 孤儿页面
- YAML 缺失
- 重复页面
- 页面内容互相冲突
- 内容长期过时
- 同义概念没有合并

### 推荐的 Lint 检查项

1. 断链检测：页面中的 `[[链接]]` 是否都能找到目标页。  
2. 孤儿页检测：哪些页面没有任何入链。  
3. 元数据完整性检查：是否缺少 `title`、`summary`、`type`、`updated` 等字段。  
4. 内容过时检查：多久没更新了。  
5. 重复概念检查：例如 `LLM` 与 `大语言模型` 是否重复建页。  
6. 冲突检查：同一概念是否在不同页面中说法矛盾。  
7. 索引完整性检查：重要页面是否已经进入总索引。

## 十六、适合写进 Claude 命令或脚本的命令示例

下面这些示例很适合整理进自定义命令、脚本或工具说明中。

### 1. 摄入命令示例

```md
---
description: 扫描 raw 目录，将新文档摄入并转化为 Wiki 页面
argument-hint: [可选：指定文件名]
---

请执行 LLM-Wiki 的摄入工作流：

1. 扫描 raw/ 目录中的未处理文件；如果指定了参数，则仅处理对应文件。
2. 先分析文档，提取核心概念、关键实体与一句话摘要。
3. 根据分析结果，在 wiki/ 中创建或更新对应页面。
4. 页面必须包含标准 YAML Frontmatter。
5. 正文提到已有知识点时，自动补充 [[WikiLink]]。
6. 更新 wiki/index.md。
7. 严禁修改 raw/ 目录中的原始文件。
```

### 2. 搜索命令示例

```md
---
description: 使用 BM25 在本地知识库中搜索相关内容
argument-hint: <搜索关键词>
---

请使用本地知识库搜索工具，检索与 "$ARGUMENTS" 相关的 Wiki 页面。
优先使用 BM25 或等价关键词检索方式返回最相关页面。
读取结果后，基于这些页面回答问题，并注明参考了哪些页面。
```

### 3. 健康检查命令示例

```md
---
description: 对知识库进行健康度体检
argument-hint: [可选：fix]
---

请对 wiki/ 目录执行一次全面健康检查：

1. 检测断链
2. 检测孤儿页面
3. 检查 YAML 元数据缺失
4. 检查长期未更新页面
5. 输出 Markdown 体检报告

如果参数为 fix，则在安全前提下：
- 补齐缺失的默认元数据
- 将明显孤儿页面加入索引
- 尝试修复拼写错误造成的简单断链
```

“我觉得刚才关于【主题】的总结很值得沉淀，需要我帮你整理成 Wiki 页面吗？”

## 十七、Skill、Command、MCP 分别适合干什么

讨论中这一部分反复出现，值得单独总结。

### 1. Command

适合：

- 手动触发固定流程
- 通过 `/ingest`、`/search`、`/lint` 之类命令一键执行

特点：

- 简单直接
- 适合把常用提示词模板化
- 更像“快捷命令”

### 2. Skill

适合：

- 把一整套工作流说明和脚本调用规则封装起来
- 让 AI 学会“在什么场景下如何做事”

特点：

- 本质上是“说明书 + 配套脚本”
- 比单条命令更适合沉淀复杂工作方式
- 比 MCP 上手门槛低

### 3. MCP

适合：

- 把本地功能正式封装成可调用工具
- 参数、输入输出更结构化
- 适合复杂且需要频繁调用的能力

特点：

- 更标准化
- 更适合做正式工具集成
- 比 Skill 复杂一些

### 实操建议

如果只是个人搭建 LLM-Wiki，建议优先顺序是：

1. 先用 `CLAUDE.md` 明确规则  
2. 再用 `Command` 封装常用流程  
3. 后续需要时再沉淀成 `Skill`  
4. 当功能稳定且复杂时，再考虑 MCP 封装

## 十八、Python 脚本一般放在哪

推荐直接放在知识库根目录下的 `scripts/` 或 `engine/` 中。

例如：

```text
your-llm-wiki/
├── raw/
├── wiki/
├── scripts/
│   ├── ingest.py
│   ├── search.py
│   ├── lint.py
│   └── chunk.py
├── requirements.txt
└── CLAUDE.md
```

这样做的优点：

- 路径清晰
- 便于 Git 管理
- 相对路径更简单
- 后续让 AI 修改脚本也更方便

## 十九、Agent 为什么会“知道用 BM25”

这一点在讨论里多次被问到，结论很明确：

AI 并不会凭空知道必须用 BM25。

如果原始理念文档里没有明确提到，而你又没有在规则或代码层明确指定，那么 AI 只会知道“要搜索”，但未必知道“具体该怎么搜”。

所以需要你在两个层面明确约束：

### 1. 规则层

在 `CLAUDE.md` 中写清楚：

- 本地 Wiki 搜索优先使用 BM25 或等价关键词检索
- 不要默认引入向量数据库
- 长文优先按 chunk 检索

### 2. 工具层

在脚本里把搜索能力封装好，例如 `search.py` 或 `wiki search` 命令内部就是 BM25 实现。

这样 AI 不需要自己“发明方案”，只需要调用你给好的工具。

## 二十、推荐写进 CLAUDE.md 的关键规则

以下规则最值得写进去：

### 1. Raw 只读原则

- 永远不要修改或删除 `raw/` 目录中的任何原始文件。

### 2. 两步摄入原则

- 处理新文档时，先分析，再生成。
- 不允许一步到位直接大段自由生成。

### 3. 页面结构统一原则

- 所有 Wiki 页面必须包含统一 YAML Frontmatter。
- `summary` 保持简洁。
- `type`、`title`、`updated` 必填。

### 4. 自动建链原则

- 正文出现已有知识点时，自动补 `[[ ]]` 双向链接。

### 5. 长文分段原则

- 超长文档必须先分 chunk，再按需加载，禁止整篇无脑塞上下文。

### 6. 高价值问答沉淀原则

- 先询问用户是否保存，再执行写入。

### 7. 巡检原则

- 定期检查断链、孤儿页、重复概念与过时内容。

### 8. 冲突保留原则

- 发现冲突信息时，不要直接粗暴覆盖；应标注争议或记录差异来源。

## 二十一、一个更成熟的系统落地路线

如果要真正把这套系统搭起来，比较稳妥的路线是：

### 阶段一：先搭最小可用版

先具备这几样：

- `raw/`
- `wiki/`
- `index.md`
- `CLAUDE.md`
- 手动触发的摄入命令

### 阶段二：加入基础脚本能力

增加：

- 中文分词
- BM25 搜索
- 长文切块
- Lint 检查

### 阶段三：加入自动化沉淀

增加：

- 自动更新索引
- 自动建双向链接
- 自动生成来源摘要页
- 高价值问答提议归档

### 阶段四：规模扩展时做混合检索

仅当知识库体量明显变大时，再考虑：

- 对 Wiki 页面或 chunk 做 embedding
- 增加向量召回
- 做 BM25 + 向量混合检索

但核心仍然是：Wiki 知识层优先，而不是把一切退回“原始资料直搜”。

## 二十二、关键经验与避坑总结

### 1. 不要一开始就做得太重

对个人知识库来说，最先需要的不是复杂基础设施，而是稳定的结构和可持续的工作流。

### 2. 不要把所有事都交给模型自由发挥

一定要用规则、模板、字段、命令和脚本约束它。

### 3. 不要混淆“原始资料”和“知识产物”

原文负责保真，Wiki 负责理解与重组。

### 4. 不要忽略长文处理

不做 chunk，系统很快就会在长文场景里失控。

### 5. 不要忽略 Lint

知识库不是建完就结束，而是要持续体检。

### 6. 不要把双向链接当成装饰

它决定了知识库最终能不能从“文件堆”变成“知识网络”。

### 7. 不要默认 AI 自己会知道技术选型

像 BM25、Chunking、YAML 规范、回写策略这些，最好都显式写进规则和工具中。

## 二十三、适合直接采纳的一套最小规则模板

下面是一段适合改写进你自己 `CLAUDE.md` 的精简规则骨架：

```md
# LLM-Wiki 工作规则

## 基本原则
- raw/ 目录只读，禁止修改或删除任何原始文件。
- wiki/ 目录存放 AI 编译后的知识页面。
- 所有新增知识都必须尽量链接到已有页面，避免孤岛化。

## Ingest 规则
- 处理新文档时，先分析再生成。
- 先提取核心概念、关键实体、一句话摘要和与现有知识的关系。
- 再根据分析结果创建或更新 Wiki 页面。
- 所有页面必须包含统一 YAML Frontmatter。
- 正文中出现已有知识点时，自动补充 [[WikiLink]]。
- 处理完成后更新 index.md 和 log.md。

## Search 规则
- 搜索本地 Wiki 时优先使用 BM25 或等价关键词检索。
- 查询时先读索引页，再读相关页面，必要时顺着双向链接扩展。
- 不要默认依赖向量数据库。
- 超长页面或原文应先按 chunk 检索，再按需加载。

## Lint 规则
- 定期检查断链、孤儿页、重复概念、元数据缺失和过时内容。
- 发现冲突信息时，不要直接删除，应标记 disputed 或说明来源差异。

## 沉淀规则
- 如果一次回答形成了高价值总结，请先询问用户是否需要存入 Wiki。
- 只有在用户确认后，才执行写入。
```

## 二十四、最后的结论

如果只用一句话概括这次关于 LLM-Wiki 的学习收获，那就是：

LLM-Wiki 不是一个单纯的“AI 搜索系统”，而是一套“让 AI 长期维护结构化知识资产”的方法论与工程实践。

它的关键不在于模型有多强，而在于：

- 有没有把原始资料与知识层分开
- 有没有稳定的页面结构和元数据
- 有没有交叉引用网络
- 有没有摄入、检索、巡检这三套闭环
- 有没有把 BM25、Chunking、规则约束、回写机制这些工程细节落实下来

把这些基础搭好之后，这个系统才有可能从“一个会读 Markdown 的 AI 助手”，真正变成“一个能长期陪你积累知识、维护知识、扩展知识的知识库系统”。
