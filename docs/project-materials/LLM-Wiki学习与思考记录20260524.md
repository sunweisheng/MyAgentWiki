## 问题 1：详细讲讲 Chunking

### 1. Chunking 是什么

Chunking，中文可以叫“切块”“分块”或“文档切片”，指的是把一篇较长的原始文档，按照一定规则拆成多个相对独立、可检索、可引用、可处理的小片段。

在 LLM-Wiki 系统里，Chunking 不是为了把文档切碎存起来，而是为了让长文档能被稳定地摄入、检索、总结、引用和更新。

可以把它理解成一个中间层：

```text
raw 原始文档 -> normalized 规范化文本 -> chunks 文档块 -> summaries / concepts / wiki pages
```

也就是说，chunk 不是最终知识成品。最终知识成品是 `wiki/` 里的概念页、实体页、来源摘要页、综述页。chunk 更像是从原文到 Wiki 页面之间的“证据单元”和“处理单元”。

### 2. 为什么 LLM-Wiki 必须重视 Chunking

如果原始文档很短，直接让 LLM 读全文通常没问题。但一旦进入长文档、论文、访谈、教程、会议记录、网页合集，直接整篇塞给模型会出现几个问题：

- 上下文窗口可能放不下。
- 即使放得下，模型也容易遗漏前文或中间细节。
- 成本变高，每次处理都要重复读大量无关内容。
- 检索不稳定，用户问一个小问题时系统却要处理整篇文档。
- 溯源粒度太粗，只能说“来自某篇文档”，很难说“来自哪一段”。
- 后续更新困难，一篇原文改动后无法判断具体影响了哪些知识点。

所以 Chunking 的核心价值不是“省 token”这么简单，而是让知识库拥有更细的工程颗粒度。

### 3. Chunk 在系统里的角色

在 LLM-Wiki 中，一个 chunk 至少承担五个角色：

1. 检索单元  
   用户提问时，可以先找相关 chunk，而不是整篇原文。

2. 摘要单元  
   每个 chunk 可以生成一句话摘要，便于后续粗筛。

3. 概念抽取单元  
   可以判断每个 chunk 涉及哪些概念、实体、方法、结论。

4. 溯源单元  
   Wiki 页面里的某个结论可以指向具体 chunk，而不是只指向整篇文件。

5. 增量更新单元  
   原文变化时，可以只重算受影响的 chunk，而不是整篇文档全部重做。

### 4. 好的 Chunking 不是机械按字数切

最差的切法是每 1000 字硬切一刀。这样很容易把一个完整论证切断，把表格切断，把代码块切断，或者把一个概念的定义和解释分到两个 chunk 里。

好的 Chunking 应该优先尊重语义边界：

- Markdown 标题
- 章节
- 小节
- 自然段
- 列表
- 表格
- 代码块
- 引用块
- PDF 页码或段落结构

只有当某个章节仍然太长时，才继续按段落或长度二次拆分。

### 5. 推荐的初版切块规则

对个人 LLM-Wiki 来说，不建议一开始就设计太复杂。可以先采用下面这套规则：

```yaml
chunking:
  strategy: heading_first
  target_tokens: 800-1200
  max_tokens: 1600
  min_tokens: 200
  overlap_tokens: 100-200
  split_order:
    - markdown_heading
    - paragraph
    - sentence
  preserve_blocks:
    - code_block
    - table
    - blockquote
```

解释如下：

- 优先按 Markdown 标题切。
- 一个 chunk 目标大小控制在 800 到 1200 tokens 左右。
- 超过 1600 tokens 的块继续拆。
- 小于 200 tokens 的块尽量和相邻块合并。
- 相邻 chunk 保留 100 到 200 tokens 的 overlap，避免上下文断裂。
- 代码块、表格、引用块尽量整体保留，不从中间切开。

这个范围不是绝对标准，而是适合个人知识库的一个稳妥起点。

### 6. 为什么需要 Overlap

Overlap 指的是相邻 chunk 之间保留一小段重叠内容。

例如：

```text
chunk_001: A B C D E
chunk_002: D E F G H
```

这里 `D E` 就是 overlap。

它的作用是解决“边界信息丢失”。很多文档的关键解释刚好横跨两个段落或两个小节，如果完全无重叠地切开，模型读单个 chunk 时可能看不到必要上下文。

但 overlap 不能太大。太大会导致：

- 存储重复
- 检索结果重复
- 摘要重复
- 成本上升
- 同一观点被误以为出现了多次

所以 overlap 应该小而稳定，主要保留上一个 chunk 的末尾上下文或标题路径，不要大面积复制。

### 7. Chunk 元数据应该记录什么

每个 chunk 最好不只是纯文本，而是带元数据的对象。推荐字段如下：

```yaml
chunk_id: src_20260524_a13f9c_chunk_012
source_id: src_20260524_a13f9c
source_path: raw/articles/example.md
section_path:
  - LLM-Wiki 架构
  - Ingest 流程
section_title: Ingest 流程
chunk_index: 12
char_count: 1850
token_estimate: 920
start_line: 120
end_line: 168
page_range: null
previous_chunk: src_20260524_a13f9c_chunk_011
next_chunk: src_20260524_a13f9c_chunk_013
summary: 这一段解释了 Ingest 如何从原始文档生成来源摘要、概念页和索引更新。
concepts:
  - Ingest
  - 来源摘要
  - 知识编译
entities: []
hash: sha256:xxxx
```

这些字段会让后续系统能力变得清楚很多：

- `source_id` 用于追踪原始文档。
- `section_path` 保留标题层级，避免 chunk 脱离语境。
- `start_line` / `end_line` 或 `page_range` 用于回看原文。
- `previous_chunk` / `next_chunk` 用于必要时补读上下文。
- `summary` 用于快速筛选。
- `concepts` / `entities` 用于概念聚合。
- `hash` 用于判断 chunk 是否变化。

### 8. Chunking 和 Wiki 页面是什么关系

Chunk 不等于 Wiki 页面。

一个 chunk 是原文片段；一个 Wiki 页面是整理后的知识资产。

二者关系通常是多对多：

- 一篇原始文档会被切成多个 chunk。
- 多个 chunk 可以共同支撑一个概念页。
- 一个 chunk 也可能同时支撑多个页面。

例如，一篇关于 RAG 的文章可能被切成：

```text
chunk_001: RAG 的背景
chunk_002: 检索流程
chunk_003: BM25 与向量检索
chunk_004: 重排序
chunk_005: 评估指标
```

这些 chunk 最后可能更新：

- `wiki/10_核心概念/RAG.md`
- `wiki/10_核心概念/BM25.md`
- `wiki/10_核心概念/向量检索.md`
- `wiki/30_综述与对比/关键词检索与向量检索对比.md`
- `wiki/40_来源摘要/某篇RAG文章摘要.md`

所以 chunk 是“证据材料”，Wiki 页面是“编译结果”。

### 9. Ingest 阶段如何使用 Chunking

推荐的摄入流程如下：

```text
1. 读取 raw 原文
2. 清洗和规范化文本
3. 生成 source_id
4. 按规则切分 chunks
5. 为每个 chunk 生成元数据
6. 为每个 chunk 生成一句话摘要
7. 从每个 chunk 抽取概念、实体、结论、关系
8. 按概念和实体聚合 chunks
9. 生成或更新 Wiki 页面
10. 在页面中记录 source_refs 到 chunk 级别
11. 更新 index.md 和 log.md
```

这里最关键的是第 8 步：不是按 chunk 顺序机械生成页面，而是把不同 chunk 中属于同一知识点的内容聚合起来，再写入相应 Wiki 页面。

### 10. Query 阶段如何使用 Chunking

当用户提问时，不应该默认读所有原文。更好的方式是：

```text
1. 先读 index.md 和页面 summary
2. 找到候选 Wiki 页面
3. 如果需要证据，再检索相关 chunks
4. 对 Top chunks 做精读
5. 综合回答，并附来源引用
```

例如用户问：“BM25 在 LLM-Wiki 里有什么用？”

系统可以先找：

- `BM25.md`
- `检索策略.md`
- `LLM-Wiki知识库搭建学习总结` 相关 chunk
- `工程落地补充清单` 相关 chunk

然后只读取这些页面或 chunk，而不是读取所有资料。

### 11. 不同材料的切法应该不同

不同类型文档适合不同切法：

| 文档类型 | 推荐切法 |
|---|---|
| Markdown 笔记 | 优先按标题，其次按段落 |
| 网页文章 | 先清洗导航和广告，再按标题/段落 |
| PDF 论文 | 按章节、页码、段落，保留页码 |
| 访谈实录 | 按问答轮次或主题段落 |
| 会议记录 | 按议题、决议、行动项 |
| 代码文档 | 按模块、函数、代码块，避免切断代码 |
| 表格资料 | 尽量按完整表格或行组切 |

这说明 Chunking 规则最好可配置，而不是写死一种全局规则。

### 12. 常见错误

1. 只按固定长度切  
   会破坏语义结构。

2. chunk 太小  
   信息不完整，模型需要读很多块才能理解一个点。

3. chunk 太大  
   检索不精确，成本高，也更容易塞满上下文。

4. 没有 overlap  
   边界处的信息容易断。

5. overlap 太大  
   造成重复、污染统计和检索结果。

6. 不保留标题路径  
   chunk 脱离章节语境后，单独看会变得含糊。

7. 不记录 chunk_id  
   后续无法精确引用、审计、重算。

8. 把 chunk 当最终知识  
   chunk 只是中间材料，真正有价值的是被编译后的 Wiki 页面。

### 13. 对当前 LLM-Wiki 项目的建议

当前阶段可以采用一个朴素但稳定的方案：

1. 先只处理 Markdown 文档。
2. 每篇 raw 文档生成稳定 `source_id`。
3. 按 Markdown 标题优先切块。
4. 每个 chunk 保留标题路径、行号、摘要、概念、实体、hash。
5. 每个 chunk 的目标长度控制在 800 到 1200 tokens。
6. 对超过 1600 tokens 的块按段落继续切。
7. 对低于 200 tokens 的块合并到相邻块。
8. 相邻块保留 100 到 200 tokens 的 overlap。
9. Wiki 页面引用来源时至少记录到 `source_id + chunk_id`。
10. chunk 结果先缓存到本地 JSONL 或 SQLite，后续再考虑向量库。

一个 JSONL 示例：

```json
{"chunk_id":"src_20260524_a13f9c_chunk_001","source_id":"src_20260524_a13f9c","section_path":["十二、超长文档怎么处理：分段加载与 Chunking"],"start_line":422,"end_line":463,"token_estimate":760,"summary":"本段说明长文档需要先分块、再粗筛和增量汇总。","concepts":["Chunking","Ingest","长文档处理"],"previous_chunk":null,"next_chunk":"src_20260524_a13f9c_chunk_002","hash":"sha256:xxxx"}
```

### 14. 一句话总结

Chunking 是 LLM-Wiki 的“知识编译预处理层”：它把长文档拆成可检索、可摘要、可引用、可更新的证据单元，让 AI 后续生成 Wiki 页面时既不会丢上下文，也不会被长文档拖垮。

## 问题 2：详细讲讲规范名、别名、重定向机制

### 1. 这三个概念分别是什么

在 LLM-Wiki 知识库里，规范名、别名、重定向机制是一套“命名治理系统”。它解决的不是内容怎么写，而是“同一个知识点到底应该被叫成什么、链接到哪里、检索时怎么被找到”。

三个概念可以这样理解：

| 名称 | 英文 | 作用 |
|---|---|---|
| 规范名 | canonical name / canonical title | 一个概念或实体在知识库里的正式名称 |
| 别名 | alias / aliases | 用户、资料、AI 可能使用的其他叫法 |
| 重定向 | redirect | 当访问旧名称、简称、误写名称时，指向规范页面 |

例如：

```yaml
title: 大语言模型
canonical_id: concept_large_language_model
aliases:
  - LLM
  - Large Language Model
  - 大模型
  - 语言大模型
```

这里：

- `大语言模型` 是规范名。
- `LLM`、`Large Language Model`、`大模型` 是别名。
- 如果曾经存在 `LLM.md`，它可以变成一个重定向页，指向 `大语言模型.md`。

### 2. 为什么这件事在 LLM-Wiki 里非常重要

知识库早期最容易忽视命名问题，因为页面少，人工还能记住。但页面一多，就会出现“命名漂移”。

比如同一个概念可能被写成：

- LLM
- 大语言模型
- Large Language Model
- 大模型
- 语言模型

如果没有规范名和别名机制，后果会很快出现：

- AI 可能重复创建多个页面。
- 双向链接会分散到不同名字上。
- 检索时明明有相关内容却搜不到。
- 统计概念关系时会把同一概念当成多个节点。
- 综述页整合内容时容易漏掉旧页面。
- 后期重命名会非常痛苦。

所以规范名机制的核心价值是：让知识库里的“一个概念”始终对应“一个主节点”。

### 3. 规范名是什么

规范名就是某个概念或实体在知识库中的正式页面标题。

它应该满足几个条件：

1. 稳定  
   不要频繁变化，否则链接和引用都会震荡。

2. 清晰  
   人看到标题就知道页面讲什么。

3. 不歧义  
   避免一个名称对应多个含义。

4. 符合知识库语言策略  
   如果你的知识库主要用中文，就优先用中文规范名；英文术语放别名。

例如当前 LLM-Wiki 可以采用：

| 规范名 | 别名 |
|---|---|
| 大语言模型 | LLM, Large Language Model, 大模型 |
| 文档切块 | Chunking, 分块, 文档切片 |
| 关键词检索 | Keyword Search, Lexical Search |
| 向量检索 | Vector Search, Semantic Search |
| 模型上下文协议 | MCP, Model Context Protocol |

这里不一定追求“学术上唯一正确”，而是追求“在你的知识库里长期稳定”。

### 4. canonical_id 为什么比 title 更稳

规范名通常会被用作页面标题，但标题仍然可能变化。

例如你一开始叫：

```text
文档切块
```

后来觉得：

```text
Chunking
```

更适合做标题。

如果系统只靠标题识别页面，重命名就很麻烦。所以建议每个重要页面都加一个稳定的 `canonical_id`：

```yaml
title: 文档切块
canonical_id: concept_chunking
aliases:
  - Chunking
  - 分块
  - 文档切片
```

`title` 可以改，但 `canonical_id` 尽量不要改。

可以把 `canonical_id` 理解成数据库里的主键，而 `title` 是人类看的显示名。

### 5. 别名是什么

别名是同一个概念或实体的其他叫法。

别名来源通常包括：

- 英文原词
- 中文翻译
- 缩写
- 全称
- 常见简称
- 旧名称
- 不同资料里的不同译法
- 用户口语表达

例如：

```yaml
title: 文档切块
canonical_id: concept_chunking
aliases:
  - Chunking
  - chunking
  - 分块
  - 切块
  - 文档切片
  - 文本切块
  - 长文切块
```

别名不是为了让页面变复杂，而是为了让系统在搜索、链接、去重时知道：这些名字其实说的是同一个东西。

### 6. 别名应该怎么用

别名至少有四个用法。

第一，用于检索扩展。

用户问：

```text
长文切块怎么做？
```

系统应该能扩展成：

```text
长文切块 OR 文档切块 OR Chunking OR 分块
```

这样即使页面标题叫 `文档切块`，正文里写的是 `Chunking`，也能搜到。

第二，用于自动加链接。

当 AI 在正文中写到：

```md
长文档需要先做 Chunking。
```

系统应该优先链接到规范页：

```md
长文档需要先做 [[文档切块|Chunking]]。
```

而不是创建一个新的 `Chunking.md`。

第三，用于页面去重。

如果 Ingest 时发现新材料里频繁出现 `Large Language Model`，系统要先查 alias registry，发现它对应 `大语言模型`，再更新已有页面，而不是新建 `Large Language Model.md`。

第四，用于排序加权。

检索时如果 query 精确命中某页的 alias，这页应该加权靠前。

### 7. 重定向机制是什么

重定向机制是为了处理“已有旧页面、别名页面、错名页面、外部链接”。

比如你早期建过一个页面：

```text
wiki/10_核心概念/Chunking.md
```

后来决定规范名统一中文，改成：

```text
wiki/10_核心概念/文档切块.md
```

这时不建议直接删除 `Chunking.md`，因为：

- 旧链接可能还指向它。
- Obsidian 图谱里可能还有入站链接。
- AI 或脚本可能还记得旧路径。
- Git 历史里也可能引用旧文件名。

更稳妥的做法是把 `Chunking.md` 改成重定向页：

```md
---
title: Chunking
type: redirect
redirect_to: 文档切块
canonical_id: concept_chunking
aliases: []
status: redirected
---

# Chunking

请见 [[文档切块]]。
```

这样人和 AI 都能知道：这个页面不是独立知识页，它只是指向规范页。

### 8. 规范页、别名、重定向页的推荐 Frontmatter

规范页：

```yaml
---
title: 文档切块
type: concept
canonical_id: concept_chunking
aliases:
  - Chunking
  - 分块
  - 切块
  - 文档切片
  - 长文切块
status: stable
---
```

重定向页：

```yaml
---
title: Chunking
type: redirect
canonical_id: concept_chunking
redirect_to: 文档切块
status: redirected
---
```

实体页：

```yaml
---
title: Andrej Karpathy
type: entity
canonical_id: person_andrej_karpathy
aliases:
  - Andrej Karpathy
  - Karpathy
  - 卡帕西
status: stable
---
```

对个人知识库来说，最重要的是先把 `title`、`type`、`canonical_id`、`aliases`、`redirect_to` 这几个字段固定下来。

### 9. alias registry：建议单独维护一张别名表

除了在每个页面 frontmatter 里写 aliases，还建议维护一个全局别名注册表。

例如：

```text
wiki/00_索引与地图/aliases.yml
```

内容可以是：

```yaml
aliases:
  LLM: concept_large_language_model
  Large Language Model: concept_large_language_model
  大模型: concept_large_language_model
  Chunking: concept_chunking
  分块: concept_chunking
  文档切片: concept_chunking
  MCP: concept_model_context_protocol
  Model Context Protocol: concept_model_context_protocol
```

这样做的好处是：

- 检索时不用扫描所有页面 frontmatter。
- Ingest 时可以快速判断是否已有规范页。
- Lint 时更容易发现别名冲突。
- 后续脚本实现更简单。

可以把页面 frontmatter 理解成“页面自己的声明”，把 `aliases.yml` 理解成“全局索引”。

### 10. Ingest 阶段怎么用

摄入新资料时，命名系统应该参与页面创建决策。

推荐流程：

```text
1. 从新文档中抽取候选概念和实体
2. 对每个候选名做 normalize
3. 查 aliases.yml 和已有页面 frontmatter
4. 如果命中已有 canonical_id，更新已有规范页
5. 如果未命中，但高度相似，进入候选合并队列
6. 如果确认为新概念，创建新规范页
7. 把新出现的常用叫法加入 aliases
8. 如发现旧页面名不规范，创建 redirect 或等待人工确认
```

例如新资料里出现：

```text
Large Language Models are changing software engineering.
```

系统不要直接创建 `Large Language Models.md`，而应该：

1. 规范化为 `Large Language Model`。
2. 查 aliases。
3. 命中 `concept_large_language_model`。
4. 更新 `大语言模型.md`。
5. 必要时把复数形式 `Large Language Models` 加入 aliases。

### 11. Query 阶段怎么用

用户提问往往不会使用你的规范名。

例如用户问：

```text
卡帕西说的那个 LLM Wiki 是不是一种 RAG？
```

Query 预处理可以识别：

```yaml
Andrej Karpathy:
  canonical_id: person_andrej_karpathy
  canonical_title: Andrej Karpathy
LLM Wiki:
  canonical_id: concept_llm_wiki
  canonical_title: LLM-Wiki
RAG:
  canonical_id: concept_retrieval_augmented_generation
  canonical_title: 检索增强生成
```

然后检索时同时查：

- 规范页标题
- aliases
- summary
- 正文
- 相关双向链接

排序时可以给这些命中更高权重：

- title 精确命中
- alias 精确命中
- canonical_id 匹配
- redirect 页指向的规范页

### 12. Lint 阶段怎么检查

命名系统需要定期巡检。否则 aliases 会越来越乱。

建议 Lint 至少检查：

1. 别名冲突  
   同一个 alias 是否指向多个 canonical_id。

2. 重复页面  
   是否有两个页面 title 不同但 aliases 高度重叠。

3. 缺少规范名  
   concept/entity 页面是否缺少 `canonical_id`。

4. 缺少 aliases  
   重要英文术语是否没有放进 aliases。

5. 断开的 redirect  
   redirect_to 指向的页面是否存在。

6. redirect 链过长  
   A -> B -> C 应该压缩成 A -> C、B -> C。

7. 正文链接未规范化  
   正文是否链接到了别名页，而不是规范页。

8. 文件名和 title 不一致  
   是否需要接受这种不一致，还是统一重命名。

### 13. 双语知识库的推荐策略

你的 LLM-Wiki 很明显会长期处于中英混合状态。最务实的规则是：

```text
页面标题：中文优先
英文原词：放入 aliases
首段：中英并列出现一次
后文：优先使用中文规范名，必要时保留英文术语
链接：统一指向中文规范页
```

例如：

```md
# 文档切块

文档切块（Chunking）是指把长文档拆成多个相对独立、可检索、可引用、可处理的小片段。
```

frontmatter：

```yaml
title: 文档切块
aliases:
  - Chunking
  - Document Chunking
  - 分块
  - 文档切片
```

这样人读起来顺，检索也不会漏掉英文资料。

### 14. 什么时候不要急着合并

不是所有相似名称都应该立刻合并。

例如：

- `向量检索` 和 `语义搜索` 很相关，但不完全等价。
- `语言模型` 和 `大语言模型` 相关，但范围不同。
- `RAG` 和 `LLM-Wiki` 有关系，但不是同一个概念。
- `MCP` 可能指 Model Context Protocol，也可能在别的领域指其他东西。

遇到这种情况，推荐做法是：

1. 不要自动合并。
2. 在 Lint 报告里列为“疑似重复或相关概念”。
3. 让人工决定是合并、建立父子关系，还是保留为相关页面。

可以用状态标记：

```yaml
status: needs_review
possible_duplicate_of: 向量检索
```

### 15. 重命名页面时的安全流程

如果要把一个规范页改名，建议按流程走：

```text
1. 确认 canonical_id 不变
2. 创建或更新新标题页面
3. 把旧标题加入 aliases
4. 把旧页面改为 redirect
5. 批量更新正文中的 WikiLink
6. 更新 aliases.yml
7. 运行 Lint 检查断链和 redirect
8. 记录到 log.md
```

例如：

```text
旧名：Chunking
新名：文档切块
canonical_id: concept_chunking
```

处理后：

- `文档切块.md` 成为规范页。
- `Chunking.md` 成为 redirect 页。
- `Chunking` 加入 `文档切块.md` 的 aliases。
- 所有正文优先链接 `[[文档切块|Chunking]]` 或 `[[文档切块]]`。

### 16. 当前项目的推荐落地方案

对你现在的 LLM-Wiki 来说，可以先这样定：

1. 概念页中文标题优先。
2. 人名、产品名、项目名保留官方英文名。
3. 每个 concept/entity 页面必须有 `canonical_id`。
4. 英文术语、缩写、旧译名全部放进 `aliases`。
5. AI 生成新页面前必须先查 aliases。
6. AI 写 WikiLink 时必须优先链接到规范页。
7. 旧名称页面不直接删除，先做 redirect。
8. 单独维护 `wiki/00_索引与地图/aliases.yml`。
9. Lint 定期检查别名冲突、重复页面、断 redirect。
10. 不确定是否同义时，不自动合并，标记 `needs_review`。

### 17. 一个最小可执行示例

规范页：

```md
---
title: 文档切块
type: concept
canonical_id: concept_chunking
aliases:
  - Chunking
  - Document Chunking
  - 分块
  - 切块
  - 文档切片
status: stable
---

# 文档切块

文档切块（Chunking）是指把长文档拆成多个相对独立、可检索、可引用、可处理的小片段。
```

重定向页：

```md
---
title: Chunking
type: redirect
canonical_id: concept_chunking
redirect_to: 文档切块
status: redirected
---

# Chunking

请见 [[文档切块]]。
```

全局别名表：

```yaml
aliases:
  Chunking: concept_chunking
  Document Chunking: concept_chunking
  分块: concept_chunking
  切块: concept_chunking
  文档切片: concept_chunking
```

### 18. 一句话总结

规范名、别名、重定向机制是 LLM-Wiki 的“命名秩序层”：规范名保证一个知识点有唯一主节点，别名保证不同叫法都能被找回，重定向保证旧名称和旧链接不会断掉。没有这层，知识库会逐渐长出重复页面、分散链接和混乱概念；有了这层，AI 才能稳定地创建、更新、检索和维护 Wiki 网络。

## 问题 3：最小溯源粒度设计如何实现

### 1. 最小溯源粒度是什么

最小溯源粒度，指的是知识库里一条知识、一个结论、一个定义、一个判断，至少要能追溯到多细的原始证据。

在 LLM-Wiki 里，不建议只追溯到“某篇原文”。更稳妥的最小粒度是：

```text
source_id + chunk_id
```

如果材料是 PDF、书籍、长报告，还应该进一步记录：

```text
source_id + chunk_id + page_range
```

如果材料是访谈、会议记录、聊天记录，则可以记录：

```text
source_id + chunk_id + timestamp / speaker / turn_id
```

也就是说，最小溯源粒度的目标是：当 Wiki 页面里出现一句重要结论时，未来可以准确知道它来自哪份原始资料、哪一个片段、哪一页或哪一段。

### 2. 为什么不能只记录 source 文件

只记录文件级来源，例如：

```yaml
source_files:
  - raw/articles/rag-guide.md
```

在早期看起来够用，但系统稍微变大就会不够。

问题主要有：

- 长文档里很难回看具体证据。
- 同一篇文档可能包含多个观点，甚至互相矛盾的观点。
- Wiki 页面中的一句话可能只来自原文某一小节。
- 后续原文更新时，很难判断哪些 Wiki 内容受影响。
- 做冲突检测时无法定位冲突发生在哪一段。
- 生成带引用回答时，引用会显得太粗。

所以文件级溯源只能回答“来自哪篇资料”，chunk 级溯源才能回答“来自哪段证据”。

### 3. 推荐的四层数据模型

可以把 LLM-Wiki 的溯源设计拆成四层：

```text
Source 原始资料
  -> Chunk 原文片段
    -> Claim 知识声明
      -> Wiki Page 知识页面
```

四层分别负责：

| 层级 | 作用 |
|---|---|
| Source | 表示一份原始资料 |
| Chunk | 表示原文中的一个可处理片段 |
| Claim | 表示从 chunk 中抽取出的一条知识声明 |
| Wiki Page | 表示最终沉淀的知识页面 |

这四层不一定都要一开始做成数据库表，但脑子里要有这个模型。

### 4. Source 层怎么实现

Source 是原始资料的唯一身份。

每个 raw 文档导入时，都应该生成一个稳定的 `source_id`。

示例：

```yaml
source_id: src_20260524_a13f9c
source_type: article
source_uri: https://example.com/rag-guide
source_path: raw/articles/rag-guide.md
source_hash: sha256:xxxx
imported_at: 2026-05-24T10:30:00+08:00
title: RAG Guide
author: null
published_at: null
version: 1
status: active
```

关键字段说明：

- `source_id`：系统内部使用的唯一 ID。
- `source_type`：article、paper、book、note、meeting、chat、video 等。
- `source_uri`：外部来源链接，没有就留空。
- `source_path`：本地 raw 文件路径。
- `source_hash`：用于判断内容是否变化。
- `imported_at`：摄入时间。
- `version`：同一来源更新后的版本号。

实现上可以先用一个 JSONL 文件：

```text
metadata/sources.jsonl
```

每行一个 source。

### 5. Chunk 层怎么实现

Chunk 是最小证据单元。

每个 source 被切块后，生成多个 chunk，每个 chunk 都要有稳定 ID。

推荐 `chunk_id` 形式：

```text
src_20260524_a13f9c_chunk_001
src_20260524_a13f9c_chunk_002
src_20260524_a13f9c_chunk_003
```

chunk 元数据示例：

```json
{
  "chunk_id": "src_20260524_a13f9c_chunk_003",
  "source_id": "src_20260524_a13f9c",
  "source_path": "raw/articles/rag-guide.md",
  "section_path": ["RAG 架构", "检索阶段"],
  "start_line": 80,
  "end_line": 128,
  "page_range": null,
  "char_count": 1640,
  "token_estimate": 860,
  "summary": "本段说明 RAG 中检索阶段如何从外部知识库召回候选内容。",
  "hash": "sha256:xxxx",
  "previous_chunk": "src_20260524_a13f9c_chunk_002",
  "next_chunk": "src_20260524_a13f9c_chunk_004"
}
```

实现上可以先用：

```text
metadata/chunks.jsonl
```

如果未来规模变大，再迁移到 SQLite。

### 6. Claim 层是什么，是否一开始就要做

Claim 是从 chunk 中抽取出来的“知识声明”。

例如一个 chunk 里可能包含三条 claim：

```text
1. BM25 是一种基于词频和逆文档频率的关键词检索排序函数。
2. BM25 适合做精确词匹配和关键词召回。
3. 在 LLM-Wiki 中，BM25 可以作为本地 Markdown 检索的基础方案。
```

每条 claim 都可以绑定来源：

```yaml
claim_id: claim_20260524_00031
text: BM25 可以作为 LLM-Wiki 中本地 Markdown 检索的基础方案。
source_refs:
  - source_id: src_20260524_a13f9c
    chunk_id: src_20260524_a13f9c_chunk_003
    evidence_type: paraphrase
    confidence: medium
```

个人知识库初期不一定要单独维护 `claims.jsonl`，因为会增加复杂度。

更务实的做法是：

- 初期：在 Wiki 页面中直接给关键段落记录 `source_refs`。
- 第二阶段：对重要结论、争议结论、可复用事实抽取 claim。
- 规模扩大后：维护独立 `metadata/claims.jsonl`。

### 7. Wiki 页面里怎么记录 source_refs

有三种常见方式。

第一种：页面级来源。

适合来源摘要页或整页基本来自同一组材料的情况：

```yaml
---
title: 文档切块
type: concept
canonical_id: concept_chunking
source_refs:
  - source_id: src_20260524_a13f9c
    chunk_id: src_20260524_a13f9c_chunk_001
  - source_id: src_20260524_b72d1e
    chunk_id: src_20260524_b72d1e_chunk_004
---
```

优点是简单。缺点是无法知道正文每一句分别来自哪里。

第二种：段落级来源。

适合概念页、综述页、对比页。

```md
文档切块（Chunking）是把长文档拆成多个相对独立、可检索、可引用、可处理的小片段。[^src_001]

[^src_001]: `src_20260524_a13f9c_chunk_001`，见 `raw/articles/llm-wiki.md` 第 422-463 行。
```

优点是可读性好，也符合 Markdown 习惯。

第三种：块级注释式来源。

适合想让机器更容易解析的情况：

```md
文档切块（Chunking）是把长文档拆成多个相对独立、可检索、可引用、可处理的小片段。
<!-- source_refs: [{"source_id":"src_20260524_a13f9c","chunk_id":"src_20260524_a13f9c_chunk_001","lines":"422-463"}] -->
```

优点是机器容易解析。缺点是人读起来稍微重一些。

当前阶段推荐：**页面 frontmatter 记录页面级 source_refs，正文关键结论用脚注记录段落级来源。**

### 8. 什么内容必须溯源，什么内容可以不溯源

不是每一句话都要加引用。否则 Wiki 页面会变得很吵。

必须溯源：

- 定义
- 关键事实
- 数据
- 时间线
- 人物观点
- 工具能力描述
- 方案优劣判断
- 与其他资料可能冲突的说法
- 你未来可能会拿来回答问题的结论

可以不逐句溯源：

- 页面导航语
- 你自己的组织性总结
- 非关键过渡句
- 明显来自全文综合的结构安排
- 已在同段落中有来源支撑的解释句

一个好规则是：如果这句话将来被质疑，你希望能快速找到证据，那它就应该有来源。

### 9. source_refs 字段建议

推荐一个够用的 `source_refs` 结构：

```yaml
source_refs:
  - source_id: src_20260524_a13f9c
    chunk_id: src_20260524_a13f9c_chunk_003
    source_path: raw/articles/rag-guide.md
    section_path: RAG 架构 > 检索阶段
    line_range: 80-128
    page_range: null
    evidence_type: paraphrase
    quote: null
    note: 用于支持 RAG 检索阶段的定义。
```

字段含义：

- `source_id`：来自哪份原始资料。
- `chunk_id`：来自哪一段。
- `source_path`：方便人直接打开原文。
- `section_path`：保留语境。
- `line_range`：Markdown 或文本文件最实用。
- `page_range`：PDF、书籍、报告最实用。
- `evidence_type`：direct_quote、paraphrase、summary、inference。
- `quote`：必要时保留短摘录，不要存太长。
- `note`：说明这个来源支撑什么。

### 10. evidence_type 很重要

不是所有来源关系都一样。

建议区分四种：

| 类型 | 含义 |
|---|---|
| direct_quote | 直接引用原文 |
| paraphrase | 改写原文观点 |
| summary | 对一段或多段内容的总结 |
| inference | 基于来源做出的推论 |

例如：

```yaml
evidence_type: inference
note: 原文没有直接说“LLM-Wiki 不是传统 RAG”，但根据其对 compile 与 retrieve 的对比可以推导出这一点。
```

这对知识库质量很关键。因为它能区分“原文明确说的”和“我们基于原文理解出来的”。

### 11. Ingest 阶段如何生成溯源

Ingest 流程里，溯源应该自动产生，而不是最后人工补。

推荐流程：

```text
1. 读取 raw 文件
2. 生成 source_id 和 source metadata
3. 规范化文本
4. 切分 chunks
5. 为每个 chunk 记录行号、页码、section_path、hash
6. 为每个 chunk 生成摘要和概念/实体标签
7. 抽取候选 claims
8. 生成或更新 Wiki 页面
9. 每个新增结论都带 source_refs
10. 写入 metadata/sources.jsonl 和 metadata/chunks.jsonl
11. 更新 log.md
```

关键点：**先有 source 和 chunk，再有 Wiki 页面。** 不要先写 Wiki 页面，最后再想办法补来源。

### 12. Query 阶段如何使用溯源

当用户问问题时，系统可以这样用溯源：

```text
1. 先检索相关 Wiki 页面
2. 读取页面中的 source_refs
3. 如果问题需要证据，回看相关 chunks
4. 判断回答中的关键结论分别由哪些 chunk 支撑
5. 输出答案时附上来源
```

回答可以这样引用：

```md
BM25 适合在 LLM-Wiki 中作为轻量关键词召回方案，因为它不依赖向量库，适合本地 Markdown 初期检索。  
来源：`src_20260524_a13f9c_chunk_003`
```

如果是面向人读的版本，可以更友好：

```md
来源：《LLM-Wiki知识库搭建学习总结20260524.md》“混合搜索和 BM25”相关段落。
```

底层仍然保留 `source_id + chunk_id`。

### 13. 更新和冲突检测怎么用溯源

溯源设计最大的价值之一，是后续更新时能判断影响范围。

例如某个 raw 文件更新了：

```text
source_id: src_20260524_a13f9c
chunk_003 hash changed
chunk_004 unchanged
chunk_005 unchanged
```

系统可以只检查引用了 `chunk_003` 的 Wiki 页面。

如果新 chunk 里的说法和旧页面不同，就不要直接覆盖，而是标记：

```yaml
status: disputed
conflict_refs:
  - old:
      source_id: src_20260524_a13f9c
      chunk_id: src_20260524_a13f9c_chunk_003
  - new:
      source_id: src_20260524_a13f9c_v2
      chunk_id: src_20260524_a13f9c_v2_chunk_003
```

这样 AI 不会凭感觉“改掉旧结论”，而是知道冲突来自哪里。

### 14. 文件结构建议

当前项目可以先这样组织：

```text
your-llm-wiki/
├── raw/
├── wiki/
│   ├── 00_索引与地图/
│   ├── 10_核心概念/
│   └── 40_来源摘要/
├── metadata/
│   ├── sources.jsonl
│   ├── chunks.jsonl
│   ├── claims.jsonl        # 第二阶段再加
│   └── aliases.yml
└── log.md
```

一开始最重要的是：

```text
metadata/sources.jsonl
metadata/chunks.jsonl
wiki 页面 frontmatter 中的 source_refs
```

### 15. 一个完整例子

假设 raw 文档里有一段：

```text
超长文档必须先分 chunk，再按需加载，禁止整篇无脑塞上下文。
```

生成 chunk：

```json
{
  "source_id": "src_20260524_llmwiki_summary",
  "chunk_id": "src_20260524_llmwiki_summary_chunk_017",
  "source_path": "raw/notes/LLM-Wiki知识库搭建学习总结20260524.md",
  "section_path": ["实践检查清单"],
  "line_range": "775-775",
  "summary": "本段强调超长文档需要先切块再按需加载。",
  "hash": "sha256:xxxx"
}
```

写入 Wiki 页面：

```md
---
title: 文档切块
type: concept
canonical_id: concept_chunking
source_refs:
  - source_id: src_20260524_llmwiki_summary
    chunk_id: src_20260524_llmwiki_summary_chunk_017
---

# 文档切块

超长文档应先切分为 chunk，再按问题需要加载相关片段，而不是整篇塞入模型上下文。[^chunking-001]

[^chunking-001]: `src_20260524_llmwiki_summary_chunk_017`，来自 `LLM-Wiki知识库搭建学习总结20260524.md` 第 775 行。
```

这样你以后看到这个结论，就能直接追到证据。

### 16. Lint 如何检查溯源质量

建议 Lint 增加这些检查：

1. concept/entity/overview 页面是否有 `source_refs`。
2. 页面中包含事实判断的段落是否至少有一个脚注来源。
3. `source_refs.source_id` 是否存在于 `sources.jsonl`。
4. `source_refs.chunk_id` 是否存在于 `chunks.jsonl`。
5. `chunk_id` 是否属于对应 `source_id`。
6. `line_range` 或 `page_range` 是否可回看。
7. redirect 页面是否不需要 source_refs。
8. disputed 页面是否有 `conflict_refs`。
9. 引用了已失效 source 或旧版本 source 的页面是否标记 `outdated`。

这些检查能让知识库避免“看起来有引用，实际追不回去”的问题。

### 17. 初期不要过度设计

最小溯源粒度容易设计得很复杂，但你当前阶段可以先抓住三件事：

1. 每份 raw 文档必须有 `source_id`。
2. 每个 chunk 必须有 `chunk_id`、`source_id`、`source_path`、`line_range/page_range`。
3. Wiki 页面里的关键结论至少引用到 `source_id + chunk_id`。

先做到这三点，就已经比“只记录文件名”强很多。

### 18. 当前项目推荐实施步骤

建议按这个顺序落地：

1. 新建 `metadata/sources.jsonl`。
2. 新建 `metadata/chunks.jsonl`。
3. 在 ingest 脚本里先生成 source metadata。
4. 切 chunk 时记录 line_range、section_path、hash。
5. 生成 Wiki 页面时，把用到的 chunks 写入 frontmatter 的 `source_refs`。
6. 对关键段落添加 Markdown 脚注。
7. 写一个简单 lint，检查 source_refs 是否能在 metadata 里找到。
8. 等页面多了以后，再考虑 claim 层。

### 19. 一句话总结

最小溯源粒度的实现，本质上是为每条重要知识建立一条从 Wiki 页面回到原始证据的链路：`Wiki 结论 -> source_refs -> chunk_id -> source_id -> raw 原文位置`。初期做到 chunk 级溯源就足够实用，后期再把重要结论升级成独立 claim 管理。

## 问题 4：Chunking 规则不能只写“要分块”的解决方案

### 1. 问题本质

“长文要分块”只是一个方向，不是工程方案。

真正需要解决的是：系统应该在什么位置切、每块多大、如何避免切断语义、怎么处理表格和代码、怎么记录元数据、怎么保证后续检索和溯源都能稳定工作。

如果规则只写“要分块”，AI 或脚本每次都可能用不同方式切：

- 今天按标题切。
- 明天按 1000 字硬切。
- 后天把表格切断。
- 再下一次 chunk_id 重新编号，旧引用全部失效。

所以这个问题的解决方案不是“提醒 AI 注意分块”，而是把 Chunking 变成一套明确、可复用、可检查的规则。

### 2. 推荐解决方案：语义优先的分层切块

建议采用“语义优先、长度兜底、元数据强约束”的方案。

核心原则：

```text
先尊重文档结构，再控制 chunk 长度，最后用元数据保证可追踪。
```

也就是说：

1. 优先按标题、章节、段落等自然结构切。
2. 如果结构块太长，再按段落继续切。
3. 如果段落仍然太长，再按句子或较小单位切。
4. 表格、代码块、引用块尽量保持完整。
5. 每个 chunk 必须有稳定 ID 和来源位置。
6. chunk 之间允许少量 overlap，但不能过度重复。

### 3. 可直接落地的配置

可以把下面这段写入 `CLAUDE.md`、`AGENTS.md` 或后续的 `config.yml`：

```yaml
chunking:
  default_strategy: semantic_heading_first

  size:
    target_tokens: 1000
    min_tokens: 200
    soft_max_tokens: 1400
    hard_max_tokens: 1800
    overlap_tokens: 120

  split_priority:
    - markdown_heading
    - horizontal_rule
    - paragraph
    - list_item_group
    - sentence

  preserve_blocks:
    - fenced_code_block
    - markdown_table
    - blockquote
    - yaml_frontmatter

  merge_rules:
    merge_small_chunks: true
    merge_if_below_tokens: 200
    prefer_merge_with_previous: true

  metadata_required:
    - chunk_id
    - source_id
    - source_path
    - chunk_index
    - section_path
    - start_line
    - end_line
    - token_estimate
    - char_count
    - hash
    - previous_chunk
    - next_chunk
```

这套配置的意思是：

- 目标 chunk 大小约 1000 tokens。
- 小于 200 tokens 的块通常太碎，要合并。
- 超过 1400 tokens 的块尽量继续拆。
- 超过 1800 tokens 的块必须拆，除非是不可拆的长表格或代码块。
- 相邻 chunk 保留约 120 tokens 的上下文 overlap。
- 优先按 Markdown 标题切，其次按段落，再按句子。
- 代码块、表格、引用块、frontmatter 不要从中间切开。

### 4. 具体切分流程

建议实际 Ingest 时按这个流程走：

```text
1. 读取 raw 文档
2. 生成 source_id
3. 清洗文本，保留标题、行号、代码块、表格结构
4. 识别 Markdown 标题树
5. 按标题树生成初始 sections
6. 对每个 section 估算 token
7. 如果 section 在目标范围内，直接成为 chunk
8. 如果 section 太长，按段落继续拆
9. 如果段落仍然太长，按句子继续拆
10. 如果 chunk 太短，与前一个或后一个 chunk 合并
11. 为相邻 chunk 添加少量 overlap
12. 为每个 chunk 写入元数据
13. 生成 chunks.jsonl
14. 运行 chunk lint 检查
```

重点是：**先按结构切，再按长度修正**。

不要一开始就按固定字数切。

### 5. Markdown 文档的切分规则

对 Markdown，优先使用标题层级。

例如：

```md
# RAG

## 背景

...

## 检索阶段

...

### BM25

...

### 向量检索

...
```

理想切分结果可能是：

```text
chunk_001: # RAG > ## 背景
chunk_002: # RAG > ## 检索阶段 > ### BM25
chunk_003: # RAG > ## 检索阶段 > ### 向量检索
```

每个 chunk 都要保留完整标题路径：

```yaml
section_path:
  - RAG
  - 检索阶段
  - BM25
```

这样单独读取 `chunk_002` 时，模型也知道它不是泛泛讲 BM25，而是在 RAG 检索阶段里讲 BM25。

### 6. 太长 section 怎么处理

如果某个标题下面内容太长，不要整个塞进一个 chunk。

规则：

```text
section <= 1400 tokens：保留为一个 chunk
1400 < section <= 1800 tokens：优先保留，必要时拆
section > 1800 tokens：必须继续按段落拆
```

拆分后，每个子 chunk 仍然继承同一个 `section_path`，并增加局部序号：

```yaml
section_path:
  - LLM-Wiki 架构
  - Ingest 流程
section_part: 1
section_part_total: 3
```

这样可以避免同一个章节被拆开后失去关系。

### 7. 太短 chunk 怎么处理

太短的 chunk 通常没有足够语境。

例如只有一句：

```text
## 总结
这就是完整流程。
```

这种 chunk 单独检索出来价值很低。

推荐规则：

```text
chunk < 200 tokens：优先并入前一个 chunk
如果前一个 chunk 已经太大，则并入后一个 chunk
如果是重要标题或目录节点，可以保留但标记为 structural
```

元数据可以这样标记：

```yaml
chunk_role: structural
```

但大多数情况下，小块合并更好。

### 8. Overlap 怎么设计

Overlap 不是简单复制上一块末尾一大段，而是为了保留边界语境。

推荐方式：

```text
overlap = 标题路径 + 上一个 chunk 末尾 1-3 个自然段，最多约 120 tokens
```

同时在元数据里标记哪些内容是 overlap：

```yaml
overlap_from_previous:
  chunk_id: src_20260524_a13f9c_chunk_002
  token_estimate: 110
```

注意：生成摘要、抽取 claim 时，最好避免把 overlap 内容重复统计为新证据。

所以更严谨的做法是：

- 检索时可以使用 overlap。
- 摘要时知道 overlap 存在。
- 生成 claim 时只基于 chunk 的主体内容。

### 9. 表格、代码块、引用块怎么处理

这些块不能随便切。

#### 表格

Markdown 表格应尽量整体保留。

如果表格太长：

```text
优先按行组切分，但每个子表都必须保留表头。
```

例如：

```md
| 工具 | 用途 | 备注 |
|---|---|---|
| BM25 | 关键词检索 | 适合初期 |
| 向量检索 | 语义召回 | 适合规模扩大后 |
```

如果切成两块，每块都要保留：

```md
| 工具 | 用途 | 备注 |
|---|---|---|
```

否则后面的行会失去含义。

#### 代码块

代码块尽量整体保留。

如果代码块超过 hard max：

```text
按函数、类、配置段落切，而不是按行数硬切。
```

#### 引用块

引用块尽量整体保留，因为引用中的上下文常常是连续表达。

如果太长，可以按段落切，但要保留引用来源。

### 10. OCR 或格式很差的文本怎么处理

OCR 文本经常没有标题、段落混乱、换行异常。

对这类文本，不要直接进入普通 chunking。先做 normalization：

```text
1. 修复异常换行
2. 合并被错误拆开的句子
3. 识别页码
4. 尝试恢复标题
5. 保留 page_range
6. 再按段落和长度切
```

如果无法恢复标题，就用页码和局部摘要做结构：

```yaml
section_path:
  - OCR 文档
  - Page 5-6
page_range: 5-6
```

对 OCR 文档，`page_range` 比 `line_range` 更重要。

### 11. 输出格式：chunks.jsonl

每个 chunk 输出为 JSONL 一行。

示例：

```json
{"chunk_id":"src_20260524_a13f9c_chunk_003","source_id":"src_20260524_a13f9c","source_path":"raw/articles/rag-guide.md","chunk_index":3,"section_path":["RAG 架构","检索阶段"],"start_line":80,"end_line":128,"page_range":null,"char_count":1640,"token_estimate":860,"summary":"本段说明 RAG 中检索阶段如何召回候选内容。","hash":"sha256:xxxx","previous_chunk":"src_20260524_a13f9c_chunk_002","next_chunk":"src_20260524_a13f9c_chunk_004","overlap_from_previous":{"chunk_id":"src_20260524_a13f9c_chunk_002","token_estimate":110}}
```

这行数据要能回答：

- 这个 chunk 来自哪篇原文？
- 在原文哪里？
- 属于哪个章节？
- 大概多长？
- 前后 chunk 是谁？
- 内容是否变过？
- 摘要是什么？

### 12. chunk_id 稳定性规则

`chunk_id` 不能每次运行都随机变化，否则旧的 `source_refs` 会失效。

初期可以用：

```text
{source_id}_chunk_{chunk_index}
```

例如：

```text
src_20260524_a13f9c_chunk_003
```

但如果文档中间插入内容，后面的编号可能全部变化。

更稳的第二阶段方案是加入 section slug 和 hash：

```text
{source_id}_{section_slug}_{short_hash}
```

例如：

```text
src_20260524_a13f9c_retrieval-stage_9fd2c1
```

当前阶段可以先用顺序编号，但必须记录 `hash`。后续如果 chunk hash 大量变化，Lint 要提示“chunk 引用可能需要重建”。

### 13. Chunk 摘要和标签

切完 chunk 后，建议立即生成两个轻量字段：

```yaml
summary: 本段说明 RAG 中 BM25 适合承担关键词召回角色。
concepts:
  - RAG
  - BM25
  - 关键词检索
entities:
  - null
```

这样 Query 阶段不用每次先读 chunk 全文，可以先读 summary 和 concepts 粗筛。

注意：summary 要描述 chunk 内容，不要写成评价。

好：

```text
本段说明 Chunking 的目标是把长文档拆成可检索、可引用、可处理的小片段。
```

差：

```text
这一段非常重要，值得认真阅读。
```

### 14. Chunk Lint 检查项

规则写出来后，必须能检查。

建议增加 `chunk lint`：

```text
1. 是否存在超过 hard_max_tokens 的 chunk
2. 是否存在低于 min_tokens 且未合并的 chunk
3. 是否切断 fenced code block
4. 是否切断 markdown table
5. 是否缺少 section_path
6. 是否缺少 source_id 或 chunk_id
7. chunk_id 是否重复
8. previous_chunk / next_chunk 是否连续
9. line_range 是否有效
10. hash 是否存在
11. overlap 是否过大
12. summary 是否为空
```

Chunking 规则没有 Lint，就会逐渐漂移。

### 15. 与 Ingest、Query、溯源的关系

Chunking 不是孤立步骤。

它直接影响三件事：

第一，Ingest。

如果 chunk 切得好，AI 能更稳定地抽取概念、实体、结论，并生成 Wiki 页面。

第二，Query。

如果 chunk 有 summary、concepts、section_path，检索时可以更快找到相关片段。

第三，溯源。

如果 chunk 有 `source_id`、`chunk_id`、`line_range`，Wiki 里的结论就能准确追回原文。

所以 Chunking 规则是 Ingest、Query、source_refs 的共同地基。

### 16. 推荐写进规则手册的版本

可以把下面这段直接写进你的规则文档：

```md
## Chunking 规则

处理长文档时，必须先生成 chunk，不允许只写“要分块”而不说明规则。

默认采用语义优先的分层切块策略：

1. Markdown 文档优先按标题层级切分。
2. 单个标题 section 超过 1800 tokens 时，按段落继续切分。
3. 目标 chunk 大小约 1000 tokens，低于 200 tokens 的 chunk 应与相邻 chunk 合并。
4. 相邻 chunk 可保留约 120 tokens 的 overlap，但 overlap 不应重复计入 claim。
5. fenced code block、Markdown 表格、blockquote、YAML frontmatter 不得从中间切断。
6. 每个 chunk 必须记录 source_id、chunk_id、source_path、section_path、start_line、end_line、token_estimate、hash、previous_chunk、next_chunk。
7. 每个 chunk 应生成一句 summary，并抽取 concepts/entities。
8. Wiki 页面中的关键结论引用来源时，至少引用到 source_id + chunk_id。
9. 每次 chunking 后必须运行 chunk lint，检查超长块、过短块、断表格、断代码块、缺失元数据和重复 chunk_id。
```

### 17. 当前阶段的最小实施版

如果暂时不写复杂脚本，可以先人工或半自动执行最小版：

1. 只处理 Markdown。
2. 按标题切。
3. 过长标题块按段落切。
4. 太短块合并。
5. 每块记录标题路径和行号。
6. 每块给一个 `chunk_id`。
7. 每块写一句 summary。
8. 存到 `metadata/chunks.jsonl`。
9. Wiki 页面引用到 `source_id + chunk_id`。

这已经足够支撑个人 LLM-Wiki 的第一版。

### 18. 一句话总结

解决“Chunking 规则不能只写要分块”的关键，是把 Chunking 固化成一套可执行协议：语义结构优先、长度阈值兜底、特殊块不切断、短块自动合并、相邻块少量 overlap、每块强制记录元数据，并用 chunk lint 检查执行质量。

### 19. 追问：overlap 是干嘛用的

Overlap 的本质作用，是防止切块边界把语义切断。

文档不是天然按 chunk 写的。一个观点经常会跨越两个段落、两个小节，甚至前一句提出问题，后一句才给答案。如果切块时正好从中间断开，模型单独读取某个 chunk 时，就可能只看到“半句话的语境”。

例如原文是：

```text
RAG 系统通常先从知识库中召回候选片段。
这些候选片段随后会被重排，并作为上下文交给大模型生成答案。
```

如果刚好切成：

```text
chunk_001:
RAG 系统通常先从知识库中召回候选片段。

chunk_002:
这些候选片段随后会被重排，并作为上下文交给大模型生成答案。
```

那么单独看 `chunk_002` 时，“这些候选片段”指的是什么就不够清楚。模型可能需要回看上一块才能理解。

如果加入 overlap，就会变成：

```text
chunk_001:
RAG 系统通常先从知识库中召回候选片段。

chunk_002:
RAG 系统通常先从知识库中召回候选片段。
这些候选片段随后会被重排，并作为上下文交给大模型生成答案。
```

这样 `chunk_002` 单独被检索出来时，也能保留必要上下文。

Overlap 主要解决三类问题：

1. 指代断裂  
   比如“它”“这些方法”“上述流程”指向上一段内容。

2. 论证断裂  
   前一个 chunk 提出原因，后一个 chunk 给出结论。

3. 检索断裂  
   用户搜索的关键词在上一块，但真正答案在下一块；没有 overlap 时下一块可能搜不到。

但 overlap 不是越多越好。太多会导致：

- chunk 内容大量重复。
- 检索结果重复。
- 摘要重复。
- 成本上升。
- 同一个观点看起来像出现了多次。

所以比较好的策略是：

```text
overlap 只保留必要上下文，不复制大段内容。
```

对当前 LLM-Wiki，推荐：

```yaml
overlap_tokens: 100-200
```

或者更具体：

```text
保留上一个 chunk 末尾 1-3 个自然段，最多约 120 tokens。
```

一句话理解：**overlap 是给 chunk 边界加一点“缓冲区”，让每个 chunk 被单独读取时仍然带着必要上下文。**

## 问题 5：上下文预算分配规则如何自动识别 LLM 配置并自动分配

### 1. 问题本质

上下文预算分配，不应该只写死成：

```yaml
total_tokens: 24000
page_chunks: 12000
reserve_for_answer: 3000
```

因为不同模型的上下文窗口不同，输出上限不同，系统提示词长度不同，用户问题复杂度也不同。如果写死配置，换一个模型后就可能出现：

- 检索内容塞太多，导致输出空间不够。
- 输出预留太大，导致证据读得太少。
- 小上下文模型直接超限。
- 大上下文模型没有充分利用。
- 中文、英文、代码混合时 token 估算不准。

所以更好的方案是做一个“上下文预算器”：

```text
模型配置识别 -> 可用上下文计算 -> 任务类型判断 -> 比例分配 -> 动态裁剪 -> 运行后反馈修正
```

### 2. 总体解决方案

推荐实现一个 `ContextBudgetManager`，负责在每次调用 LLM 前计算预算。

它需要输入：

```yaml
model: 当前模型名
provider: openai / anthropic / local / other
task_type: query / ingest / summarize / compare / lint
language: zh / en / mixed
requested_output_type: short_answer / long_answer / wiki_page / report
system_prompt_tokens: 已估算系统规则 token
conversation_tokens: 已估算历史对话 token
candidate_pages: 候选页面
candidate_chunks: 候选 chunks
```

输出：

```yaml
context_budget:
  model_context_window: 128000
  max_output_tokens: 8000
  usable_input_tokens: 102000
  safety_margin_tokens: 12000
  allocation:
    system_rules: 8000
    query_history: 6000
    index_and_aliases: 8000
    page_summaries: 14000
    evidence_chunks: 52000
    source_refs: 4000
    working_notes: 4000
    reserve_for_answer: 8000
```

注意：具体数值不应该手填，而应该根据模型上下文窗口自动算。

### 3. 第一步：识别模型上下文配置

模型上下文配置至少要识别两个值：

```yaml
context_window_tokens: 模型最大上下文窗口
max_output_tokens: 单次最大输出 token
```

可选再识别：

```yaml
supports_system_prompt: true
supports_tool_calling: true
supports_json_mode: true
tokenizer: o200k / cl100k / sentencepiece / unknown
```

实现方式可以分三层。

第一层：运行时 API 元数据。

如果 provider 的 SDK 或模型列表接口能返回上下文窗口，就优先使用它。

```text
provider_api.get_model(model).context_window
provider_api.get_model(model).max_output_tokens
```

第二层：本地模型注册表。

很多 API 不会在每次调用时返回完整上下文配置，所以需要维护一个本地 registry：

```yaml
models:
  gpt-xxx:
    provider: openai
    context_window_tokens: 128000
    max_output_tokens: 16000
    tokenizer: o200k

  claude-xxx:
    provider: anthropic
    context_window_tokens: 200000
    max_output_tokens: 8000
    tokenizer: anthropic

  local-qwen:
    provider: local
    context_window_tokens: 32768
    max_output_tokens: 4096
    tokenizer: unknown
```

第三层：安全兜底。

如果模型未知，就使用保守默认值：

```yaml
default_unknown_model:
  context_window_tokens: 32000
  max_output_tokens: 4096
  safety_margin_ratio: 0.15
```

不要在未知模型上激进塞满上下文。

### 4. 推荐配置文件结构

可以新建：

```text
config/models.yml
config/context_budget.yml
```

`models.yml` 负责模型能力：

```yaml
models:
  default:
    context_window_tokens: 32000
    max_output_tokens: 4096
    tokenizer: unknown
    safety_margin_ratio: 0.15

  high_context:
    context_window_tokens: 128000
    max_output_tokens: 12000
    tokenizer: unknown
    safety_margin_ratio: 0.12
```

`context_budget.yml` 负责分配策略：

```yaml
profiles:
  zh_query:
    reserve_output_ratio: 0.16
    safety_margin_ratio: 0.10
    allocation:
      system_rules: 0.08
      query_history: 0.06
      index_and_aliases: 0.08
      page_summaries: 0.12
      evidence_chunks: 0.50
      source_refs: 0.04
      working_notes: 0.02

  zh_ingest:
    reserve_output_ratio: 0.12
    safety_margin_ratio: 0.10
    allocation:
      system_rules: 0.08
      source_metadata: 0.06
      chunk_text: 0.58
      existing_page_summaries: 0.14
      aliases_and_index: 0.06
      working_notes: 0.08
```

这里的 allocation 比例，是在“扣掉输出预留和安全余量之后的可用输入预算”里分。

### 5. 预算计算公式

每次调用前先算：

```text
total = model.context_window_tokens
output_reserved = min(model.max_output_tokens, total * reserve_output_ratio)
safety_margin = total * safety_margin_ratio
usable_input = total - output_reserved - safety_margin
```

然后：

```text
system_rules_budget = usable_input * system_rules_ratio
query_history_budget = usable_input * query_history_ratio
page_summaries_budget = usable_input * page_summaries_ratio
evidence_chunks_budget = usable_input * evidence_chunks_ratio
...
```

例如一个 128k 上下文模型，中文查询任务：

```text
total = 128000
output_reserved = 128000 * 0.16 = 20480
safety_margin = 128000 * 0.10 = 12800
usable_input = 94720
```

如果 evidence_chunks 占 50%：

```text
evidence_chunks_budget = 94720 * 0.50 = 47360
```

这就比手写 `page_chunks: 12000` 灵活很多。

### 6. 中文语言下比较合理的默认比例

中文 LLM-Wiki 查询任务，推荐默认比例：

```yaml
zh_query_budget:
  reserve_for_answer: 15%-20%
  safety_margin: 8%-12%

  input_allocation_after_reserve:
    system_rules: 6%-10%
    query_history: 4%-8%
    index_and_aliases: 6%-10%
    page_summaries: 10%-15%
    evidence_chunks: 45%-55%
    source_refs: 3%-5%
    working_notes: 2%-4%
```

如果只给一个最推荐版本：

```yaml
zh_query_budget_recommended:
  reserve_for_answer: 16%
  safety_margin: 10%
  input_allocation_after_reserve:
    system_rules: 8%
    query_history: 6%
    index_and_aliases: 8%
    page_summaries: 12%
    evidence_chunks: 50%
    source_refs: 4%
    working_notes: 2%
```

解释：

- `reserve_for_answer` 不能太小，中文回答如果要解释充分、带引用、做对比，15%-20% 比较稳。
- `safety_margin` 必须保留，因为 token 估算经常有误差。
- `evidence_chunks` 应该最大，因为回答质量主要取决于证据读得是否足够。
- `page_summaries` 占 10%-15%，用于先广泛了解候选页面。
- `index_and_aliases` 不能省，中文知识库里别名、中英术语扩展很重要。
- `query_history` 不宜太大，历史对话只保留和当前问题强相关的部分。

### 7. 中文为什么要这样分

中文内容有几个特点：

1. 信息密度高  
   同样长度的中文往往能表达较多信息，所以 summary 和 evidence chunk 的价值较高。

2. 术语中英混杂  
   比如 `Chunking / 文档切块 / 分块`，所以 aliases 和 query normalization 要留预算。

3. 分词边界不天然明显  
   检索和摘要阶段需要更多依赖标题、summary、aliases、section_path。

4. 解释型回答容易变长  
   中文技术解释如果要讲清楚“是什么、为什么、怎么做”，输出预留不能太少。

所以中文场景下，不建议把大部分预算都给历史对话；更应该给：

```text
page_summaries + evidence_chunks + aliases
```

### 8. 不同任务类型的比例

#### 普通查询 query

适合用户问一个具体问题。

```yaml
reserve_for_answer: 16%
safety_margin: 10%
input:
  system_rules: 8%
  query_history: 6%
  index_and_aliases: 8%
  page_summaries: 12%
  evidence_chunks: 50%
  source_refs: 4%
  working_notes: 2%
```

#### 多页综合 compare / synthesis

适合对比、综述、路线图。

```yaml
reserve_for_answer: 20%
safety_margin: 10%
input:
  system_rules: 7%
  query_history: 5%
  index_and_aliases: 8%
  page_summaries: 20%
  evidence_chunks: 45%
  source_refs: 5%
  working_notes: 10%
```

这里 page_summaries 和 working_notes 要更高，因为综合任务需要先横向看更多页面。

#### Ingest 摄入

适合处理新文档并生成 Wiki 页面。

```yaml
reserve_for_answer: 12%
safety_margin: 10%
input:
  system_rules: 8%
  source_metadata: 6%
  chunk_text: 58%
  existing_page_summaries: 14%
  aliases_and_index: 6%
  working_notes: 8%
```

Ingest 时最大预算应该给当前 chunk 原文。

#### Lint 检查

适合检查断链、重复页、别名冲突、缺引用。

```yaml
reserve_for_answer: 12%
safety_margin: 10%
input:
  lint_rules: 10%
  index_and_metadata: 30%
  sampled_pages: 35%
  issue_context: 15%
  working_notes: 10%
```

Lint 不一定要读所有正文，可以先读索引、元数据、抽样页面。

### 9. 自动裁剪规则

预算不够时，不要平均砍。要按优先级裁剪。

推荐保留优先级：

```text
1. system_rules
2. 当前用户问题
3. aliases / canonical mapping
4. 高相关 page summaries
5. 高相关 evidence chunks
6. source_refs
7. 最近但弱相关的历史对话
8. 低相关候选页面
```

裁剪策略：

```text
先砍低相关页面，再砍旧历史，再砍低分 chunks。
不要砍 system_rules。
不要砍当前用户问题。
不要砍关键 source_refs。
```

Evidence chunks 的选择可以按分数排序：

```text
final_score =
  bm25_score * 0.45
  + alias_match_score * 0.20
  + title_match_score * 0.15
  + recency_score * 0.05
  + source_quality_score * 0.10
  + diversity_score * 0.05
```

这样预算不足时，保留最可能有用的证据。

### 10. 自动识别语言并切换配置

可以在 query normalization 阶段判断语言：

```text
zh_ratio = 中文字符数 / 总字符数
en_ratio = 英文字母数 / 总字符数
```

规则：

```yaml
if zh_ratio >= 0.5:
  language_profile: zh
elif en_ratio >= 0.6:
  language_profile: en
else:
  language_profile: mixed
```

对于 mixed，建议使用中文 profile，但提高 aliases 和 page_summaries：

```yaml
mixed_query_adjustment:
  index_and_aliases: +3%
  page_summaries: +3%
  evidence_chunks: -4%
  query_history: -2%
```

因为中英混合问题通常更依赖别名扩展和术语归一。

### 11. token 估算方法

最稳的方法是使用模型对应 tokenizer。

优先级：

```text
1. 使用 provider 官方 tokenizer 或 SDK tokenizer
2. 使用兼容 tokenizer
3. 使用本地估算函数
```

如果暂时没有 tokenizer，可以用保守估算：

```text
中文 token ≈ 中文字符数 * 1.1
英文 token ≈ 英文单词数 * 1.3
代码 token ≈ 字符数 / 3
Markdown 结构符号额外加 5%-10%
```

这不是精确值，但对预算裁剪足够安全。

关键是保留 `safety_margin`，不要把上下文塞到 100%。

### 12. 伪代码实现

可以先这样实现：

```python
def build_context_budget(model_name, provider, task_type, language, token_counts):
    model_cfg = resolve_model_config(model_name, provider)
    profile = resolve_budget_profile(task_type, language)

    total = model_cfg.context_window_tokens
    max_output = model_cfg.max_output_tokens

    output_reserved = min(
        max_output,
        int(total * profile.reserve_output_ratio)
    )
    safety_margin = int(total * profile.safety_margin_ratio)
    usable_input = total - output_reserved - safety_margin

    allocation = {}
    for bucket, ratio in profile.input_allocation.items():
        allocation[bucket] = int(usable_input * ratio)

    return {
        "model": model_name,
        "total_tokens": total,
        "output_reserved": output_reserved,
        "safety_margin": safety_margin,
        "usable_input": usable_input,
        "allocation": allocation,
    }
```

然后在组装 prompt 时：

```python
context.add("system_rules", system_rules, budget["system_rules"])
context.add("query_history", relevant_history, budget["query_history"])
context.add("index_and_aliases", aliases_and_index, budget["index_and_aliases"])
context.add("page_summaries", ranked_summaries, budget["page_summaries"])
context.add("evidence_chunks", ranked_chunks, budget["evidence_chunks"])
context.add("source_refs", source_refs, budget["source_refs"])
```

每个 bucket 超预算时，按相关性排序截断。

### 15. 建议写进规则手册的版本

可以直接写：

```md
## 上下文预算规则

每次调用 LLM 前，必须根据当前模型上下文窗口动态计算预算，不允许固定写死 total_tokens。

流程：

1. 识别当前 model 和 provider。
2. 从 provider API 或 `config/models.yml` 读取 `context_window_tokens` 和 `max_output_tokens`。
3. 根据任务类型选择预算 profile。
4. 根据 query 语言选择 `zh`、`en` 或 `mixed` profile。
5. 先预留输出预算和安全余量。

7. 超预算时按相关性裁剪，优先保留系统规则、当前问题、aliases、page summaries 和高相关 evidence chunks。
8. 中文查询默认预留 16% 输出、10% 安全余量；输入预算中 evidence_chunks 占 50%、page_summaries 占 12%、index_and_aliases 占 8%。
```

现在先不要做太复杂。你可以先实现这三个文件/模块：

```text
config/models.yml

scripts/context_budget.py
```

最小功能：

1. 输入模型名，查上下文窗口。
2. 输入任务类型和语言，选预算 profile。
3. 自动计算输出预留、安全余量和各 bucket token。
4. 根据预算裁剪 page summaries 和 chunks。
5. 打印本次调用的预算报告，便于调试。

预算报告示例：

```yaml

```

### 17. 一句话总结

上下文预算分配应该做成动态预算器：先识别模型的 `context_window_tokens` 和 `max_output_tokens`，再根据任务类型和中文/中英混合语言特征选择预算 profile，扣掉输出预留和安全余量后，把最大比例分给高相关 evidence chunks，同时保留足够的 aliases、page summaries 和 source_refs。中文 LLM-Wiki 查询的推荐默认值是：输出预留 16%、安全余量 10%，剩余输入预算中 evidence chunks 约 50%、page summaries 约 12%、index/aliases 约 8%。

## 问题 6：希望大部分自动完成时，哪些场景仍然需要人工干预

### 1. 基本原则

你的方向是对的：LLM-Wiki 如果动不动就要求人工确认，会变成一个很累的半自动系统，维护成本反而上升。

更合理的目标不是“所有动作都人工审批”，而是：

```text
低风险动作自动执行。
中风险动作自动执行但完整记录。
高风险动作生成变更计划，等待人工确认。
不可逆或敏感动作默认禁止自动执行。
```

也就是说，人工干预应该只出现在少数关键节点：会造成知识丢失、语义误合并、历史断裂、隐私泄露、批量污染的地方。

### 2. 推荐的四级自动化策略

可以把所有动作分成四级：

| 等级 | 名称 | 处理方式 |
|---|---|---|
| L0 | 安全自动 | 直接执行 |
| L1 | 自动执行并记录 | 执行，但写入 log 和 diff |
| L2 | 生成方案等待确认 | 不直接改，先给变更计划 |
| L3 | 默认禁止 | 除非你明确授权，否则不做 |

这比简单写“必须人工确认”更灵活。

### 3. L0：可以直接自动完成的动作

这些动作风险低、可逆、语义判断少，建议默认自动完成。

```text
L0 safe_auto
```

包括：

1. 补齐缺失的 `created`、`updated`、`status` 等元数据。
2. 为新 raw 文档生成 `source_id`。
3. 为文档生成 chunk 和 chunk metadata。
4. 为 chunk 生成摘要、token 估算、hash。
5. 更新 `metadata/sources.jsonl`、`metadata/chunks.jsonl`。
6. 新建来源摘要页。
7. 更新 `index.md` 中的新增页面链接。
8. 为正文中已存在的规范页自动加 WikiLink。
9. 修复明显格式问题，例如多余空行、缺失 frontmatter 分隔符。
10. 运行 Lint 并生成报告。
11. 生成候选别名，但不一定直接合并到 aliases。

这些动作即使出错，也比较容易通过 Git diff 看出来并回滚。

### 4. L1：可以自动执行，但必须记录的动作

这些动作可以自动化，但应该留下清晰日志，便于回看。

```text
L1 auto_with_log
```

包括：

1. 给已有页面追加新来源引用。
2. 在概念页末尾追加“补充资料”或“新来源补充”。
3. 给已有 aliases 增加低争议别名。
4. 新建 draft 状态的概念页或实体页。
5. 新建 `qa-note` 页面保存一次高质量问答。
6. 自动创建 redirect 页，但仅限旧文件名明确指向新规范名。
7. 更新来源摘要页中的摘要和关联概念列表。
8. 自动修复少量断链。
9. 对过期页面加 `status: outdated` 标记。
10. 对疑似冲突页面加 `status: disputed` 或 `needs_review`。

L1 的关键是：可以做，但必须写入：

```text
log.md
变更文件列表
变更原因
涉及 source_id / chunk_id
```

不要默默改。

### 5. L2：仍然需要你确认的动作

这些是你真正需要干预的场景。它们共同特点是：AI 可以提出建议，但最后判断涉及知识体系取舍、命名策略、历史语义或较大范围影响。

```text
L2 require_review
```

#### 1. 合并两个已有页面

例如：

```text
向量检索.md
语义搜索.md
```

它们相关，但不一定完全等价。AI 如果直接合并，可能会丢失概念边界。

你需要决定：

- 是完全同义，应该合并？
- 是上下位关系，应该互相链接？
- 是相关但不同，应该保留两个页面？

#### 2. 重命名 canonical page

例如：

```text
Chunking.md -> 文档切块.md
```

重命名会影响：

- WikiLink
- aliases
- redirect
- index
- Git 历史
- Obsidian 图谱

AI 可以生成 rename plan，但最好你确认。

#### 3. 覆盖或改写已有高置信度结论

例如旧页面写：

```text
LLM-Wiki 不是传统 RAG，而是 compile-first 的知识库模式。
```

新资料出现不同说法时，不应自动覆盖。

自动化应该先做：

```yaml
status: disputed
conflict_refs:
  - old: ...
  - new: ...
```

由你决定是否改写主结论。

#### 4. 把一次问答提升为正式概念页

QA 回写可以自动保存为 `qa-note`，但不应该自动变成正式 `concept`。

因为正式概念页会影响知识结构：

- 是否值得成为独立节点？
- 是否已有相近页面？
- 是否只是临时问题？
- 是否应该进入 overview 而不是 concept？

建议：

```text
qa-note 自动
concept page 需要确认
```

#### 5. 批量改链接或批量改名

例如一次性把所有 `[[LLM]]` 改成 `[[大语言模型]]`。

如果 alias 判断错了，会造成大面积污染。

AI 可以先生成：

```text
将修改 38 个文件，112 处链接。
样例 diff 如下...
```

你确认后再执行。

#### 6. 删除页面

删除永远应该谨慎。

推荐默认策略不是删除，而是：

```yaml
status: archived
```

或者移动到：

```text
wiki/_archive/
```

真正删除需要你确认。

#### 7. 处理别名冲突

例如 `MCP` 在你的知识库里可能是：

```text
Model Context Protocol
```

但在其他领域也可能是别的含义。

AI 不应自动把所有 `MCP` 都归到同一个 canonical_id，除非上下文非常明确。

#### 8. 处理隐私、敏感资料和导出边界

如果系统准备把 private raw 的内容写入 public wiki 或 export-safe outputs，需要你确认。

这类风险不是知识准确性问题，而是信息边界问题。

#### 9. 大规模结构重组

例如：

```text
重排整个目录结构
把 10_核心概念 拆成 算法/架构/工程实践
把大量页面迁移到新分类
```

这种改动影响长期浏览习惯和链接结构，应该先生成方案。

#### 10. 低置信度推论写入稳定页面

如果 AI 是从多段资料推断出一个结论，而不是原文明确表达，应该标记：

```yaml
evidence_type: inference
confidence: low
status: needs_review
```

低置信度推论不要自动写成稳定结论。

### 6. L3：默认禁止自动执行的动作

这些动作除非你明确授权，否则不要让系统做。

```text
L3 forbidden_by_default
```

包括：

1. 永久删除 raw 原始资料。
2. 删除 Git 历史或重写历史。
3. 清空或覆盖整个 wiki 目录。
4. 将 private/sensitive 内容导出到 public 区域。
5. 自动提交或推送到远程仓库，如果你还没明确启用。
6. 自动覆盖人工写过并标记为 `pinned` 或 `locked` 的页面。
7. 在无法追溯 source_refs 的情况下批量生成稳定结论页。

L3 的原则是：涉及不可逆、外部扩散、敏感信息、历史破坏的动作，默认禁止。

### 7. 如何让系统“少问你”但仍然安全

关键是给 AI 设计安全默认动作。

当遇到高风险场景时，不要停在那里问一堆问题，而是自动降级处理。

例如：

| 场景        | 不要直接做              | 自动降级为                                   |
| --------- | ------------------ | --------------------------------------- |
| 想删除页面     | 删除                 | 标记 `archived`                           |
| 想合并页面     | 合并                 | 建立 cross-link + `possible_duplicate_of` |
| 想覆盖旧结论    | 覆盖                 | 标记 `disputed`                           |
| 想新建正式概念页  | 直接建 stable concept | 建 `draft` 或 `qa-note`                   |
| 想批量改链接    | 直接改                | 生成 change plan                          |
| 不确定别名是否同义 | 合并 alias           | 标记 `needs_review`                       |

这样大部分工作仍然自动完成，只是高风险动作不会直接破坏知识库。

### 8. 推荐的页面状态字段

为了支持自动化降级，建议增加这些状态：

```yaml
status: draft | stable | disputed | outdated | needs_review | archived
automation_level: safe_auto | auto_with_log | require_review | locked
review_reason: null
```

如果页面不希望 AI 自动改，可以加：

```yaml
automation_level: locked
```

如果页面需要你看：

```yaml
status: needs_review
review_reason: "疑似与 向量检索.md 重复，但语义边界不确定。"
```

### 9. 推荐的动作审批配置

可以写进 `config/automation_policy.yml`：

```yaml
automation_policy:
  safe_auto:
    - add_missing_metadata
    - generate_source_id
    - generate_chunks
    - update_index_links
    - add_existing_wikilinks
    - create_source_summary

  auto_with_log:
    - append_source_refs
    - append_new_evidence
    - create_draft_page
    - create_redirect_page
    - mark_outdated
    - mark_disputed

  require_review:
    - delete_page
    - merge_pages
    - rename_canonical_page
    - bulk_rewrite_links
    - overwrite_stable_claim
    - promote_qa_to_concept
    - resolve_alias_conflict
    - export_private_to_public

  forbidden_by_default:
    - delete_raw_source
    - rewrite_git_history
    - clear_wiki_directory
    - publish_sensitive_content
    - overwrite_locked_page
```

这份配置的价值是让 AI 和脚本都有一致边界。

### 10. 人工确认时应该给你什么信息

当动作进入 L2 时，系统不要只问：

```text
是否确认？
```

而应该给你一份变更计划：

```yaml
review_request:
  action: merge_pages
  risk_level: L2
  reason: 两个页面 aliases 高度重叠，但语义边界不确定。
  affected_pages:
    - wiki/10_核心概念/向量检索.md
    - wiki/10_核心概念/语义搜索.md
  evidence:
    - shared_aliases: ["Semantic Search"]
    - inbound_links: 24
    - conflicting_sections: ["适用边界"]
  proposed_options:
    - merge
    - keep_separate_and_crosslink
    - mark_needs_review
  recommended_option: keep_separate_and_crosslink
```

这样你的干预成本会很低：你不是从零判断，而是在几个选项里拍板。

### 11. 当前项目建议保留人工干预的最小清单

如果你希望尽可能自动化，我建议真正需要你确认的只保留这 8 类：

1. 删除页面或删除 raw 资料。
2. 合并两个已有页面。
3. 重命名规范页。
4. 批量改链接、批量移动文件、批量重构目录。
5. 覆盖 stable 页面里的核心结论。
6. 解决别名冲突或概念边界冲突。
7. 把 QA 笔记提升为正式概念页或综述页。
8. 涉及 private/sensitive 到 public/export 的内容流动。

其他动作基本都可以自动做，最多记录日志。

### 12. 一句话总结

如果希望 LLM-Wiki 大部分自动完成，人工干预应该只保留在“删除、合并、重命名、批量改动、覆盖稳定结论、解决语义冲突、提升正式知识页、处理敏感边界”这些高风险场景。其余动作可以通过 `safe_auto` 和 `auto_with_log` 自动执行；遇到不确定情况时，系统应自动降级为 `draft`、`needs_review`、`disputed`、`archived` 或 change plan，而不是频繁打断你。

## 问题 7：输入标准化层的原理、作用和实现方案

### 1. 输入标准化层是什么

输入标准化层，也可以叫 `normalize pipeline`，是 raw 原始资料进入 Ingest 主流程之前的一层预处理。

它的位置是：

```text
raw 原始资料
  -> normalize 输入标准化
    -> normalized document 标准化文档
      -> chunking 文档切块
        -> analyze / generate / link / index
```

它的任务不是理解知识，也不是生成 Wiki 页面，而是把各种来源、各种格式、各种脏数据，统一整理成：

```text
可分析文本 + 稳定结构 + 基础元数据 + 可追溯位置
```

一句话说：**输入标准化层是把“乱七八糟的原始资料”整理成“后续系统能稳定处理的标准输入”。**

### 2. 为什么必须有这一层

如果你的 raw 永远都是干净 Markdown，可以暂时弱化输入标准化。但真实知识库很快会遇到：

- PDF
- 网页剪藏
- 微信/飞书/Slack 聊天记录
- YouTube 字幕
- 截图 OCR
- Word / Notion / HTML 导出
- 带广告和导航栏的网页
- 表格、代码、图片混排文档
- 编码混乱、换行混乱的复制文本

如果直接把这些东西丢给 Ingest，Ingest 就会同时承担两件事：

```text
脏数据清洗 + 知识编译
```

这会导致系统不稳定。

典型问题包括：

- chunk 切分不准，因为标题和段落结构混乱。
- source_refs 不准，因为没有保留行号、页码或时间戳。
- 检索变差，因为网页广告、导航栏、页脚进入正文。
- 摘要变差，因为模型读到很多无关噪声。
- 表格语义丢失，因为表头和行被拆散。
- 图片说明丢失，因为图片链接没有 alt text 或 caption。
- 重复导入增加，因为同一内容格式不同导致 hash 不同。

所以输入标准化层的价值是：让后面的 chunking、检索、摘要、溯源都站在稳定输入上。

### 3. 输入标准化层不做什么

为了边界清楚，它不应该做这些事：

- 不生成正式 Wiki 页面。
- 不合并概念页。
- 不改写知识结论。
- 不判断新旧观点冲突。
- 不做复杂推理。
- 不把临时摘要写成 stable 页面。

它只做“整理输入”，不做“编译知识”。

这条边界很重要。否则 normalize pipeline 会越来越胖，最后变成另一个不可控的 Ingest。

### 4. 输入标准化的输出是什么

推荐输出一个标准化文档对象 `NormalizedDocument`。

结构可以是：

```yaml
normalized_document:
  source_id: src_20260524_a13f9c
  source_type: web_article
  source_path: raw/articles/example.html
  normalized_path: normalized/src_20260524_a13f9c.md
  title: LLM-Wiki 架构说明
  author: null
  source_uri: https://example.com/llm-wiki
  created_at: null
  imported_at: 2026-05-24T10:30:00+08:00
  language: zh
  content_format: markdown
  text_hash: sha256:xxxx
  extraction_quality: good
  warnings:
    - removed_navigation_blocks
    - missing_image_alt_text
  assets:
    - asset_id: asset_001
      type: image
      path: raw/assets/example.png
      caption: 系统架构图
  location_map:
    type: line_map
    note: normalized lines map back to raw html offsets.
```

同时输出一份标准化 Markdown：

```text
normalized/src_20260524_a13f9c.md
```

后续 chunking 不直接读 raw，而是优先读 normalized 文档。

### 5. 推荐目录结构

可以增加：

```text
your-llm-wiki/
├── raw/
├── normalized/
│   ├── src_20260524_a13f9c.md
│   └── src_20260524_b72d1e.md
├── metadata/
│   ├── sources.jsonl
│   ├── normalized.jsonl
│   └── chunks.jsonl
└── wiki/
```

其中：

- `raw/` 保留原始文件，不改。
- `normalized/` 保存标准化后的可分析文本。
- `metadata/normalized.jsonl` 保存标准化过程的元数据、hash、质量警告。
- `chunks.jsonl` 基于 normalized 文档生成。

这样 raw 和 normalized 分层明确。

### 6. Normalize Pipeline 的步骤

推荐流程：

```text
1. 识别输入类型
2. 抽取文本和基础元数据
3. 统一编码和换行
4. 清理格式噪声
5. 恢复或保留文档结构
6. 处理图片、表格、代码块
7. 保留位置映射
8. 生成 normalized markdown
9. 计算 hash
10. 输出质量报告
```

每一步都尽量做确定性处理，减少 LLM 自由发挥。

### 7. 第一步：识别输入类型

输入类型决定后续处理方式。

可以按文件扩展名、MIME type、内容特征识别：

```yaml
source_type:
  - markdown
  - html
  - pdf
  - docx
  - plain_text
  - chat_export
  - image_ocr
  - code_doc
  - spreadsheet
```

例如：

- `.md` -> markdown
- `.html` -> html
- `.pdf` -> pdf
- `.docx` -> docx
- `.png/.jpg` -> image_ocr
- `.json` 且含 message 字段 -> chat_export

识别结果要写入 metadata，因为后续 chunking 策略会用到。

### 8. 第二步：抽取文本和基础元数据

不同来源抽取方式不同。

| 输入类型 | 抽取重点 |
|---|---|
| Markdown | 保留标题、列表、表格、代码块 |
| HTML / 网页 | 提取正文，去导航、广告、页脚 |
| PDF | 提取页码、段落、标题，保留 page_range |
| DOCX | 提取标题层级、段落、表格 |
| Chat | 保留 speaker、timestamp、turn_id |
| Image OCR | 提取文本、置信度、位置框 |
| Code Doc | 保留代码块、文件路径、函数名 |

基础元数据包括：

```yaml
title:
author:
source_uri:
published_at:
captured_at:
source_type:
language:
```

这些元数据后续会进入 source metadata。

### 9. 第三步：统一编码、换行和空白

这一层看起来琐碎，但很关键。

建议统一：

```text
编码：UTF-8
换行：LF
连续空行：最多保留 2 行
段内硬换行：按规则合并
全角/半角：谨慎处理，不要破坏中文标点
不可见字符：清理
```

尤其是 PDF 和 OCR，经常会出现：

```text
这是一段被错误
换行打断的句子。
```

应该合并为：

```text
这是一段被错误换行打断的句子。
```

但列表、诗歌、代码、表格不能随便合并。所以 normalization 要识别块类型。

### 10. 第四步：清理格式噪声

网页和剪藏最常见的问题是噪声。

应该清理：

- 导航栏
- 广告
- 相关推荐
- 评论区
- cookie 提示
- 分享按钮
- 页脚版权
- 重复标题
- 空链接
- 跟正文无关的侧边栏

但不要清理：

- 正文中的引用
- 图片 caption
- 表格
- 脚注
- 参考文献
- 作者和发布时间

可以使用规则 + 可选 LLM 判断：

```text
规则先清理明显噪声。
不确定的块标记为 maybe_noise，而不是直接删除。
```

这样避免误删正文。

### 11. 第五步：恢复文档结构

标准化后的文档最好统一成 Markdown，因为后续 chunking 更容易按标题、段落、表格、代码块处理。

应该尽量恢复：

- 标题层级
- 段落
- 列表
- 表格
- 代码块
- 引用块
- 脚注
- 图片说明
- 页码或时间戳

例如 PDF 标准化后可以变成：

```md
# 原文标题

<!-- page: 1 -->

## Introduction

正文...

<!-- page: 2 -->

## Method

正文...
```

聊天记录可以变成：

```md
# 会议记录

## 2026-05-24

<!-- turn_id: t001, speaker: speaker_a, time: 10:03 -->
说话人A: 我们需要先定义 source_id。

<!-- turn_id: t002, speaker: speaker_b, time: 10:04 -->
说话人B: 还需要 chunk 级别溯源。
```

这样后续 chunk 能保留 page、speaker、timestamp。

### 12. 图片、表格、代码如何标准化

#### 图片

图片不要简单丢弃。

推荐策略：

```yaml
images:
  keep_local_path: true
  keep_alt_text: true
  keep_caption: true
  ocr_if_text_image: optional
  describe_if_important: optional
```

标准化 Markdown：

```md
![系统架构图](../raw/assets/arch.png)

图注：展示 raw、wiki、schema 三层架构。
```

如果图片很重要但没有说明，可以标记：

```md
<!-- image_needs_description: raw/assets/arch.png -->
```

#### 表格

表格尽量转成 Markdown table。

如果表格太复杂，可以转成：

```md
表格：模型对比

- 模型：A
  - 上下文：128k
  - 适用：长文综合
- 模型：B
  - 上下文：32k
  - 适用：普通问答
```

重点是保留表头和行列关系。

#### 代码

代码必须保留 fenced code block：

````md
```python
def chunk_text(text):
    ...
```
````

不要让格式清洗破坏缩进。

### 13. 位置映射如何保留

输入标准化不能只产出干净文本，还要保留“从 normalized 回到 raw 的路径”。

不同来源有不同位置字段：

| 来源 | 位置映射 |
|---|---|
| Markdown / txt | line_range |
| PDF | page_range + block_id |
| HTML | CSS selector / text offset |
| Chat | timestamp + speaker + turn_id |
| Image OCR | page/image_id + bounding box |
| DOCX | paragraph_id / heading path |

例如：

```yaml
location_map:
  normalized_line_range: 120-145
  raw_page_range: 5-6
  raw_block_ids:
    - p_005_03
    - p_006_01
```

这一步直接影响最小溯源粒度。

如果没有位置映射，后面只能说“来自某文档”，很难说“来自哪一页、哪一段”。

### 14. Normalized Hash 设计

建议至少维护两个 hash：

```yaml
raw_hash: sha256:xxxx
normalized_hash: sha256:yyyy
```

`raw_hash` 用来判断原始文件是否变化。

`normalized_hash` 用来判断标准化结果是否变化。

为什么需要两个？

因为有时候 raw 没变，但 normalize 规则变了，normalized 结果会变。比如你后来改进了网页广告清理规则，输出文本就不同。

所以 metadata 里还应记录：

```yaml
normalizer_version: normalize_v1.2
```

这样后续能判断是否需要重新 chunk。

### 15. 输入标准化质量等级

标准化结果应该有质量标记：

```yaml
extraction_quality: good | partial | poor | failed
warnings:
  - ocr_low_confidence
  - missing_title
  - table_may_be_broken
  - image_without_caption
```

处理策略：

| 质量 | 后续动作 |
|---|---|
| good | 正常进入 chunking |
| partial | 进入 chunking，但标记 warnings |
| poor | 只生成 draft 摘要，等待复查 |
| failed | 不进入 Ingest，写入 error log |

这样系统不会把 OCR 乱码当成高质量知识写进 Wiki。

### 16. Query 输入也需要标准化吗

需要，但它是另一种标准化，叫 query normalization。

Source normalization 处理的是原始资料：

```text
raw document -> normalized document
```

Query normalization 处理的是用户问题：

```text
口语问题 -> 结构化检索意图
```

例如用户问：

```text
卡帕西那个 wiki 跟 rag 到底差在哪？
```

标准化为：

```yaml
intent: compare
canonical_terms:
  - Andrej Karpathy
  - LLM-Wiki
  - RAG
expanded_aliases:
  - Retrieval-Augmented Generation
  - 检索增强生成
query_terms:
  - 区别
  - compile
  - retrieve
```

这两者都叫 normalization，但不要混在一个模块里。

建议分成：

```text
source_normalizer.py
query_normalizer.py
```

### 17. 实现方案：先做最小可用版

当前阶段不需要一口气支持所有格式。

推荐先做 Markdown / 网页剪藏 / 纯文本三类：

```text
v1:
  markdown
  html
  plain_text

v2:
  pdf
  docx
  chat_export

v3:
  image_ocr
  spreadsheet
  video_transcript
```

最小 pipeline：

```text
1. detect_source_type
2. extract_text
3. clean_noise
4. normalize_markdown
5. extract_metadata
6. compute_hash
7. write_normalized_file
8. write_normalized_metadata
```

### 18. 推荐模块结构

可以这样设计：

```text
scripts/
├── normalize.py
├── normalizers/
│   ├── markdown.py
│   ├── html.py
│   ├── plain_text.py
│   ├── pdf.py

└── utils/
    ├── hashing.py
    ├── text_cleaning.py
    └── metadata.py
```

每个 normalizer 输出同一个对象：

```python
class NormalizedDocument:
    source_id: str
    source_type: str
    source_path: str
    normalized_path: str
    title: str | None
    language: str
    content_markdown: str

这样后续 chunking 不需要关心原始格式。

### 19. 示例：网页文章标准化

LLM-Wiki 不是在每次查询时临时检索原文，而是让 LLM 持续维护一个结构化 Wiki。

## 三层架构

...
```

metadata：

```json

```

### 20. 示例：聊天记录标准化

原始聊天可能是：

```text

```

### 21. Normalize Lint 检查项

建议增加 `normalize lint`：

```text
1. normalized 文件是否存在
2. raw_hash 是否存在
3. normalized_hash 是否存在
4. source_id 是否唯一
5. source_type 是否识别
6. title 是否缺失
7. 乱码比例是否过高
8. 空行/换行是否异常
9. 表格是否疑似损坏
10. 代码块 fence 是否闭合
11. 图片是否缺少 alt/caption
12. PDF 是否缺少 page_range
13. OCR 置信度是否过低
14. normalized 是否可进入 chunking
```

Normalize Lint 的目标是避免脏输入进入知识编译阶段。

### 22. 和 Chunking、溯源、缓存的关系

输入标准化层是三件事的基础。

第一，Chunking。

结构清楚的 normalized Markdown，才能按标题、段落、表格、代码块稳定切分。

第二，溯源。

标准化时保留 line/page/turn/location map，后面 source_refs 才能追到具体位置。

第三，缓存。

如果 raw_hash 和 normalized_hash 没变，就不用重复标准化、重复 chunk、重复摘要。

所以它不是“锦上添花”的清洗步骤，而是整个 LLM-Wiki 工程稳定性的入口。

### 23. 当前项目推荐落地步骤

建议你先这样做：

1. 新建 `normalized/` 目录。
2. 新建 `metadata/normalized.jsonl`。
3. 先支持 Markdown 和纯文本标准化。
4. 标准化输出统一为 Markdown。
5. 每个 normalized 文档记录 `source_id`、`source_type`、`raw_hash`、`normalized_hash`、`normalizer_version`。
6. 尽量保留标题、行号、表格、代码块。
7. 对网页剪藏增加简单噪声清理。
8. 对 PDF/OCR 暂时标记 `partial`，不要急着全自动写入 stable Wiki。
9. chunking 只读取 normalized 文档。
10. 增加 normalize lint，拦截明显脏数据。

### 24. 一句话总结

输入标准化层的作用，是在 Ingest 之前把不同格式、不同质量、带噪声的 raw 资料，统一转换成可分析、可切块、可检索、可溯源的 normalized Markdown 和元数据。它不负责生成知识结论，只负责提供稳定输入；它做得越稳，后面的 chunking、source_refs、检索、摘要和 Wiki 生成就越可靠。

## 问题 8：Lint + 失败恢复 + Git 回滚的解决方案

### 1. 这个分类解决什么问题

`Lint + 失败恢复 + Git 回滚` 是 LLM-Wiki 的工程安全网。

它不是为了保证系统永远不出错，而是为了保证：

```text
出错能发现。
中断能恢复。
改坏能回滚。
问题能定位。
```

没有这层，系统一旦自动化程度提高，就会出现这些问题：

- AI 批量改坏链接但你很晚才发现。
- Ingest 跑到一半中断，重跑又产生重复页面。
- 某个 raw 文档解析失败，但没有错误记录。
- 页面被覆盖后不知道原来是什么。
- chunk 规则改了以后，大量 source_refs 失效。
- 自动化改动太多，Git diff 看不懂。

所以这三者要组合设计，而不是分开想。

### 2. 三者的分工

可以这样理解：

| 模块 | 负责什么 | 什么时候用 |
|---|---|---|
| Lint | 发现问题 | 运行前、运行后、定期巡检 |
| 失败恢复 | 让流程可恢复 | Ingest / Normalize / Chunk / Generate 中断时 |
| Git 回滚 | 让改动可撤销 | 自动化改坏、误合并、批量污染时 |

它们之间的关系是：

```text
执行前 Git checkpoint
  -> 运行 normalize / ingest / update
    -> 每一步写 state
      -> 失败写 error log
        -> 成功后跑 lint
          -> lint 通过再 commit
          -> lint 不通过则保留 diff 或回滚
```

### 3. 推荐总体架构

建议做成一个安全执行框架：

```text
safe_run(task)
  1. 检查 Git 工作区是否干净或记录 dirty 状态
  2. 创建 task_id
  3. 写入 task state: started
  4. 创建 Git checkpoint
  5. 分阶段执行任务
  6. 每阶段成功后更新 state
  7. 失败时写 error log 和 failed state
  8. 成功后运行 lint
  9. lint 通过后 commit
  10. lint 不通过则标记 needs_review
```

这个框架让每次自动化都有清晰边界。

### 4. 推荐目录结构

可以新增：

```text
your-llm-wiki/
├── metadata/
│   ├── sources.jsonl
│   ├── normalized.jsonl
│   ├── chunks.jsonl
│   ├── ingest_state.jsonl
│   └── error_log.jsonl
├── reports/
│   ├── lint/
│   │   ├── lint_20260524_103000.md
│   │   └── lint_latest.md
│   └── tasks/
│       └── task_20260524_103000.md
├── scripts/
│   ├── lint.py
│   ├── ingest.py
│   ├── recover.py
│   └── rollback.py
└── log.md
```

最小必需：

```text
metadata/ingest_state.jsonl
metadata/error_log.jsonl
reports/lint/
```

Git 本身负责版本安全，但这些 metadata 负责解释“为什么出错、错到哪一步”。

### 5. Lint 应该分层设计

Lint 不应该只有“断链检查”。建议分成七类：

```text
normalize lint
chunk lint
metadata lint
wikilink lint
source_refs lint
alias/canonical lint
page quality lint
```

#### 1. Normalize Lint

检查标准化输入是否可靠：

- normalized 文件是否存在。
- `raw_hash` 是否存在。
- `normalized_hash` 是否存在。
- `source_type` 是否识别。
- 乱码比例是否过高。
- PDF 是否缺少 page_range。
- OCR 置信度是否过低。
- 代码块 fence 是否闭合。
- 表格是否疑似损坏。

#### 2. Chunk Lint

检查 chunk 是否可用：

- chunk 是否超过 hard max tokens。
- chunk 是否过短且未合并。
- chunk_id 是否重复。
- chunk 是否缺少 source_id。
- section_path 是否缺失。
- previous_chunk / next_chunk 是否连续。
- 是否切断代码块。
- 是否切断表格。
- overlap 是否过大。
- summary 是否为空。

#### 3. Metadata Lint

检查页面元数据：

- concept/entity 页面是否有 `canonical_id`。
- 页面是否有 `title`、`type`、`status`。
- `updated` 是否缺失。
- `type` 是否属于允许枚举。
- `status` 是否属于允许枚举。
- 页面文件名和 title 是否明显冲突。

#### 4. WikiLink Lint

检查链接网络：

- 是否有断链。
- 是否链接到 redirect 页而不是规范页。
- 是否存在孤儿页。
- 是否有重要页面入链过少。
- 是否存在未创建但频繁出现的概念。

#### 5. Source Refs Lint

检查溯源：

- source_refs 是否存在。
- source_id 是否能在 sources.jsonl 找到。
- chunk_id 是否能在 chunks.jsonl 找到。
- chunk_id 是否属于对应 source_id。
- line_range / page_range 是否存在。
- disputed 页面是否有 conflict_refs。
- stable 页面是否缺少来源。

#### 6. Alias / Canonical Lint

检查命名体系：

- alias 是否冲突。
- 同一个 alias 是否指向多个 canonical_id。
- canonical_id 是否重复。
- redirect_to 是否存在。
- redirect 链是否过长。
- 疑似重复页面是否需要 review。

#### 7. Page Quality Lint

检查页面质量：

- summary 是否过泛。
- 页面是否过长。
- 页面链接是否过少。
- 页面是否没有来源。
- 页面是否长期 draft。
- 高频震荡页面是否需要锁定。
- stable 页面是否包含低置信度推论。

### 6. Lint 严重级别

Lint 不应该只有 pass/fail。建议分四级：

```yaml
severity:
  error: 必须修复，否则不能提交
  warning: 可以提交，但要记录
  info: 提醒
  suggestion: 优化建议
```

示例：

| 问题 | 级别 |
|---|---|
| source_id 缺失 | error |
| chunk_id 重复 | error |
| source_refs 指向不存在 chunk | error |
| 断链 | warning/error，取决于页面类型 |
| summary 过泛 | warning |
| 页面链接少 | info |
| 建议增加别名 | suggestion |

自动化规则：

```text
有 error：停止提交，标记 failed 或 needs_review。
只有 warning：允许提交，但写入 lint report。
只有 info/suggestion：正常提交。
```

### 7. Lint 报告格式

建议每次生成 Markdown 报告：

```md
# Lint Report

task_id: task_20260524_103000
created_at: 2026-05-24T10:30:00+08:00
result: failed

## Summary

- errors: 2
- warnings: 5
- info: 12

## Errors

### E001 duplicate chunk_id

- file: metadata/chunks.jsonl
- chunk_id: src_abc_chunk_003
- suggestion: regenerate chunk ids for source src_abc

### E002 missing source_ref target

- page: wiki/10_核心概念/BM25.md
- source_id: src_old
- chunk_id: src_old_chunk_004
- suggestion: check whether source was re-normalized
```

同时更新：

```text
reports/lint/lint_latest.md
```

这样人和 AI 都能快速读最新健康状态。

### 8. 失败恢复的核心：状态机

每个 source 或 task 都要有状态。

推荐状态机：

```text
new
  -> normalized
  -> chunked
  -> analyzed
  -> generated
  -> linked
  -> indexed
  -> linted
  -> done
       \
        failed
```

如果在 `generated` 阶段失败，下次不应该从 raw 重新开始，而是从最近成功阶段恢复。

例如：

```yaml
source_id: src_20260524_a13f9c
task_id: task_20260524_103000
state: failed
last_successful_stage: chunked
failed_stage: analyzed
retry_count: 1
error_code: llm_timeout
error_message: model call timed out after 120s
updated_at: 2026-05-24T10:35:00+08:00
```

### 9. ingest_state.jsonl 示例

```json
{"task_id":"task_20260524_103000","source_id":"src_20260524_a13f9c","state":"chunked","last_successful_stage":"chunked","failed_stage":null,"retry_count":0,"updated_at":"2026-05-24T10:32:00+08:00"}
{"task_id":"task_20260524_103000","source_id":"src_20260524_a13f9c","state":"failed","last_successful_stage":"chunked","failed_stage":"analyzed","retry_count":1,"error_code":"llm_timeout","error_message":"model call timed out","updated_at":"2026-05-24T10:35:00+08:00"}
```

JSONL 的好处是 append-only，出错时也不容易把状态文件写坏。

第二阶段可以迁移到 SQLite。

### 10. 哪些失败可以自动重试

可以自动重试：

- 模型 API 超时。
- 网络短暂失败。
- 速率限制。
- 临时文件写入失败。
- OCR 工具偶发失败。
- 检索服务临时不可用。

不建议自动重试，应该进入 `needs_review`：

- source_id 冲突。
- chunk_id 大量变化。
- 页面合并冲突。
- source_refs 大量失效。
- PDF/OCR 提取质量 poor。
- 模型输出结构严重不合规。
- 可能覆盖 stable 结论。

推荐重试策略：

```yaml
retry_policy:
  max_retries: 3
  backoff:
    type: exponential
    base_seconds: 10
  retryable_errors:
    - llm_timeout
    - rate_limit
    - temporary_network_error
    - file_lock
  non_retryable_errors:
    - source_id_conflict
    - invalid_frontmatter
    - broken_source_refs
    - low_quality_extraction
```

### 11. error_log.jsonl 示例

```json
{"task_id":"task_20260524_103000","source_id":"src_20260524_a13f9c","stage":"analyzed","error_code":"llm_timeout","message":"model call timed out after 120s","retryable":true,"retry_count":1,"created_at":"2026-05-24T10:35:00+08:00"}
```

错误日志至少要保留：

- task_id
- source_id
- stage
- error_code
- error_message
- retryable
- retry_count
- created_at
- affected_files

这样后续排查不会失忆。

### 12. Git 工作流：把每次自动化变成可回滚单元

Git 的作用不是只做备份，而是给每次自动化创建边界。

推荐原则：

```text
一次 ingest / lint fix / update = 一个可理解的 commit
```

commit message 示例：

```text
ingest: add source summary for karpathy llm-wiki article
update: append chunking source refs to concept page
lint: fix missing metadata and broken wikilinks
normalize: add normalized markdown for rag guide
```

不要让一次 commit 同时包含：

```text
新增 raw + 重命名 20 个页面 + 合并概念 + 修复链接 + 改模板
```

这种 commit 很难回滚。

### 13. Git checkpoint 流程

每次自动化任务建议这样走：

```text
1. git status 检查工作区
2. 如果有未提交改动，记录 dirty files
3. 开始 task 前创建 checkpoint
4. 执行自动化
5. 生成 task report
6. 运行 lint
7. lint 通过后提交
8. lint 不通过则不提交，生成 review report
```

如果你愿意更安全，可以用临时分支：

```text
main
  -> automation/task_20260524_103000
    -> 自动修改
    -> lint
    -> 人工或自动 merge
```

个人知识库初期可以不必每次开分支，但大规模改动最好开分支。

### 14. 回滚策略

回滚分三种。

#### 1. 未提交时回滚

如果自动化改动还没 commit，只需要撤销本次 task 触及的文件。

注意不要误删你手动改的内容。

所以 task report 必须记录：

```yaml
affected_files:
  - wiki/10_核心概念/文档切块.md
  - metadata/chunks.jsonl
```

回滚时只处理 affected_files。

#### 2. 已提交但未继续修改

可以用 Git revert 生成反向提交。

原则：

```text
优先 revert，不要 reset history。
```

这样历史清楚。

#### 3. 已经有后续提交

仍然优先 revert 指定 commit，或者手动生成修复 commit。

不要轻易改写历史。

对 LLM-Wiki 来说，保留“曾经发生过什么”通常比历史干净更重要。

### 15. 哪些东西应该纳入 Git

建议纳入：

```text
wiki/
metadata/sources.jsonl
metadata/normalized.jsonl
metadata/chunks.jsonl
metadata/ingest_state.jsonl
metadata/error_log.jsonl
reports/lint/
config/
scripts/
log.md
```

视情况纳入：

```text
raw/
normalized/
```

如果 raw 里有大量 PDF、图片、视频，建议：

```text
raw metadata 入 Git
大文件用 Git LFS 或外部存储
```

不建议纳入：

```text
临时缓存
模型中间大输出
embedding 大文件
本地私密 token
```

### 16. 自动修复和人工确认边界

Lint 发现问题后，能自动修的就自动修。

可以自动修：

- 缺失 `updated`。
- 明显断掉的 redirect。
- 已知 canonical 页的 WikiLink。
- 缺失但可推导的 title。
- 多余空行和格式问题。
- index.md 链接列表。

需要 review：

- 合并重复页面。
- 删除孤儿页。
- 解决 alias 冲突。
- 覆盖 stable 结论。
- 大规模批量改链接。
- source_refs 大量失效。

原则和第六问一致：低风险自动修，高风险生成 change plan。

### 17. 推荐命令设计

可以设计这些命令：

```text
python scripts/lint.py --all
python scripts/lint.py --scope wiki
python scripts/lint.py --scope chunks
python scripts/ingest.py raw/articles/example.md
python scripts/recover.py --task task_20260524_103000
python scripts/recover.py --source src_20260524_a13f9c
python scripts/rollback.py --task task_20260524_103000
python scripts/rollback.py --commit abc123
```

每个命令都输出结构化报告，不要只在终端打印一堆文字。

### 18. 当前项目最小落地方案

不用一开始做全量系统。第一版建议只做：

1. `metadata/ingest_state.jsonl`
2. `metadata/error_log.jsonl`
3. `reports/lint/lint_latest.md`
4. `scripts/lint.py`
5. 每次 ingest 前后跑 `git status`
6. 每次 ingest 成功后一个 commit
7. Lint 至少检查：
   - 断链
   - 缺 frontmatter
   - 缺 source_refs
   - chunk_id 重复
   - source_refs 找不到 chunk
   - alias 冲突
8. 失败时记录：
   - source_id
   - task_id
   - failed_stage
   - last_successful_stage
   - error_message
9. 重跑时从 `last_successful_stage` 继续。
10. 大规模变更先生成 change plan，不直接执行。

这十项做完，系统就具备基本可恢复能力。

### 19. 建议写进规则手册的版本

可以直接写：

```md
## Lint、失败恢复与 Git 回滚规则

1. 每次自动化任务必须有 task_id。
2. 每个 source 必须记录 ingest state。
3. 每个阶段成功后更新 `last_successful_stage`。
4. 失败必须写入 `metadata/error_log.jsonl`。
5. 可重试错误最多自动重试 3 次。
6. 非可重试错误进入 `needs_review`。
7. 每次写入 Wiki 后必须运行 Lint。
8. Lint error 阻止自动 commit。
9. Lint warning 可提交，但必须写入报告。
10. 每次成功 ingest 或 lint fix 应形成一个语义清楚的 Git commit。
11. 大规模改动应在临时分支或 change plan 中完成。
12. 回滚优先使用 revert，不重写 Git 历史。
```

### 20. 一句话总结

`Lint + 失败恢复 + Git 回滚` 的解决方案，是把每次自动化都纳入一个可检查、可恢复、可撤销的执行框架：Lint 负责发现结构和质量问题，状态机与错误日志负责记录任务进度和失败原因，Git commit/checkpoint 负责把每次变更变成清晰可回滚的单元。第一版先做到 ingest_state、error_log、lint_latest、最小 lint 检查和每次 ingest 一个 commit，就能显著降低系统自动化后的失控风险。
