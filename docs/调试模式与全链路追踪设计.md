# MyAgentWiki 调试模式与全链路追踪设计

## 1. 目标与边界

调试模式用于回答三类问题：一次命令实际执行了哪些步骤、数据如何拆分和流转、LLM 每次请求为何成功或失败。它只在用户明确要求调试模式时启用，不改变正常模式的处理结果。

调试模式覆盖初始化完成后的工作区业务命令，不覆盖 `init`、`doctor` 和 `bootstrap`。统计只描述单次运行，不做跨运行聚合。所有统计由 Python 根据记录计算，不调用 LLM。

## 2. 开启方式

工作区业务命令统一接受 `--debug`：

```bash
python3 -m myagentwiki ingest --target-dir /path/to/workspace --debug
python3 -m myagentwiki query "问题" --target-dir /path/to/workspace --debug
```

当用户明确说“用调试模式运行……”时，Agent 应在实际业务命令上添加 `--debug`。没有该表达时保持正常模式。

## 3. 运行目录

调试根目录来自工作区 `config/project.yml` 的 `paths.logs`，默认运行目录为：

```text
logs/debug/<run_id>/
  run.json
  steps.jsonl
  lineage.jsonl
  snapshots/
  llm/
  report.md
```

`run_id` 使用 UTC 时间和随机后缀生成，不能仅依赖秒级时间。`run.json` 在业务处理前创建，初始状态为 `running`；正常结束、已知失败和用户中断分别写为 `success`、`failed` 和 `interrupted`。`record_complete` 只表示调试记录是否完整，业务命令失败但记录完整时仍可为 `true`。进程被强制终止时允许保留 `running`，此时 `record_complete` 为 `false`。

## 4. 步骤记录

`steps.jsonl` 每行一个步骤完成记录，字段如下：

- `step_id`、`parent_step_id`：表达命令、阶段、资料、批次、页面和 LLM 请求的父子关系。
- `name`、`kind`：稳定的步骤标识和类型。
- `status`：`success`、`failed`、`skipped` 或 `interrupted`。
- `started_at`、`finished_at`、`duration_ms`：UTC 时间与单调时钟耗时。
- `input_snapshot`、`output_snapshot`：本步骤完整结构化输入输出快照的相对路径。
- `details`：数量、路径、业务任务 ID、跳过或失败原因等补充信息。

步骤追踪使用显式业务边界，不记录没有排查价值的普通函数调用。复合命令触发的后续流程继续使用同一个运行上下文。

## 5. 数据关系记录

`lineage.jsonl` 记录数据从输入到输出的实际关系：

- `lineage_id`、`step_id`、`created_at`。
- `operation`：`created`、`reused`、`replaced`、`archived`、`removed`、`skipped` 或 `generated`。
- `reason`：直接来自实际分支判断，例如输入哈希相同、转换器版本变化、语义指纹命中、页面缺失或上游数据变化。
- `inputs`、`outputs`：实体类型、实体 ID、路径、内容哈希和对应快照位置。
- `details`：前后指纹、数量、页面类型、批次编号等。

导入链路必须能够按实际 ID 追踪：

```text
source -> normalized -> structure_block / evidence_block / knowledge_unit
       -> chunk -> claim -> semantic_decision -> page -> index
```

未变化数据也必须记录 `reused` 或 `skipped`，不能只记录新生成数据。重新生成时必须同时保留变化前和变化后的快照引用。

## 6. 快照边界

`snapshots/` 保存步骤输入、输出以及变化前后的完整文本和 JSON 数据。快照文件名包含步骤序号和用途，内容使用 UTF-8 JSON；无法直接 JSON 序列化的值转换为稳定的字符串或元数据结构。

原始图片、Office、PDF 和其他二进制文件不复制到调试目录，只记录绝对路径、文件大小、MIME 类型和 SHA-256。LLM 图片输入同样不保存 base64 或二进制内容。

完整快照可能包含原始资料和知识库内容，必须将 `logs/debug/` 加入 Git 忽略并按敏感数据对待。

## 7. LLM 请求记录

每个逻辑请求写入 `llm/<request_id>.json`，并与当前步骤和运行编号关联。记录内容包括：

- 任务名、函数名、函数说明、指令、参数 Schema、处理后的上下文和图片元数据。
- 在线模型、API 风格、CLI 模型、提示版本、Schema 版本和合同版本。
- 每次在线重试与 CLI 备用尝试的开始结束时间、耗时、等待时间、状态和错误分类。
- 原始函数名与参数文本、JSON 修复状态、Schema 检查和业务检查后的结构化结果。
- 服务端请求编号和 token 用量；线路未提供时显式写 `available: false`。
- 调试模式下 Codex CLI 的 JSONL 事件、标准错误和退出码。

API Key、认证头、Cookie 和从本地配置读到的凭据值不得进入调试记录。在线请求记录 API 方法参数时，图片 data URL 必须替换为图片元数据。

现有 `logs/llm_requests.jsonl` 继续保留脱敏摘要；调试模式下只增加 `run_id`，不向该文件写入完整上下文或输出。

## 8. 保留与清理

`config/project.yml` 增加：

```yaml
debug:
  retention_days: 7
```

每次调试运行开始前，以及执行 `debug-list`、`debug-show` 时，清理已到期运行。清理只允许删除解析后仍位于当前工作区调试根目录下、带有效 `run.json` 且 `expires_at` 已过期的运行目录；不跟随符号链接，不删除当前运行。

系统不启动后台任务，因此“保留 7 天”表示到期后在下一次调试相关命令中清理。用户可以随时手工删除单个运行目录或整个 `logs/debug/`。

## 9. 查看与报告

新增只读命令：

```bash
python3 -m myagentwiki debug-list --target-dir /path/to/workspace
python3 -m myagentwiki debug-show --target-dir /path/to/workspace --run-id latest
python3 -m myagentwiki debug-show --target-dir /path/to/workspace --run-id <id> --source-id <id>
python3 -m myagentwiki debug-show --target-dir /path/to/workspace --run-id <id> --request-id <id>
```

`debug-show` 的 `--source-id`、`--step-id`、`--request-id` 互斥。两个命令都支持 `--json`。

`report.md` 至少包含运行状态、总耗时、主要阶段耗时、LLM 逻辑请求与尝试次数、重试等待、token 用量、失败和修复次数、各类数据操作数量，以及按来源整理的数据流摘要。嵌套步骤的耗时不能相加后冒充总耗时。

## 10. 失败处理

启用调试模式后，如果运行目录无法在业务处理前创建，命令直接失败。运行中写记录失败时，调试运行标记为 `failed` 或 `trace_incomplete`，不得把缺失记录显示为完整成功。

业务异常仍遵循现有错误返回方式。调试结束逻辑必须使用 `finally` 写入尽可能完整的 `run.json` 和 `report.md`；调试记录本身不得修改业务账本或用虚假结果替代失败的 LLM 请求。
