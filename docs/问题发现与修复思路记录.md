# 问题发现与修复思路记录

本文件用于记录在对话和实际使用中发现的 MyAgentWiki 问题，以及当时形成的修复思路。

记录原则：

- 只有用户明确要求记录时才追加。
- 每条问题同时记录现象、影响范围、初步原因和可执行的解决方案。
- 若涉及用户工作区中的具体样例，应保留 claim/chunk/page 的可追踪线索。

## 1. 关键词触发语义判断导致误判

### 现象

当前系统里存在多处通过单个关键词触发语义分类或页面路由的启发式规则。典型例子是 claim 文本中出现“案例”时，被判断为 `knowledge_role=example`、`page_intent_hints=["example"]`。

用户工作区样例：

```text
对高频或典型故障案例进行系统复盘，提炼标准化处理流程与简易维修方法，制作图文或视频形式的培训素材，面向城市运营团队开展专项培训，提升一线人员自主解决故障与应急处置能力
```

该 claim 当前被标记为：

```text
claim_type=fact
knowledge_role=example
page_intent_hints=["example"]
```

但从实际语义看，这句话是在描述“故障处理组”的职责或工作方法，不是在提供一个具体示例。更合理的角色可能是 `fact`，若强调动作流程，也可能是 `procedure`。

### 初步原因

相关逻辑位于 `src/myagentwiki/agent_hook.py` 的 claim role / page intent 规则中。当前规则使用类似下面的关键词判断：

```python
elif any(marker in text for marker in ("例如", "比如", "示例", "案例")):
    role = "example"
    page_intent_hints = ["example"]
```

类似风险还存在于其他语义触发词：

- `案例` -> `example`
- `规则 / 参数 / 清单 / 列表` -> `reference`
- `步骤 / 如何 / 怎么 / 首先 / 然后` -> `procedure` 或 `guide`
- `时间线 / 历史 / 历程 / 演变` -> `timeline`
- `是 / 用于 / 意味着 / 是一种` -> `definition` 或 `concept`
- `系统 / 能力 / 职责 / 机制 / 设计 / 定义` -> `concept`

这些词在业务文档中经常只是普通名词或职责描述的一部分，不能单独决定语义角色。

### 影响

- Claim 的 `knowledge_role` 可能不准确。
- `page_intent_hints` 可能把 claim 路由到错误页面类型。
- 后续页面生成可能产生不必要的 example / reference / guide / timeline 页面。
- 同一类原文结构可能因为局部关键词被分散到不同 wiki 目录，例如同属“岗位职责”的页面被分到 `references/`、`examples/`、`concepts/`。
- 查询排序和 answer-ready reading pack 可能被错误页面类型影响。

### 解决思路

1. 把单关键词规则升级为“关键词 + 句式 + 负面语境”的组合判断。

   例如 `example` 应优先命中这些强模式：

   ```text
   例如：...
   比如：...
   示例：...
   案例：某次事件/某个场景/某个用户...
   ```

   但遇到以下语境时不应直接判为 `example`：

   ```text
   复盘案例
   管理案例
   分析案例
   整理案例
   案例库
   案例素材
   案例培训
   典型案例进行...
   ```

2. 为高风险词增加 negative pattern。

   示例：

   ```text
   处理/复盘/管理/分析/整理 + 案例 -> 倾向 fact/procedure，不直接判 example
   制定/执行/落地/运营 + 规则 -> 倾向 fact/procedure，不直接判 reference
   提升/支持/说明 + 如何/怎么 -> 不直接判 guide
   历史数据/历史运营数据 -> 不直接判 timeline
   ```

3. 将 claim role 和 page intent 的判定结果记录更明确的 reason。

   例如从笼统的 `agent_hook_claim_role_batch_v1` 拆成：

   ```text
   role_example_positive_pattern
   role_example_blocked_by_case_management_context
   role_reference_positive_table_or_config_pattern
   role_reference_blocked_by_business_rule_context
   ```

   这样后续 review 和报告中能解释“为什么这么判”。

4. 增加回归测试。

   至少覆盖：

   ```text
   对高频或典型故障案例进行系统复盘... -> 不应为 example
   例如：某城市出现车辆离线时... -> 应为 example
   制定运营规则并落地执行... -> 不应为 reference
   参数表包含字段 A/B/C... -> 应为 reference
   历史运营数据分析... -> 不应为 timeline
   产品演变经历三个阶段... -> 应为 timeline
   ```

5. 重新收敛现有工作区。

   修复源码后，通过正常 CLI 流程重跑相关语义角色判定或 ingest，不直接手改 `state/*.jsonl`。

### 待确认

- 目前已先保留在 `agent_hook.py`，并通过更保守的结构优先规则、负面语境和 lint warning 收口；后续如果不同用户语料差异很大，再考虑迁移到可配置规则文件。
- role / page intent 的判定原因已通过 `reason_code`、`risk_flags`、`semantic_decision_ids` 和 page route 投影进入语义账本与页面记录；是否进一步在更友好的 report / review-list UI 中展示，仍可后续增强。

### 当前实现状态

已基本解决“一票关键词”导致的主链路误判问题。

当前实现不再把 `案例 / 规则 / 历史 / 如何 / 用于` 这类中文词作为单独决定项，而是按以下顺序处理：

1. 优先读取 Markdown Structure IR、Evidence Block、Knowledge Unit 和 `structure_context / group_context`。
2. 将局部关键词沉淀为 `content_tags` 或 `semantic_features`，只作为弱特征。
3. 对 `案例库 / 产品规则 / 历史数据 / 如何` 等高风险语境写入 `ambiguous_*` risk flags。
4. 页面意图层增加二次校验，单条 specialized hint 不足以生成 `example / reference / guide / timeline` 页面。
5. `lint` 新增 warning 级检查，用于提示未复核的语义风险和被降级的 page intent brake。

已覆盖的代表性回归包括：

```text
团队整理历史数据用于分析转化趋势 -> 不应进入 timeline
我们沉淀案例库，方便新人学习常见问题 -> 不应进入 example
产品规则在这次迭代中需要继续完善 -> 不应进入 reference
案例：某城市出现车辆离线...输入/过程/结果... -> 应进入 example
参数表 / 字段表 / Markdown 表格 -> 可进入 reference
起初 / 随后 / 后来 的连续演进结构 -> 可进入 timeline
```

仍需注意：

- 这不是把所有语义判断都写死成规则，而是给默认保守 hook 和真实 LLM hook 建立同一套结构优先协议。
- 当前真实 LLM 接入通过 `myagentwiki.agent_cli_hook` 调用 Codex / Claude Code CLI；默认模板仍使用本地保守 `agent_hook`，失败时回退到保守路径。
- lint 中的 `claim_semantic_risk_flags_reviewed` 和 `semantic_page_intent_brakes_reviewed` 是 warning 级刹车，不代表 ingest 失败。

## 2. Markdown 列表标题与正文被拆成独立 claims

### 现象

用户工作区中的业务文档大量使用 Markdown 列表表达“职责标题 + 职责正文”：

```markdown
- **支付和支出渠道问题处理**

负责对接支付渠道（如微信支付、支付宝）及支出渠道（如云账户），接收并处理代理商或内部团队反馈的渠道相关问题；根据业务需求，主动与渠道服务商沟通，推动问题解决与流程优化。
```

当前 claim 抽取会把列表标题和下方正文拆成独立 claims：

```text
支付和支出渠道问题处理
负责对接支付渠道（如微信支付、支付宝）及支出渠道（如云账户），接收并处理代理商或内部团队反馈的渠道相关问题
根据业务需求，主动与渠道服务商沟通，推动问题解决与流程优化
```

类似标题型 claim 包括：

```text
城市端人员信息管理
故障维修经验沉淀与赋能
开发部开发小组分工
客服中心开发组（南宁）
```

这些标题更适合作为正文 claim 的上下文，不适合作为独立知识声明。

### 初步原因

相关逻辑位于 `src/myagentwiki/cli.py` 的 `split_claim_candidates_from_text` 附近。当前候选 claim 会按句号、分号、问号、感叹号和换行切分，其中换行规则类似：

```python
raw_pieces = re.split(r"(?<=[。！？!?；;])\s*|\n{1,}|(?<=\.)\s{2,}", text)
```

因此 Markdown 中的：

```markdown
- **标题**

正文
```

在去掉列表符号和加粗标记后，会自然变成两段文本，并被抽成多条 claim。

此外，长句二次切分还可能按逗号、分号、连接词继续拆分职责段，导致一些片段脱离原始上下文。

### 影响

- 列表标题被当成简单知识，增加噪声 claim。
- 正文 claim 丢失标题上下文，单独看时可能不完整。
- 职责类长句被过度拆分后，可能出现弱语义片段，例如：

  ```text
  及时反馈一线问题
  协调资源解决运营瓶颈
  保障业务稳健运行
  ```

- 后续 claim role、page intent、页面生成、查询排序都会受这些噪声和碎片影响。

### 候选解决方向

后续再确定具体方案。当前可考虑的方向包括：

1. 在 claim 抽取前识别 Markdown 列表标题块。

   将以下结构识别成一个逻辑块：

   ```text
   label = 支付和支出渠道问题处理
   body = 负责对接支付渠道...
   ```

2. 不再为纯列表标题单独生成普通 claim。

   标题可作为 `section_label`、`local_heading` 或类似 metadata 保存。

3. 生成 claim 时保留标题上下文。

   可选方式：

   ```text
   支付和支出渠道问题处理：负责对接支付渠道...
   ```

   或：

   ```json
   {
     "text": "负责对接支付渠道...",
     "section_label": "支付和支出渠道问题处理"
   }
   ```

4. 对职责类文档降低长句二次拆分力度。

   尤其在 `主要职责 / 岗位职责 / 部门职责` 这类 chunk 中，优先保留完整职责段；只有遇到明确多个独立句子时再拆分。

5. 增加回归测试。

   至少覆盖：

   ```text
   - **支付和支出渠道问题处理** + 正文 -> 不生成纯标题 claim
   正文 claim 应保留“支付和支出渠道问题处理”上下文
   职责段中用分号连接的多个动作不应被拆成过弱片段
   ```

### 待确认

- 最终采用“标题并入 claim 文本”，还是“正文 claim + 标题 metadata”的结构化方案。
- 是否需要给业务职责类文档增加专门的 document_kind 或 chunk_strategy。
- 是否需要提供一次迁移/重跑流程，清理现有工作区中的标题型 claims。

## 3. 页面路由没有优先尊重原文结构，导致同类岗位职责分散到不同目录

### 现象

用户工作区中，原文同属“岗位职责”的多个工作组页面被生成到不同 wiki 目录：

```text
wiki/references/岗位职责 综合运营部 平台运营组.md
wiki/references/岗位职责 综合运营部 支出核算组.md
wiki/references/岗位职责 综合运营部 固定资产组.md
wiki/examples/岗位职责 综合运营部 故障处理组.md
wiki/concepts/岗位职责 综合运营部 城市运营组.md
wiki/concepts/岗位职责 综合运营部 数据分析组.md
wiki/concepts/岗位职责 综合运营部 共享电单车组.md
wiki/concepts/岗位职责 开发部.md
```

这些页面从原文结构看都属于“岗位职责 / 部门或小组职责”，但系统按推断出的 `page_intent` 分别路由到了 `reference`、`example`、`concept`。

### 初步原因

页面生成目录当前主要跟随 `page_intent`：

```text
reference -> wiki/references/
example -> wiki/examples/
concept -> wiki/concepts/
```

而 `page_intent` 又会受到 claim 级 `page_intent_hints` 和关键词启发式影响。例如：

- 平台运营组包含“运营规则”，触发 `reference`
- 支出核算组包含“费用审批规则”“费用清单”，触发 `reference`
- 固定资产组包含“通知规则”“防控规则”，触发 `reference`
- 故障处理组包含“典型故障案例”，触发 `example`
- 其他组没有被 `reference/example` 抢走，继续进入 `concept`

这说明当前 page intent 路由对局部关键词过于敏感，没有把 `section_path` 中的“岗位职责”作为强结构信号。

### 影响

- 同一类知识被分散到多个目录，降低用户浏览和维护直觉。
- `references/`、`examples/`、`concepts/` 的语义边界被稀释。
- 查询时 page type 加权可能放大错误路由结果。
- 后续 answer-ready 输出可能误把岗位职责页当成参考页或案例页。
- 若继续积累类似文档，wiki 目录会越来越不稳定。

### 候选解决方向

后续再确定具体方案。当前可考虑的方向包括：

1. 原文结构优先于局部关键词。

   当 `section_path` 或 `section_path_parts` 包含以下结构信号时：

   ```text
   岗位职责
   主要职责
   部门职责
   工作职责
   小组职责
   ```

   页面路由应优先进入统一职责类页面，而不是被单条 claim 中的“规则 / 案例 / 清单”等词抢走。

2. 短期统一路由到 `topic` 或 `concept`。

   对职责类页面，先避免进入 `reference/example`：

   ```text
   岗位职责 / 综合运营部 / 平台运营组 -> topic 或 concept
   岗位职责 / 综合运营部 / 故障处理组 -> topic 或 concept
   ```

3. 长期新增专门页面类型。

   可考虑新增：

   ```text
   duty
   role
   org-role
   ```

   对应目录可为：

   ```text
   wiki/duties/
   wiki/roles/
   ```

4. 将“页面类型”和“内容标签”拆开。

   例如页面仍是职责页：

   ```yaml
   type: duty
   content_tags:
     - rules
     - cases
     - training
   ```

   这样“包含案例”不等于“这是案例页”，“包含规则”不等于“这是参考页”。

5. 将 page_intent 从一票命中改为计分制。

   示例思路：

   ```text
   section_path 命中岗位职责：duty/topic +5
   单条 claim 命中规则：reference +1
   单条 claim 命中案例：example +1
   多条明确参数/字段/配置表：reference +3
   多条明确示例句：example +3
   ```

   这样职责结构不会被单个关键词带跑。

6. 增加回归测试。

   至少覆盖：

   ```text
   岗位职责 / 综合运营部 / 平台运营组 不应因“运营规则”进入 references
   岗位职责 / 综合运营部 / 故障处理组 不应因“典型故障案例”进入 examples
   真正的 FAQ / 参数表 / 字段清单 仍应进入 references
   真正的案例复盘页面仍应进入 examples
   ```

### 待确认

- 短期是否先统一职责类页面到 `concepts/`，还是新增 `topics/` 输出。
- 长期是否引入 `duty` / `role` 页面类型和目录。
- 页面类型与内容标签已在语义层拆开；`content_tags / semantic_features` 当前主要保存在语义决策、claim projection 和结构上下文中，是否进一步稳定进入 page frontmatter 仍可后续增强。
- 是否需要一次重建流程，把现有岗位职责页面从 `references/examples/concepts` 收敛到统一目录。

### 当前实现状态

已解决“局部关键词把同类结构页面分散到不同目录”的通用机制问题，但尚未新增 `duty / role` 专门页型。

当前落地方式是：

1. `claim_role` 不再因单个 `案例 / 规则 / 历史 / 如何` 直接给出 specialized page hint。
2. `page_intent` 读取 claim group 的角色分布、结构上下文、内容标签和证据块类型，而不是只看单条 claim。
3. specialized 页型必须有组级证据或强结构证据；不足时降级为 `topic`，若 claim group 满足概念条件，再由统一逻辑提升为 `concept`。
4. 表格行仍是强 reference 结构证据；普通 `字段：值` / 冒号句不再自动压过正文语义，避免 `案例：...` 被误当成 reference。
5. 已新增混合中文文档端到端回归，覆盖 guide、example、reference、timeline、普通学习笔记和歧义工作记录同批导入。

因此，岗位职责类文档不会再仅因为局部出现“规则 / 案例 / 清单”就进入 `references/` 或 `examples/`。但如果后续希望让这类内容独立进入 `wiki/duties/` 或 `wiki/roles/`，仍需要新增正式 page taxonomy、模板和迁移/重建策略。

## 4. 组织元信息抽取不一致，部分负责人和人数信息未进入 claims

### 现象

对用户工作区原文与 active claims 做覆盖检查后，未发现 raw 到 chunk 的明显缺失，但发现一批组织元信息没有进入 active claims。

覆盖检查报告：

```text
/Users/sunweisheng/Library/Mobile Documents/iCloud~md~obsidian/Documents/RawWiki/raw_claim_coverage_report.md
```

疑似未覆盖内容主要包括：

```text
平台运营组
负责人：负责人A
小组人数：4人
主要职责：

城市运营组
负责人：负责人B
小组人数：4人
主要职责：

故障处理组
负责人：负责人B
小组人数：2人
主要职责：

数据分析组
负责人：负责人C
小组人数：7人
主要职责：

固定资产组
负责人：负责人D
小组人数：4人
主要职责：

支出核算组
负责人：负责人D
小组人数：4人
主要职责：

共享电单车组
负责人：负责人E
小组人数：1人
主要职责：
```

同时，开发部中的部分组织元信息又进入了 claims，例如：

```text
负责人：负责人F（兼任）、负责人G（副经理）
部门人数：共66人（含南宁团队）
```

这说明组织元信息抽取存在不一致：同类信息在不同层级或不同格式下，有的被保留，有的被过滤。

### 初步原因

当前 claim 抽取偏向“像完整陈述”的自然语言句子。短标题、负责人、人数、栏目标签这类结构化行容易被判为噪声或不够像 claim。

可能原因包括：

- `小组人数：4人`、`负责人：负责人A` 这类短行缺少常规谓语，被噪声/短句规则过滤。
- 小组标题如 `平台运营组` 更像 section heading，被当成结构信息而不是 claim。
- `主要职责：` 属于结构标签，不应作为普通 claim，但应该参与结构理解。
- 开发部的 `负责人`、`部门人数` 可能因为文本更长、格式略不同或处在更大的 chunk 中而被保留，导致不一致。

### 影响

- 负责人、人数、岗位编制等组织事实可能在 wiki 查询中查不到。
- 组织结构页可能缺少关键元数据。
- 同类信息处理不一致，会让用户难以判断系统到底保留了哪些原文事实。
- 后续如果新增 `duty` / `role` 页面类型，这些字段应成为页面结构化 metadata，而不是随机进入或缺失 claims。

### 候选解决方向

后续再确定具体方案。当前可考虑：

1. 将组织元信息作为结构化字段抽取。

   对职责类 chunk 识别：

   ```text
   group_name
   owner /负责人
   member_count / 小组人数
   department_count / 部门人数
   role_counts / 岗位人数
   ```

2. 区分“结构 metadata”和“普通 claim”。

   例如：

   ```json
   {
     "section_title": "平台运营组",
     "metadata": {
       "负责人": "负责人A",
       "小组人数": "4人"
     }
   }
   ```

   同时可选择是否生成可检索 claim：

   ```text
   平台运营组负责人是负责人A
   平台运营组小组人数为4人
   ```

3. 给职责类页面生成固定信息区。

   页面可优先渲染：

   ```text
   负责人
   人数
   岗位构成
   主要职责
   ```

   而不是把这些信息混在普通 claim 列表里。

4. 统一小组级和部门级规则。

   确保以下格式都能稳定处理：

   ```text
   负责人：负责人A
   负责人：负责人F（兼任）、负责人G（副经理）
   小组人数：4人
   部门人数：共66人（含南宁团队）
   测试岗位：16人
   ```

5. 增加覆盖率检查或 lint 规则。

   对职责类文档，如果发现 `负责人`、`人数`、`岗位：N人` 等结构行没有进入 metadata 或 claims，应给出 warning。

### 待确认

- 负责人和人数是否应该生成普通 claim，还是只进入页面 metadata。
- 若生成普通 claim，是否应自动补全上下文，例如“平台运营组负责人是负责人A”。
- 是否要把 `raw_claim_coverage_report.md` 这类覆盖检查能力做成 CLI 命令或 lint 子项。
