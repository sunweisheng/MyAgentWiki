## 核心判断

### 1. 问题不是“概念页标题不好”，而是语义职责分层不清

如果只在概念页末端补标题过滤规则，系统仍然会不断遇到同类问题：

- 结构标题被当成主题候选
- 步骤标题被当成概念
- 总结段、建议句、示例名误生成正式页面
- 明明应该在 Claim 层解决的问题，被拖到页面层兜底

因此，问题的根源不是“命名策略不够聪明”，而是“语义职责没有前移并显式建模”。

### 2. LLM 的最佳角色是受限语义分析器

LLM 不应作为事实来源，也不应作为任意文本重写器。

更合理的角色是：

- 对脚本难以稳定处理的灰区做结构化判定
- 输出有限枚举、有限字段、有限动作
- 所有结果都能回链到输入对象

这意味着 LLM 最适合做的是：

- 文档结构判定
- 短句候选质量判定
- Claim 角色判定
- 页面意图判定
- 页面路由复核
- 灰区候选的 accept / reject / rename / reroute
- grounded 的可读化改写

当前实现里，真实 LLM 接入不直接依赖某个云 API，而是通过 CLI-first 的 `myagentwiki.agent_cli_hook` 调用 Codex 或 Claude Code。默认工作区仍使用包内保守 `agent_hook`，因此没有登录 CLI、模型不可用、超时或输出无法解析时，系统会回退到保守路径，而不是中断 `ingest`。

### 3. 语义分析应该作为正式阶段，而不是零散 hook

如果把 LLM 只当作若干 hook，系统会长期面临几个问题：

- 同一类判断散落在多个命令里
- 不同命令对同一问题使用不同话语体系
- prompt 升级、schema 升级和缓存失效没有统一落点
- 后续很难解释“为什么这条路由结果和另一条不一样”

因此，语义协同应被正式建模为若干语义分析阶段，而不是零散外挂点。

## 建议保留的专题原则

### 确定性优先，按需进入语义灰区

- 能用脚本稳定解决的问题，不交给 LLM
- 只有在字符串规则不足以可靠判定语义角色时，才进入 LLM 灰区
- 不能因为 LLM 看起来更灵活，就把本可确定的事情交给模型
- Markdown 结构、Evidence Block、Knowledge Unit、section path、表格行、局部标题等结构证据优先于局部关键词

中文文档尤其不能让单个词一票决定语义角色。`案例 / 规则 / 历史 / 如何 / 用于` 等词只应提供弱特征或风险提示；只有当句式、结构、组级上下文共同支持时，才应升级为 `example / reference / timeline / guide / concept` 等页型信号。

短句 / 短 claim 是典型灰区：

- `保留回链` 这类文本很短，但可能是完整主张
- `项目说明` 这类文本也很短，却更像结构壳标题
- 因此不能再让单一长度阈值替代语义判断

推荐流程应为：

1. 规则先拦明显垃圾
2. 把短句灰区批量送入 LLM
3. LLM 返回 `standalone / fragment / title_shell / noise` 等受限标签
4. 脚本再据此决定是否保留 claim、是否进入 review、以及是否允许 `safe_auto`

### 先判页型，再命名，再渲染

正确顺序应为：

1. 先判断内容属于什么语义角色
2. 再判断是否值得成页，以及适合成什么页
3. 最后才允许命名和可读化改写

这条顺序的价值，在于把“生成正式页面”的门槛前移，避免大量噪声候选进入后半段。

### 批处理优先于单例调用

- 默认优先批量调用 LLM
- 以同一任务类型、同一阶段、同一上下文模板为单位组织批次
- 输出必须满足严格 JSON schema

这样做的原因是：

- 减少静态上下文重复传输
- 便于缓存、重试和预算管理
- 便于后续统一审计与回放

当前已落地的语义批处理任务包括：

- `document_analysis`
- `claim_candidate_quality`
- `claim_role`
- `page_intent`
- `page_route`

批处理 payload 会携带 `structure_context / group_context / semantic_features / source_refs / evidence ids` 等结构信息，提示词也明确要求优先使用结构证据，不要对中文关键词做一票判定。

### 语义账本与证据账本必须分离

证据层负责回答“材料里有什么”。

语义层负责回答“系统为什么这样理解和组织这些材料”。

如果把所有可变语义字段直接塞回确定性账本，系统会失去下面这些能力：

- 重跑语义层而不污染证据层
- 比较不同 prompt / 模型 / schema 的判断差异
- 给 lint、review、page rebuild 提供可解释链路

### grounded 输出是硬约束，不是风格偏好

LLM 只能在已有 `normalized / chunks / claims / pages / reviews` 证据上做：

- 分类
- 选择
- 重命名
- 汇总
- 可读化表达

无法 grounded 的结果必须：

- 回退到脚本默认行为
- `abstain`
- 或升级人工判断

## 与当前实现最相关的专题结论

### 1. `document analysis / claim candidate quality / claim role / page intent / page route` 应视为同一条语义主链

不要把它们理解为互不相关的局部优化。

这些阶段共同决定：

- 文档怎么切
- 短 claim 是否值得保留
- Claim 怎么分类
- 页面怎么路由

如果前几步没收口，页面路由再聪明也会不断被噪声拖累。

当前实现中，`page_intent` 不是单条 claim 的即时反应，而是 claim group 级判断；`page_route` 进一步把最终 `route_target / route_reason / rejected_alternatives` 写成可回放语义决策。

### 2. `review-auto` 和 `stable promotion` 本质上也属于语义协同链的一部分

它们虽然更靠近审核和恢复层，但本质上仍然是在处理：

- “哪些对象已足够明确，可以保守自动收口”
- “哪些对象仍然需要人做最终判断”

所以它们不应被看成和语义判定完全无关的独立小工具。

### 3. 页面可读化改写必须晚于页型收口

否则系统会在还没确定对象是否适合成页时，就先做表达润色，最后把表达层误当成结构正确。

顺序必须固定为：

- 先有证据
- 再有语义判断
- 再有页面路由
- 最后才有 grounded rewrite
