# 全链路重构实现计划

## 1. 目标

把 `MyAgentWiki` 从“以页面生成为中心的脚本流水线”重构为 **evidence-first semantic compiler**，并按可落地阶段逐步替换当前实现，而不是一次性推翻重写。

本计划遵循三条原则：

1. 先搭基础设施，再替换高层流程。
2. 先把语义层做成可记录、可回放、可缓存的正式系统，再让更多 LLM 判定接入。
3. 每一阶段都要求 CLI、账本、测试和回退路径同时成立。

## 2. 总体阶段

### Phase 1: 语义基础设施

目标：
- 引入 `semantic/` 目录与 `state/semantic_decisions.jsonl`
- 建立 `semantic batch scheduler` 骨架
- 建立 `document_analysis / claim_role / page_intent` 三类任务配置
- 提供统一的 batch 执行入口与默认 hook 协议

产出：
- 工作区模板新增 `semantic` 配置与目录
- CLI 新增语义批处理入口
- `agent_hook` 新增批处理任务协议
- 初版语义决策缓存与批次报告

验收标准：
- `init` 后工作区具备语义层骨架
- `ingest` 后可单独运行语义批处理命令
- 语义决策可写入账本并可重复命中缓存

### Phase 2: document analysis pass

目标：
- 在 `normalized` 层补齐 `document_kind / structure_quality / chunk_strategy_hint`
- 让 chunking 不再只走单一路径

产出：
- `document_analysis` 决策写回
- chunking 前可读取文档结构语义
- FAQ / timeline / table-heavy / chat-log 等文档可走不同策略

验收标准：
- 语义决策能稳定回链到 normalized 文档
- chunking 可以消费文档结构提示

### Phase 3: claim role pass

目标：
- 把 Claim 从“句子集合”升级成“带知识角色的 Knowledge Unit V1”
- 补齐 `knowledge_role / page_intent_hints / concept_candidate_score`

产出：
- `claim_role` 决策账本
- 查询、审核、页面候选收口可读取知识角色
- 将 `procedure / example / conclusion / structural_shell / meta` 从概念候选里分流

验收标准：
- 明显非概念内容不再自动进入概念候选主路径
- claim 角色批处理可缓存和重放

### Phase 4: page intent pass

目标：
- 把“先命名再看像不像概念页”改成“先定页型，再命名，再渲染”
- 建立正式 taxonomy：`concept / guide / example / topic / reference / timeline / overview / source-summary`

产出：
- `page_intent` 决策账本
- 页面生成链按页型路由
- `source-summary` 从杂项回收站收缩为来源入口页

验收标准：
- 章节标题、问句、总结段、示例名不会误长成概念页
- 非概念内容会稳定落到正确页型或被拒绝成页

### Phase 5: presentation rebuild

目标：
- 让 `wiki / indexes / reading_pack / answer-ready` 正式消费语义层
- 让检索、lint、review 都按 evidence/semantic/presentation 三层工作

产出：
- 检索调权从“固定旧页型”切到“intent-aware”
- 页面模板按 `page_intent` 选模板族
- lint 新增 semantic consistency 检查

验收标准：
- query 能按 `evidence / how_to / timeline / compare` 输出不同阅读路径
- lint 能检查 role/intent/page type 冲突

### Phase 6: 迁移与收口

目标：
- 先建立未来新旧版本之间可扩展的迁移框架，再把当前兼容清理动作挂到这个框架下
- 把旧逻辑降级为兼容层样例，而不是继续做主干

产出：
- 版本迁移分类与执行框架
- 兼容映射规则
- 定向迁移脚本
- V1 之后的清理列表

验收标准：
- 老工作区与未来版本工作区都可进入同一迁移框架
- 新工作区默认走新链路

## 3. 代码落点

### 当前建议的模块拆分

- `src/myagentwiki/semantic.py`
  - 语义决策模型
  - batch scheduler
  - 缓存命中规则
  - ledger 读写辅助

- `src/myagentwiki/agent_hook.py`
  - 保留现有 `review_auto / stable_promotion / grounded render`
  - 新增 batch 任务：
    - `review_document_structure_batch`
    - `review_claim_candidates_batch`
    - `review_page_intent_batch`

- `src/myagentwiki/cli.py`
  - `init` 负责生成 `semantic/` 骨架与配置
  - 新增 `semantic-batch` 命令
  - 后续逐步把 ingest 中的语义阶段接入这里

### 工作区侧新增内容

- `semantic/`
- `semantic/batches/`
- `state/semantic_decisions.jsonl`
- `config/project.yml` 中的：
  - `semantic.batch_scheduler.*`
  - `semantic.document_analysis.*`
  - `semantic.claim_role.*`
  - `semantic.page_intent.*`

## 4. 每阶段实施顺序

### 4.1 先做的最小闭环

1. `init` 生成语义层目录与配置
2. CLI 提供 `semantic-batch --task ...`
3. batch scheduler 能对 `normalized` / `claims` 组批
4. hook 返回结构化批量结果
5. 决策写入 `state/semantic_decisions.jsonl`
6. 支持缓存命中与 dry-run

### 4.2 再做的第二闭环

1. chunking 读取 `document_analysis`
2. claim grouping / page candidate 读取 `claim_role`
3. 页面生成前读取 `page_intent`
4. lint / query 显式检查和消费这些决策

## 5. 迁移策略

### 不立即做强迁移的部分

- 不要求长期保留旧 `concept-summary` 页面并存，旧页型只作为明确迁移/清理对象处理
- 查询侧若需要兼容过渡，应通过显式迁移映射或一次性清理收口，而不是长期保留旧权重体系
- 旧概念页生成逻辑不再作为常驻 fallback，正式主链路直接以新页型路由与生成骨架为准

### 立即切换到新骨架的部分

- 新工作区目录结构
- 新工作区配置
- 新语义账本
- 新批处理 hook 协议

## 6. 测试计划

### Phase 1 必补测试

- `init` 会创建 `semantic/` 与 `state/semantic_decisions.jsonl`
- 配置模板包含 `semantic.batch_scheduler / document_analysis / claim_role / page_intent`
- `semantic-batch --task claim_role` 能写入语义账本
- 相同输入重复执行能命中缓存
- `--dry-run` 不写入账本

### 后续阶段测试

- document analysis 能影响 chunk strategy
- claim role 能阻断明显错误的概念候选
- page intent 能把 `procedure / example / conclusion / structural_shell` 从 concept 路由出去
- lint 能发现 role/intent/page type 冲突

## 7. 当前实施建议

建议从 **Phase 1** 开始逐一落地，顺序固定为：

1. 语义账本与目录
2. batch scheduler
3. 默认 batch hook
4. CLI 语义命令
5. Phase 1 测试补齐

这样后面接 `document_analysis / claim_role / page_intent` 时，系统已经具备正式落盘、缓存、批处理和回放能力，不会再陷入“先写很多临时 if/else，之后再整体返工”的局面。

  - 已把迁移候选拆成 `auto_plan` 与 `report_only` 两类，避免把所有未来版本差异都误当成可自动执行动作。

  - 已把迁移动作的 contract 收敛到中心定义，`compat-report / migrate / lint / apply` 共享同一份动作元数据。
  - 已对外暴露 `action_catalog`，让上层 Agent/LLM 不必从 candidate 反推动作能力。
  - 已补上 `migrate --format prompt|messages|chatml` handoff，只把 `report_only` 灰区交给上层 Agent/LLM 批量判断。
  - 已补上 `migrate` handoff 的批次划分能力，降低多条灰区页型判断时的上下文重复开销。
  - 已补上 `migration_decisions` ledger 与 `migrate-decisions` 入口，让外部批量判断结果可被脚本标准化接回。
  - 已补上 `migration_followups` queue，让 decision ledger 的 apply 结果进入可继续消费的脚本队列。
  - 已补上 `migrate-followups`，让 follow-up queue 至少具备列出与完成的脚本消费入口。
  - 已支持把 migration follow-up 提升为 review item，开始与现有 review 工作流接轨。
  - 已让 `review-auto` 明确认识 `migration_followup`，默认升级而不是误做普通自动裁决。
  - 已补上最小多版本 schema 迁移骨架：旧 `schema_version` 可进入 `compat-report / migrate`，并通过 `upgrade_workspace_schema_to_v1` 纳入统一 action registry。
  - 已把 schema migration 从“单跳动作判断”升级为“transition graph + path planning”骨架；当前虽只注册 `unversioned -> v1`，但输出契约已能表达未来多步跃迁。
  - 已让 `apply_migrate_plan` 能按 `transition_path` 展开并顺序执行多步 schema 迁移，不再只消费最终动作名。
  - 已把 transition registry 提升为版本跃迁元数据层：每一步已可携带 `prerequisites / rollback_strategy / requires_confirmation / notes`，并贯通到 path planning 输出。
  - 已让 `requires_confirmation` 真正进入迁移规划决策：只要 schema path 中有确认步，当前就会保守落到 `report_only`，而不是继续自动 apply。
  - 已补上 `state/schema_confirmations.jsonl` 与 `migrate-schema-confirm`，让需要显式确认的 schema path 在确认后可重新进入 `auto_plan`，而不是永远停留在 `report_only`。
  - 已补上 `migrate --rollback`，可基于最近一次 migration backup snapshot 恢复关键状态与配置。
  - 已补上 `state/migration_runs.jsonl`，让 `plan / apply / rollback` 都进入统一 run ledger，方便 Agent 接力和后续排障。
  - 已把 schema 迁移提升为 transition graph + classifier：现在可区分“已注册可自动升级”“缺 schema_version 需人工确认”“超出支持图谱仅报告”三类情况。
  - 已让 `compat-report / migrate` 支持显式 `to-schema-version` 目标，schema path planning 不再被默认当前版本写死，后续 `v1 -> v2 -> v3` 可沿同一入口继续扩展。
  - 已把显式目标版本的 `report_only` 再细分为“目标版本根本不在已知 registry 中”与“目标版本已知但 transition path 尚未注册”两类，避免未来版本迁移都挤成同一种灰区。
  - 已补上 schema registry 自校验，至少会检查 `version order / transition graph / action contract` 三者是否互相对齐，降低后续补版本定义时把迁移骨架写散的风险。
  - 已把 `risk_level` 纳入 `action_catalog / planned_actions / manual_followups / handoff prompt`，方便后续 Agent/LLM 按风险消费迁移任务。
  - 已把 `migrate` 主视图重排为“schema migration first, compatibility cleanup second”，旧页型收口只作为兼容清理能力存在，不再作为长期并行方案保留。
